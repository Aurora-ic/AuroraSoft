# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AuroraSoft — a multi-tenant psychometric evaluation SaaS for schools (Peru). A psychologist creates an evaluation campaign, each student gets a unique magic link (`/examen/[token]`), answers a test without logging in, and the backend scores it, interprets it against baremos (norm tables), and withholds at-risk reports until a professional reviews them.

Two independent projects, no shared tooling or root package:

- [backend/](backend/) — FastAPI + SQLAlchemy 2 + PostgreSQL 16, Alembic migrations.
- [aurora_ui/](aurora_ui/) — Next.js 16 (App Router) + React 19 + Tailwind v4.

Code, comments, identifiers, and API paths are in Spanish. Keep writing Spanish — `crear_prueba`, `usuario_actual`, `institucion_id`. Do not rename existing symbols to English.

The backend went through a phased remediation (Fases 0–4, tracked in commit-message-free sessions, not in separate docs) that closed the audit findings referenced throughout this file (`B-1`…`B-12`, `C-1`…`C-17`). Where this file says "antes" ("before"), it means before that remediation — the old behavior no longer exists in the code, but the comments explaining *why* the current code is shaped the way it is were kept on purpose. Don't undo a fix because the surrounding comment reads like a historical note; the note is there so the fix doesn't get silently reverted.

## Commands

Backend (run from [backend/](backend/); requires a `.env` with `DATABASE_URL` and `SECRET_KEY` — the app refuses to boot without them):

```bash
uvicorn main:app --reload          # dev server on :8000, Swagger at /docs (only when ENTORNO=development)
alembic revision --autogenerate -m "mensaje"
alembic upgrade head               # apply migrations — the normal way to change schema; see "Migrations" below
python -m seeds.seed_superadmin    # create/reset the AuroraSoft superadmin (uses SUPERADMIN_EMAIL/SUPERADMIN_PASSWORD)
python -m seeds.seed_phq9          # load the public PHQ-9 catalog (items, baremos, item-9 rule, informe content) — idempotent, additive-only on a re-run
python tareas/notificar_agenda_diaria.py   # cron job: emails each psychologist their day's appointments
```

`crear_tablas.py` **drops the entire `public` schema** and rebuilds from models. It is guarded (refuses unless `ENTORNO=development`, plus an interactive `BORRAR` confirmation) and exists only for local resets — never suggest it as a migration path. A database built this way has no `alembic_version` row; stamp it with `alembic stamp head` (never `upgrade`) before touching it with Alembic again, or Alembic will try to recreate tables that already exist.

**File organization**: the 16 `seed_*.py` instrument/bootstrap scripts live under [backend/seeds/](backend/seeds/), not at the backend root — they used to sit directly in `backend/` alongside `main.py`, which is also why every one of them is invoked with `python -m seeds.seed_x` (module form) rather than `python seed_x.py` (direct path): a direct-path invocation only puts the script's *own* directory on `sys.path`, which would break every `from modulos...`/`from core...` import the moment the script isn't sitting next to those packages — the exact same reason `tests/` has used `python -m tests.<archivo>` all along. `seeds/__init__.py` makes it an importable package for that purpose only; nothing on the import side changed (`from modulos.educativo import models` etc. still resolve from `backend/` being on `sys.path`, same as before the move). `backend/bd/` was an empty, unreferenced leftover directory and has been deleted — it held nothing and nothing pointed to it.

The Fase-1 concurrent-double-submit test (CASO 5 inside `verificar_fase1_e2e.py`) used to fail intermittently — both requests returning 200 instead of one 200/one 400 — and was once believed to be TIME_WAIT connection buildup on the dev machine. It wasn't: the row lock (`with_for_update()`) was always serializing correctly at the Postgres level (verified in isolation), but `finalizar_examen_seguro` queried the same `Inscripcion` twice in the same `Session` — once unlocked (Fase 1), once locked (Fase 2) — and without an explicit refresh, SQLAlchemy's identity map handed the Fase 2 query back the *same Python object* Fase 1 had already loaded, with its stale (pre-lock) `estado`, instead of the row Postgres had just unblocked. The idempotency check (`if inscripcion.estado == "Finalizado"`) read that stale value and never fired for the losing request, which then recomputed everything and duplicated real side effects (the risk alert email sent twice, a second informe-generation attempt colliding on `uq_edu_informes_inscripcion`). Fixed by extracting the Fase 2 query into `crud.bloquear_inscripcion_para_finalizar()`, which adds `.populate_existing()` to force the fresh, post-lock row onto that same identity-mapped object. `tests/verificar_concurrencia_finalizar_e2e.py` reproduces the exact mechanism deterministically (two real ORM sessions, no dependence on a real network race) and separately confirms, via a real concurrent HTTP double-submit, that the informe and its version are generated exactly once.

## Backend architecture

`main.py` wires five module routers under `/api`; each module owns its own `models.py` / `schemas.py` / `crud.py` / `router.py` and the router carries its own prefix, so the full path is the mount prefix plus the router prefix:

| Module | Full prefix | Owns |
| --- | --- | --- |
| `modulos/auth` | `/api/auth` | `Usuario` (the only user table), password reset tokens, login |
| `modulos/instituciones` | `/api/instituciones` | `Institucion` — the tenant; licence flags and per-tenant limits |
| `modulos/superadmin` | `/api/personas` | `Persona` (students), the academic structure (`NivelEducativo`/`Grado`/`Seccion`/`MatriculaAcademica`), informed consent (+ its audit trail), ARCO anonymization, scheduled appointments, the clinical expediente timeline, `PersonaDatosFamiliares`/`PersonaAntecedentesClinicos` |
| `modulos/educativo` | `/api/educativo` | tests, dimensions, questions, baremos, campaigns, enrolments, answers, diagnoses, dashboards, follow-up sessions |
| `modulos/documentos` | `/api/documentos` | the institutional-document engine — `TipoDocumento`/`PlantillaDocumento` catalog, `DocumentoInstitucional` and its versions (see "Motor de documentos institucionales" below); also owns `modulos/documentos/pdf_generador.py`, its own PDF renderer, independent of `core/pdf_generator.py` |

Note the mismatch: `superadmin_router` is mounted at `/api/admin` in `main.py` but its own prefix is `/personas`, so persona endpoints live at `/api/admin/personas/...`. `modulos/{clinico,organizacional,seleccion}` are empty placeholders for future verticals.

`main.py` calls `load_dotenv()` as its very first import-time action, before anything reads an environment variable (including Sentry's `SENTRY_DSN`, read a few lines later) — if you add a new top-of-file `os.getenv(...)` in `main.py` or `migraciones/env.py`, it now works from the first line; before this fix it silently read `None` for anything checked ahead of the `core.database` import, which is where `load_dotenv()` used to run as a side effect.

### Multi-tenancy is the central invariant

Every tenant-scoped row carries `institucion_id`. Enforcement lives in [core/deps.py](backend/core/deps.py) and must go through it:

- `obtener_usuario_actual` — decodes the JWT, loads the user, checks the token's credential version against `Usuario.token_version` (see JWT below), and additionally rejects the request if the institution's `plan_activo` is false or its licence expired. `superadmin` bypasses the licence check.
- `verificar_acceso_institucion` — use on any endpoint that takes an `institucion_id` from path/query/body. `superadmin` passes always; everyone else only for their own institution.
- `requerir_rol("superadmin", "admin", ...)` — role gate. Roles are `superadmin` (AuroraSoft staff, `institucion_id` may be NULL), `admin` (school owner), `psicologo`, `colegio`.

CRUD functions that list or mutate tenant data take `institucion_id` and filter on it (see `listar_campanas_de_institucion`, `soft_delete_alumno`, `verificar_propiedad_de_prueba`). When adding an endpoint, thread the tenant filter all the way into the query — **never trust an id sent by the frontend** (`institucion_id`, `persona_id`, `prueba_id`...) when it can instead be derived from the authenticated user or re-validated against the record it claims to belong to. `matricular_roster_en_campana` is the canonical example: it re-checks every `persona.institucion_id` against the campaign's institution from the DB row, not from the request.

Answering a public exam endpoint (no login, just a magic-link token) goes through its own authority chain, not the JWT one: `guardar_respuestas_examen` walks *inscripción → evaluación/campaña → prueba → pregunta → opción* in the database and rejects the whole batch if any (pregunta, opción) pair falls outside it, so a crafted request can't borrow another test's — or another school's — scoring values.

### Scoring engine

[core/algoritmo.py](backend/core/algoritmo.py) is deliberately generic: there is no per-test code. A `Prueba` row carries `modo_calculo` (`likert_suma` or `correcto_incorrecto`) and `escala_minima`/`escala_maxima`, and reverse-scored items are flagged by `Pregunta.es_inverso` — inversion is computed as `(min + max) - valor`. If `escala_minima`/`escala_maxima` are NULL, `resolver_escala()` backfills them from the test's actual answer options instead of raising — a `Prueba` created before the scale was set no longer breaks inverted items with a `TypeError`. Adding a test is meant to be a data-loading exercise (`POST /educativo/pruebas/carga-masiva/` plus baremos, optionally `ReglaInterpretacion` rows), not a code change — **`cargar_test_masivo` used to commit after every single dimension/pregunta/opción instead of once at the end**, so a bad row partway through (e.g. a `dimension_id` that didn't actually belong to the `prueba_id`) left a permanently half-loaded test in the DB with no rollback; it now uses `flush()` throughout and a single `commit()` at the end, with the whole call wrapped in `try/except: db.rollback(); raise`, same pattern as `aplicar_importacion`/`guardar_respuestas_examen` — confirmed in practice by now loading **fourteen** real public-catalog instruments this way, each via its own idempotent `seed_*.py` script under `backend/seeds/` (run as `python -m seeds.seed_phq9` from `backend/`, same module-invocation convention `tests/` already uses, and for the same reason — see "File organization" note after the Commands section): `seed_phq9.py` (PHQ-9, the only one with a full informe/PDF content pipeline — see "Informes" below), `seed_gad7.py` (GAD-7), `seed_chaside.py` (CHASIDE), `seed_apgar_familiar.py` (APGAR-FAMILIAR), `seed_scared.py` (SCARED-C), `seed_rcads47.py` (RCADS-47 Youth), `seed_riasec.py` (IPIP-RIASEC), `seed_rosenberg.py` (EAR/Rosenberg Self-Esteem Scale), `seed_sdq.py` (SDQ-CAS), `seed_cesdc.py` (CES-DC), `seed_barsit.py` (BARSIT — **deliberately partial**, see "Catálogo de pruebas cargadas" below: `visible_para_clientes=False`), `seed_vanderbilt_padres.py` (NICHQ Vanderbilt — Escala de Evaluación para Padres, first real `informante_tipo="padre_madre"` load and first real use of `Dimension.tipo_calculo='conteo_sintomas'` — see "Conteo de síntomas" below), `seed_dass21.py` (DASS-21 — the most permissively licensed instrument loaded so far, explicitly public domain), and `seed_hamilton_autoinforme.py` (a self-report adaptation of a form circulating as "Escala de Hamilton" — **explicitly not** the official heteroaplicada HDRS-17, see "Catálogo de pruebas cargadas" below: `visible_para_clientes=False`). See "Catálogo de pruebas cargadas" below for what's specific to each and the three real engine limits their loading surfaced (all three now closed), a fourth real limit (no constructed-response/free-text item type) that BARSIT's loading surfaced and that remains open, and a fifth real limit (no "N of M items over a threshold" symptom-count scoring) that Vanderbilt's loading surfaced and that is now closed — see "Conteo de síntomas" below. Code comments deliberately don't name any *other* commercial test (CARAS-R, FES, ICAR, etc. — BARSIT is no longer hypothetical, see above) as an aspirational example (see `core/algoritmo.py`, `modulos/educativo/models.py`, `modulos/documentos/models.py`) to avoid implying one is implemented or planned when it isn't yet.

Scores (`valor_puntuacion`, `puntaje_obtenido`, `puntaje_directo`, and the baremo bounds) are `Numeric(12,4)`/`float`, not integers — a test whose items score in fractions (e.g. 0.5, 1.25) keeps its precision all the way to the stored diagnosis and the PDF. Creating or editing a `Baremo` is validated: `puntaje_minimo` can't exceed `puntaje_maximo`, `edad_min` can't exceed `edad_max`, and a new/edited tramo can't overlap an existing one that shares the same dimension, sexo (or NULL = unisex), población (or NULL = any) and puntaje range — the API returns 409 rather than silently creating two tramos where the interpretation query could match either one. A *gap* between tramos is still allowed (it isn't an error to leave, say, 6.00–6.99 uncovered) but is handled explicitly downstream, see below.

Two more `Prueba` columns extend this generic catalog without adding any interpretation behavior yet: `modo_interpretacion` (CHECK-constrained today to the single value `'rango'` — `models.MODOS_INTERPRETACION_VALIDOS`/`MODO_INTERPRETACION_RANGO`) is a deliberate placeholder for a future `'perfil'` mode; nothing in `interpretar_resultados_alumno` reads it yet, so this is zero behavior change so far. `visible_para_clientes` (Boolean, default `True` so no existing test changes behavior) is the switch between a test offered to institutions and an AuroraSoft-internal one — the campaign catalog and campaign creation both filter/404 on it for every non-superadmin role, **never** by test name. `seed_prueba_aptitud_tecnica.py` loads exactly this kind of internal-only test: a non-clinical, non-commercial `correcto_incorrecto`-mode instrument (3 dimensions, 2 age bands with different thresholds) marked `visible_para_clientes=False`, built solely to exercise the second `modo_calculo` branch and the `edad_min`/`edad_max` baremo filter end-to-end (PHQ-9's own baremos are unisex/any-age and never exercise that filter) before any real second clinical instrument is loaded. Tests: `test_modo_interpretacion_unitario.py`, `test_visibilidad_prueba_unitario.py`, `test_prueba_aptitud_tecnica_unitario.py`/`verificar_prueba_aptitud_tecnica_e2e.py`. Migrations: `2026_09_23_1258-bf13b309a06b_modo_interpretacion.py`, `2026_09_23_1316-186e63c7c8d4_visible_para_clientes.py`.

### Informante: who answers is not always who the result is about

Most instruments are self-report (`Prueba.informante_tipo = "estudiante"`, the default, zero behavior change for every test loaded so far), but several real batteries this platform is meant to eventually load — NICHQ Vanderbilt, SDQ, RCADS, SCARED — are specifically designed to be filled out by a parent/guardian or a teacher **about** a student, not by the student. `Inscripcion.persona_id` never changes meaning: it is always the *subject* being evaluated, whether they answered themselves or someone else did on their behalf. `Prueba.informante_tipo` (`"estudiante"` | `"padre_madre"` | `"docente"`, `models.INFORMANTES_VALIDOS`, CHECK-constrained) declares which one this particular `Prueba` row expects — a battery with both a parent and a teacher version (e.g. Vanderbilt) is loaded as **two separate `Prueba` rows**, each with its own items/baremos, exactly the same "one row per variant" data-loading discipline this catalog already uses for everything else (PHQ-9 vs. the internal aptitud técnica test, etc.) — the scoring/interpretation engine never needs to know an informante concept exists.

`Inscripcion.informante_tipo` is a snapshot of `Prueba.informante_tipo` taken by `matricular_roster_en_campana` at enrolment time (same pattern as `grado_seccion_historico` — read once, never re-read from `Prueba` afterward). When it isn't `"estudiante"`, `POST /educativo/comenzar-test/{token}` requires `RegistroAlumnoDemograficos.informante_nombre` (400 otherwise) and stores it, plus the optional `informante_relacion` (e.g. "Madre", "Docente de aula"), onto `Inscripcion.informante_nombre`/`.informante_relacion` — filled only once, never overwritten on resume, same "complete what's still empty" rule the demographic fields already follow. The professional psychometric informe (`core/pdf_generator.py`) prints an "Informante" row in DATOS DE FILIACIÓN whenever `informante_tipo` isn't `"estudiante"`, so a report can never be misread as the student's own self-report when it wasn't. Consent, privacy, and baremo matching are entirely unaffected — they still apply to the *subject* (`persona_id`), regardless of who physically answered.

Combining a parent's and a teacher's perspective on the same student into one document (a common real need for these instruments) doesn't require a new mechanism: it's the same `documentos` engine's `resultados_prueba` sections doing what they already do — two sections in one `DocumentoInstitucional`, each linked (via `PUT .../resultados-prueba`) to a different `Inscripcion` for the same `persona_id`. Migration: `2026_09_29_1100-486fadd173f0_informante_prueba_e_inscripcion.py`. **`informante_tipo="padre_madre"` now has its first real load**: `seed_vanderbilt_padres.py` (NICHQ Vanderbilt — Escala de Evaluación para Padres, see "Catálogo de pruebas cargadas" and "Conteo de síntomas" below) — the foundation built ahead of time worked exactly as intended, zero changes needed to `Inscripcion.informante_tipo`/`informante_nombre`/`informante_relacion` or the exam flow itself. A dedicated `test_informante_unitario.py` for this field specifically is still open work (the new `test_conteo_sintomas_unitario.py` covers the scoring-engine extension this load also needed, not the informante mechanism itself); verified manually against the real DB instead, same criterion already used for every other `seed_*.py` instrument load. Three of the instruments loaded since (see "Catálogo de pruebas cargadas" below) are themselves one piece of a real multi-informant battery — **SCARED-C** (self-report) and **RCADS-47 Youth** (self-report) both have an official parent/caregiver counterpart (SCARED-P, RCADS-47 Caregiver) that would load as its own `Prueba` with `informante_tipo="padre_madre"`, and **SDQ-CAS** (autoinforme) is explicitly a 3-informant instrument by design (student/`padre_madre`/`docente`, each with its own cutoff table already in the ficha técnica) — none of the parent/teacher versions are loaded yet, only because their literal item text hasn't been provided in full (SDQ's ficha gives just two grammatical-adaptation examples, not the complete 25-item Padres/Maestros wording), not because of any remaining architectural gap.

Texto de ítems **temático/paráfrasis, no literal** (la ficha que lo sustenta señala explícitamente que el instrumento es de derechos de autor y no reprodujo el texto oficial) — reemplazar `PREGUNTAS` por el formulario real que use cada colegio es un cambio de datos, no de estructura. Baremo: el corte clásico internacional (≥10) queda activo por defecto (`criterio_normativo=NULL`) y el corte reportado en evidencia peruana secundaria (≥8, especificidad mucho menor, 50.1%) se cargó como segundo criterio (`criterio_normativo="corte_peru_2024"`) — **ya no son mutuamente excluyentes**, ver "Criterio normativo de Baremo" más abajo, que cerró el límite del motor que este mismo script documentaba antes.
- **`seed_chaside.py` (CHASIDE)** — 14 dimensiones (7 áreas vocacionales × Intereses/Aptitudes), 98 ítems dicotómicos, texto literal (protocolo real de UCASAL). No clínico — ningún tramo tiene `es_alerta=True`. La matriz de corrección usada es la del propio protocolo UCASAL, no la de una ficha técnica secundaria que tenía una inconsistencia real verificada (el ítem 30 aparece en sub-escalas distintas según la fuente).

De las dos tablas de corte peruanas contradictorias reportadas, el Sistema A (con corroboración independiente de una tercera fuente) queda activo por defecto (`criterio_normativo=NULL`) y el Sistema B se cargó como segundo criterio (`criterio_normativo="sistema_b"`) — ver "Criterio normativo de Baremo" más abajo. `es_alerta=True` en los dos tramos de disfunción (severa/moderada), en ambos sistemas, es una decisión clínica explícita, no un valor por defecto.
- **`seed_scared.py` (SCARED-C)** — 5 dimensiones (sub-escalas clínicas reales), 41 ítems literales (formulario real, Htal. Zubizarreta), escala 0-2, edad 8-12 (la que declara el propio formulario, no el rango internacional más amplio de 8-18). Solo la versión autoinforme (`informante_tipo="estudiante"`); SCARED-P pendiente.
- **`seed_rcads47.py` (RCADS-47 Youth)** — 6 dimensiones, 47 ítems literales (formulario oficial © Chorpita y Spence, childfirst.ucla.edu — **con licencia limitada, no de dominio público**: antes de cualquier uso comercial real hay que confirmar con los autores que la licencia vigente lo cubre), escala 0-3, edad 8-18. Texto de ítems **temático/paráfrasis, no literal** (mismo criterio que GAD-7): la ficha técnica no reproduce el cuestionario oficial de 48 ítems, protegido y de **licencia no comercial** (mismo tipo de advertencia que RCADS-47 — verificar con los autores antes de uso comercial real). **No tiene ningún `Baremo` cargado** — la interpretación realmente válida de este instrumento es **comparativa** (ordenar las 6 dimensiones de la misma persona de mayor a menor puntaje y tomar las 3 más altas como código Holland), así que corre en `Prueba.modo_interpretacion='perfil'` (ver "Interpretación por perfil" más abajo), el único de los nueve instrumentos cargados que usa ese modo en vez de `'rango'`. Se evaluaron dos documentos fuente distintos para esta carga; solo el que tenía ficha técnica real (estructura, escala, fórmula de puntuación) se usó como base — un segundo PDF describía un cuestionario de 60 ítems/10 por dimensión en formato de casillas, sin respaldo psicométrico declarado, y no se cargó.
- **`seed_rosenberg.py` (EAR — Escala de Autoestima de Rosenberg)** — 1 dimensión (Autoestima Global, unifactorial — la ficha técnica advierte explícitamente que la estructura positiva/negativa discutida en la literatura "no debe confundirse automáticamente con dos dimensiones oficiales"), 10 ítems literales (traducción española de Atienza, Balaguer & Moreno, 2000), escala Likert 1-4, 5 ítems inversos (2, 5, 8, 9, 10). **Hallazgo verificado por código antes de cargar** (mismo tipo que el ítem 30 de CHASIDE): la ficha técnica secundaria se contradice a sí misma sobre cuáles son los ítems inversos — su sección "3. ÍTEMS" (con asteriscos) y el cuestionario original coinciden en "2, 5, 8, 9, 10", pero sus secciones "5.B" y "CONFIGURACIÓN RECOMENDADA PARA SOFTWARE" dicen "2, 5, 6, 8, 9" (sustituyendo el 10 por un 6 que, en la misma lista, también aparece como ítem *directo* — una contradicción interna irreconciliable). Se cargó el conjunto verificado por las dos fuentes independientes que sí coinciden entre sí. **No clínico — `es_alerta=False` en los 6 tramos (3 por criterio), en ambos criterios**: la ficha técnica es inusualmente insistente en que "no diagnostica... no existe un punto de corte diagnóstico universal" y hasta desaconseja explícitamente escribir afirmaciones categóricas como "la persona tiene autoestima baja" en un informe — la misma `Baremo.interpretacion` reutiliza casi literalmente la redacción no-categórica que la propia ficha sugiere. **Segundo caso real de `criterio_normativo`** (después de GAD-7/APGAR-FAMILIAR): la ficha reporta dos tablas de corte peruanas que se solapan y no coinciden (sección 8, activa por defecto, vs. sección 7 de una muestra de 1,228 estudiantes, `criterio_normativo="percentil_n1228"`) — mismo mecanismo, ningún código nuevo. Solo se cargó la versión original de 10 ítems; una variante peruana estudiada de 9 ítems (omite el ítem 8, con comportamiento psicométrico señalado por más de un estudio) existe documentada pero no se cargó, mismo criterio que SCARED-P/RCADS-47 Caregiver — es una `Prueba` distinta, no un criterio normativo alternativo, si alguna vez se necesita.
- **`seed_sdq.py` (SDQ-CAS — Cuestionario de Capacidades y Dificultades, autoinforme 11-17 años, Robert Goodman)** — 25 ítems literales, escala 0-2, 5 dimensiones "items" (Síntomas Emocionales, Problemas de Conducta, Hiperactividad, Problemas con Compañeros, Conducta Prosocial, 5 ítems cada una) **más 1 dimensión COMPUESTA** ("Dificultades Totales" = suma de las 4 de dificultad, excluyendo Prosocial a propósito — la ficha es explícita: "La escala de conducta prosocial no se incluye en el total") — **primer uso real de `Dimension.tipo_calculo='suma_de_dimensiones'`/`DimensionComponente` fuera de sus propios tests** (ver "Dimensión compuesta" más abajo). **Hallazgo significativo, verificado por una contradicción interna comprobable (no solo por conocimiento externo del SDQ oficial)**: la ficha técnica secundaria lista como invertidos los ítems "1, 4, 7, 9, 11, 14, 17, 20, 21, 25" — los 5 ítems de Conducta Prosocial MÁS los 5 positivamente redactados dentro de las escalas de dificultad — pero invertir los 5 prosociales es demostrablemente incorrecto: la propia ficha (sección de baremos) dice que un puntaje prosocial ALTO es "Normal" y uno BAJO es "Anormal"; si se invirtieran esos 5 ítems, alguien que responde "Absolutamente cierto" (el máximo) a los cinco obtendría el puntaje MÍNIMO (0/10, "Anormal") — invirtiendo el sentido completo de la escala para la persona que más la respalda. Se cargó el conjunto corregido **{7, 11, 14, 21, 25}** (verificado en vivo: una aplicación con "Absolutamente cierto" en los 25 ítems da Conducta Prosocial = 10/10 "Normal", no 0/10 "Anormal"). Edad 11-17 explícita (la ficha advierte contra mezclar grupos de edad). **Sí es cribado clínico** (a diferencia de CHASIDE/IPIP-RIASEC/EAR): `es_alerta=True` en los tramos "Anormal"/"Muy alto", la propia ficha se autodescribe como instrumento de cribado. **Tercer caso real de `criterio_normativo`**: el sistema tradicional de 3 bandas (activo por defecto) convive con un sistema de 4 bandas (`criterio_normativo="cuatro_bandas"`), ambos cargados solo sobre "Dificultades Totales" (la única dimensión para la que la ficha da ambas tablas). Solo la versión autoinforme — las versiones Padres/Maestros (cada una con su propio `informante_tipo` y sus propios puntos de corte, ya documentados en la ficha) no se cargaron por no tener su cuestionario completo de 25 ítems, solo dos ejemplos de adaptación gramatical — mismo criterio que SCARED-P/RCADS-47 Caregiver.
- **`seed_cesdc.py` (CES-DC — Center for Epidemiological Studies Depression Scale for Children)** — 1 dimensión ("CES-DC Total", unifactorial a propósito: la propia ficha técnica indica explícitamente que esta debe ser la dimensión principal porque "no existe una única estructura factorial universal" entre el estudio original de Faulstich et al. y una validación española reciente de 671 escolares, ambos con tres factores pero sin coincidir en su composición — mismo criterio ya usado en APGAR-FAMILIAR/EAR), 20 ítems literales tomados del protocolo de aplicación real proporcionado (no de la paráfrasis temática de la ficha técnica secundaria), escala 0-3, 4 ítems inversos (4, 8, 12, 16, verificados sin contradicción entre ambas fuentes). **Hallazgo de discrepancia documentado, no resuelto por código** (mismo tipo que el ítem 30 de CHASIDE o los ítems inversos de EAR): el ítem 17 del protocolo real dice "Sentía gusto de gritar" mientras que la ficha técnica describe su contenido temático como "Sensación de querer llorar" — una discrepancia de traducción/contenido, no de dirección de puntaje (el ítem 17 no es uno de los invertidos). Se cargó el texto literal del protocolo real, que es el formulario efectivamente en uso. **Solo un criterio normativo cargado** (a diferencia de GAD-7/APGAR-FAMILIAR/EAR/SDQ-CAS): la ficha reporta que el punto de corte óptimo "puede variar entre 12 y 24" pero no entrega una segunda tabla de corte concreta y verificable, así que no se inventó un segundo criterio — el único tramo activo es el corte de referencia internacional/tradicional (≥15), registrado explícitamente como tal y no como "baremo peruano" (la ficha confirma que no existe un baremo peruano nacional verificado de la CES-DC-20). **Solo dos niveles, no cuatro**: la ficha desaconseja explícitamente programar categorías mínima/leve/moderada/severa sin un manual que las defina; se cargan únicamente "por debajo del corte" y "alcanza/supera el corte". `edad_min`/`edad_max`/`sexo`/`poblacion` quedan `NULL` — la ficha reporta rangos de edad incompatibles entre fuentes (6-17 vs. 12-18) y ningún baremo diferenciado por sexo o nivel educativo. **Sin `ReglaInterpretacion`**: la ficha es explícita, "No existen ítems críticos" (a diferencia del ítem 9 de PHQ-9 o el ítem 37 de RCADS-47). Autoinforme (`informante_tipo="estudiante"`), periodo de recall de una semana (no dos, a diferencia de PHQ-9/GAD-7).
- **`seed_barsit.py` (BARSIT — Medición Rápida de Habilidad Intelectual)** — **DELIBERADAMENTE INCOMPLETO, decisión consultada y confirmada con el usuario antes de cargarlo**, no una simplificación silenciosa: 4 de las 5 áreas documentadas (Información/Comprensión Verbal/Razonamiento Verbal/Razonamiento Lógico, 48 de 60 reactivos), con texto literal tomado de un cuestionario institucional real y completo (Universidad Juárez del Estado de Durango) que sí reproduce los 60 reactivos y su clave. La 5ª área, "Razonamiento numérico" (12 reactivos de completar series, ej. "10 15 20 25 ___ 35 40 ___ 50"), **no se cargó porque expone un cuarto límite real del motor, todavía abierto** — ver más abajo. Por la misma razón tampoco se carga el baremo "BARSIT total" (0-60, por grado/edad): está calibrado sobre los 60 ítems completos, y aplicarlo sobre un máximo real de 48 clasificaría mal a cualquier alumno sin ningún aviso. Sí se carga el único baremo que es válido de forma independiente: la tabla "por dimensión" de la ficha (0-4 Deficiente/5-7 Inferior/8-10 Promedio/11-12 Superior, idéntica para las 4 áreas, sin distinción de edad/sexo/grado — el límite inferior se extendió de 1 a 0 para cubrir el piso natural de la escala, no es una categoría inventada). No clínica (`es_alerta=False` en los 16 tramos, mismo criterio que CHASIDE/IPIP-RIASEC/EAR). **`visible_para_clientes=False`, a diferencia de todo lo demás cargado hasta ahora**: la ficha documenta Copyright 1957 (The Psychological Corporation) sin ningún permiso de reproducción/uso comercial especificado — más explícito que la advertencia ya conocida de RCADS-47/IPIP-RIASEC — combinado con que la carga es parcial (una institución que elija "BARSIT" nunca podría obtener el CI/percentil global que razonablemente esperaría). Adaptación/baremo peruano: la ficha es explícita en que ninguno de los dos está acreditado — `edad_min`/`edad_max`/`sexo`/`poblacion` quedan `NULL`. Sin contenido de informe ni `ReglaInterpretacion` (la ficha no reporta ítems críticos).
- **`seed_vanderbilt_padres.py` (NICHQ Vanderbilt — Escala de Evaluación para Padres, 3.ª edición AAP 2020)** — 56 ítems literales (formulario oficial en español, "ADHD Toolkit 3rd Edition"), 6 dimensiones, **primer uso real de `informante_tipo="padre_madre"`** (ver "Prueba.informante_tipo" arriba — la base de datos ya estaba lista desde antes de que cualquier instrumento real la usara) y **primer uso real de `Dimension.tipo_calculo='conteo_sintomas'`** (ver "Conteo de síntomas" más abajo — extensión del motor consultada y confirmada con el usuario antes de construirla, porque el criterio clínico oficial de este instrumento — "6 de 9 síntomas con puntuación ≥2" — no es expresable como una suma comparada contra un rango). **Discrepancia de EDICIÓN detectada entre las dos fuentes de esta carga, resuelta a favor del formulario real** (decisión consultada y confirmada con el usuario): el formulario real (`test.pdf`, 56 ítems, con sus propias casillas de conteo oficial impresas) numera Conducta=27-41 (15 ítems), Ansiedad/depresión=42-48, Funcionamiento=49-56; el documento de puntuación que acompaña la carga usa una numeración de una edición anterior (55 ítems: Conducta=27-40/14 ítems, Ansiedad=41-47, Funcionamiento=48-55). Sin baremo percentilar (las normas estadounidenses de 2022 existen pero la ficha técnica — usada aquí solo como panorama, nunca como fuente de implementación — no reproduce las tablas numéricas reales) y sin baremo peruano (ninguna fuente lo reporta). Solo el formulario para padres — el de maestros (43 ítems, distribución distinta) es una `Prueba` futura separada. Sin contenido de informe.
- **`seed_dass21.py` (DASS-21 — Depression Anxiety Stress Scales, 21 ítems)** — 3 dimensiones (Depresión/Ansiedad/Estrés, 7 ítems cada una), texto literal tomado del documento completo de ClinikLab/Fundación Universitaria Konrad Lorenz (Bogotá — cita la validación colombiana real de Ruiz et al., 2017), que reproduce los 21 ítems y la escala de respuesta íntegros, a diferencia de la ficha técnica secundaria que advierte no poder reproducirlos por derechos de autor. **Licencia más permisiva de las trece pruebas cargadas**: la fuente oficial (UNSW/Psychology Foundation of Australia) declara el DASS en dominio público, descargable y copiable sin restricciones (solo no debe modificarse ni venderse con fines de lucro) — `visible_para_clientes=True` sin reservas. **Baremo por subescala verificado por cálculo entero, no copiado directamente de ninguna fuente**: los cortes oficiales se publican sobre el puntaje ×2 (comparable con el DASS-42 original) y hay que aplicarlos ítem por ítem al puntaje bruto (0-21) para obtener fronteras enteras correctas, no dividir las fronteras del rango ×2 entre 2 (que da fronteras fraccionarias sin sentido). Sin segundo `criterio_normativo` (la evidencia peruana de 2025, 1,163 universitarios de Lima, respalda los cortes tradicionales pero no propone una tabla alternativa con valores propios). Sin contenido de informe.

Se cargó el formulario tal cual, vía el flujo normal de examen (`informante_tipo="estudiante"`), con `nombre_tecnico="HAMILTON_AUTOINFORME"` (nunca "HDRS-17"/"HAM-D") y `nombre_publico` dejando constancia expresa de que esto NO es el instrumento clínico oficial. **Estructura de dominios verificada contra la ficha, no solo con distinta numeración** (a diferencia de BARSIT/Vanderbilt): el formulario real omite dominios oficiales (ansiedad somática, agitación psicomotora, insight), añade un ítem de variación diurna que la propia ficha dice que la HDRS-17 oficial excluye explícitamente de su puntuación, y descompone el ítem oficial único "3. Suicidio" (una escala ordinal 0-4) en 4 preguntas de sí/no independientes. **Ítem 14 invertido — hallazgo verificado por inconsistencia lógica interna** (mismo criterio que los ítems de EAR/SDQ-CAS): el formulario imprime "¿Le encuentra sentido a la vida? Verificado en la BD real: sin la inversión, una persona completamente sana que responde "Sí" a este ítem habría puntuado 1 en vez de 0. **Baremo propio del formulario** (0-7 Normal/8-15 Depresión Menor/>16 Depresión Mayor — decisión consultada y confirmada con el usuario), que no coincide con ninguno de los tres sistemas de la ficha técnica (Bech, "otro sistema", "clasificación alternativa"); el valor exacto "16" quedaba sin cubrir entre los dos tramos impresos y se resolvió a favor de "Depresión Mayor" (mismo tipo de ajuste de piso/techo ya hecho para BARSIT). `es_alerta` en Depresión Menor/Mayor es decisión propia de la plataforma (el formulario no declara cuál nivel es "cribado positivo"). **Tres `ReglaInterpretacion` de seguridad propias de la plataforma** sobre los ítems 15-17 (ideación/planificación/intento suicida directos, cualquier respuesta "Sí" fuerza alerta) — el ítem 14 (invertido) no lleva regla propia, por la complejidad añadida de comparar contra su valor crudo. `visible_para_clientes=False`, mismo nivel de cautela que BARSIT (licencia sin resolver + autenticidad/oficialidad del formulario dudosa). Sin contenido de informe.

**Cinco límites reales del motor, descubiertos al cargar estas pruebas (no al diseñarlo) — cuatro ya cerrados en sesiones posteriores, el que surgió al cargar BARSIT sigue abierto, todos documentados aquí para que no se redescubran desde cero**:

1. **RESUELTO — "dimensión suma de dimensiones."** Tanto SCARED (puntaje total 0-82, suma de sus 5 sub-escalas) como RCADS-47 (Total Ansiedad = suma de 5 sub-escalas; Total Ansiedad+Depresión = suma de las 6) definen oficialmente un puntaje agregado por encima de las sub-escalas, con su propio punto de corte, y no se podían cargar como `Baremo` porque `Pregunta.dimension_id` es una FK única — un ítem pertenece a exactamente una `Dimension`. Ver "Dimensión compuesta: `Dimension.tipo_calculo` y `DimensionComponente`" más abajo, que añade exactamente la `Dimension` marcada como "suma de otras dimensiones" que este punto pedía — SCARED/RCADS-47 en sí todavía no tienen su total cargado con el mecanismo nuevo (es trabajo de datos, no de motor; sigue abierto), pero el motor ya lo soporta.
2. **RESUELTO — ningún eje de "criterio normativo" o "versión de baremación."** Apareció primero con GAD-7 (corte clásico vs. corte peruano) y de nuevo con APGAR-FAMILIAR (dos tablas de corte peruanas contradictorias) — en ambos casos había más de un criterio de interpretación válido y documentado para el mismo rango de puntaje, y el modelo antes solo permitía cargar uno a la vez (cargar los dos como tramos simultáneos chocaba con la validación de solapamiento). Ver "Criterio normativo de Baremo: `Baremo.criterio_normativo` y `Prueba.criterio_normativo_activo`" más abajo — GAD-7, APGAR-FAMILIAR, EAR y SDQ-CAS (su cuarta ocurrencia real del mismo problema) tienen todos sus dos criterios cargados simultáneamente con este mecanismo (ver sus propios bullets arriba, actualizados).
3. **RESUELTO — ningún modo de interpretación comparaba las dimensiones de una misma persona entre sí.** Apareció al cargar IPIP-RIASEC: a diferencia de todo lo clínico cargado hasta ahora (que interpreta cada dimensión contra su propio rango absoluto de `Baremo`), un inventario de intereses tipo RIASEC se interpreta de forma **comparativa** — ordenar las 6 dimensiones de la misma persona de mayor a menor puntaje y tomar las 3 más altas como "código Holland". `Prueba.modo_interpretacion` ya reservaba el valor `'perfil'` exactamente para esto (ver "Scoring engine" arriba) pero nadie había escrito el algoritmo — ver "Interpretación por perfil: `crud.interpretar_perfil_alumno`" más abajo, que lo cierra de fondo (no solo la lectura del PDF, que ya se había resuelto por separado con "Diseño A" — ver esa misma sección más abajo). IPIP-RIASEC ya corre en `modo_interpretacion='perfil'` de verdad, sin ningún `Baremo` cargado.
4. **ABIERTO — ningún tipo de ítem/respuesta de texto libre o construida.** Apareció al cargar BARSIT: 48 de sus 60 reactivos son de opción múltiple y encajan sin cambios en `Pregunta`/`OpcionRespuesta`, pero los 12 de "Razonamiento numérico" piden escribir dos números que faltan en una serie — una respuesta de texto libre, no una selección entre alternativas predefinidas. `guardar_respuestas_examen` valida cada respuesta como un par (pregunta_id, opcion_id) ya existente en la BD, así que no hay forma de representarlo sin inventar alternativas de opción múltiple que ninguna fuente da, o sin un tipo de ítem/respuesta nuevo (un `Pregunta.tipo_respuesta` o similar, más el trabajo correspondiente en `guardar_respuestas_examen`/`calcular_resultados`/el frontend del examen). Por eso `seed_barsit.py` deliberadamente NO carga la dimensión "Razonamiento numérico" ni el baremo "BARSIT total" que depende de los 60 ítems completos (ver su propio bullet arriba) — a diferencia de los otros límites de esta lista, este sigue sin cerrarse; la decisión de no extender el motor ahora fue consultada y confirmada con el usuario, no una simplificación silenciosa.
5. **RESUELTO — ningún criterio de "N de M ítems sobre un umbral" (conteo de síntomas).** Apareció al cargar NICHQ Vanderbilt — Escala de Evaluación para Padres: su criterio clínico oficial ("6 de 9 ítems con puntuación ≥2") no es expresable como una suma comparada contra un rango — una suma puede ser mayor para una distribución de respuestas que en realidad NO cumple el criterio de conteo (ver el ejemplo numérico concreto en "Conteo de síntomas" más abajo). A diferencia de los límites 1-3 (resueltos antes de que el usuario los pidiera explícitamente, como parte del trabajo de carga de cada instrumento), este se resolvió tras consultarlo con el usuario, que confirmó extender el motor en vez de cargar el instrumento sin interpretación automática. Ver "Conteo de síntomas: `Dimension.tipo_calculo='conteo_sintomas'` y `conteo_umbral_item`" más abajo. NICHQ Vanderbilt ya corre en `tipo_calculo='conteo_sintomas'` de verdad, en sus 6 dimensiones.

Ninguna de las trece pruebas nuevas tiene contenido de informe cargado (`motivo_consulta_default`/`tecnicas_adicionales`/`Baremo.conclusion_sugerida`/`recomendacion_sugerida` quedan `NULL` a propósito en los trece scripts — EAR y SDQ-CAS son las únicas cuyo `Baremo.interpretacion` sí reutiliza casi literal una "redacción sugerida para un informe" que trae su propia ficha técnica, lista para una carga de contenido futura) — eso sigue siendo, como dice la sección "Informes" más abajo, trabajo pendiente explícito, no un descuido. Tampoco tienen tests dedicados (ni unitarios ni e2e) más allá de la verificación manual contra la base de datos real hecha al cargarlas — mismo criterio que ya se aplicaba a `seed_prueba_aptitud_tecnica.py` antes de tener su propio par de tests. **Nota de inconsistencia conocida**: `tests/verificar_documentos_casos_reales_e2e.py` (prefijo `ZZDOCEJ`) incluye una aserción que confirma "PHQ-9 sigue siendo el único instrumento con catálogo+baremos cargados, sin CARAS/FES/otra prueba comercial referenciada" — esa aserción específica ya no es cierta desde la sesión que cargó GAD-7/CHASIDE/APGAR-FAMILIAR/SCARED-C/RCADS-47, y ahora tampoco con IPIP-RIASEC/EAR/SDQ-CAS/CES-DC/BARSIT/VANDERBILT_PADRES/DASS-21/HAMILTON_AUTOINFORME sumados, y necesita actualizarse para reflejar los trece instrumentos nuevos (BARSIT, NICHQ Vanderbilt y HAMILTON_AUTOINFORME son los únicos de ellos con `visible_para_clientes=False` por licencia/autenticidad sin resolver — ver sus propios bullets arriba; DASS-21, en cambio, es el más permisivamente licenciado de todos — pero ninguno es CARAS/FES/otro comercial de terceros no mencionado hasta ahora, así que el espíritu de la aserción sigue cumpliéndose, pero el texto literal "único instrumento" no).

### Interpreting a result: `es_alerta` and `estado_interpretacion` are the only signals that matter

Two flags decide everything about whether a result is shown to the student or held for review — **never infer risk from the text of `nivel`**, which is free text a psychologist can spell however they want ("Alto", "Severo", "Sin indicadores aparentes" used as an *alert* label is a real test case in the suite):

- `Baremo.es_alerta` (bool) marks a tramo as requiring professional review. It's copied verbatim into `DiagnosticoAlumno.es_alerta` at the moment a result is interpreted — a snapshot, not a live reference, so editing a baremo later never rewrites the alert status of a diagnosis that already went out. `detectar_niveles_de_alerta()` and `obtener_casos_pendientes_de_seguimiento()` (the psychologist's follow-up worklist) both filter on this field. A leftover text-matching set, `models.NIVELES_DE_ALERTA`, still exists in `modulos/educativo/models.py` but only as a suggestion when authoring new baremos — it has no effect on any business logic; do not wire it back into a filter.
- `Inscripcion.estado_interpretacion` (`"completa"` / `"incompleta"`, constants `INTERPRETACION_COMPLETA`/`INTERPRETACION_INCOMPLETA` in `models.py`) records whether *every* dimension found an applicable baremo. Missing a baremo is not "no risk" — it's a configuration gap, and it forces `requiere_revision = True` exactly like an alert does, with the affected dimension names logged in `Inscripcion.dimensiones_sin_baremo` and passed to the alert email as a separate section from the actual risk hits.

**Fixed**: both `interpretar_resultados_alumno` and `interpretar_perfil_alumno` computed `interpretacion_completa` as `not dimensiones_sin_baremo` / an unconditional `True` — correct when at least one `ResultadoDimension` exists, but vacuously (and wrongly) `True` when there are zero, since an empty list has no "missing" entries to report. `POST /educativo/examen/{token}/finalizar` never required at least one `RespuestaAlumno` before finalizing, so a token could be finalized with nothing answered: `calcular_resultados_dimensiones` produces zero `ResultadoDimension` rows, both interpretation functions returned `interpretacion_completa=True` on that empty set, `requiere_revision` came out `False`, and the enrolment was released to the student (`resultado_visible_alumno`/`informe_liberado` both `True`) as a clean, no-risk result instead of being retained — the same class of bug `estado_interpretacion`/`dimensiones_sin_baremo` exists to prevent, just reached through an empty collection instead of a missing baremo. Both functions now return `interpretacion_completa = bool(puntajes_directos) and ...` (gated on having at least one `ResultadoDimension` to begin with), which flows through the same `requiere_revision`/retention machinery as any other incomplete interpretation — no new state, no new gate, just closing the vacuous-truth gap in the existing one. `interpretar_perfil_alumno`'s own docstring already claimed this behavior ("interpretacion_completa es True mientras haya al menos un ResultadoDimension") before the code actually did it — two existing unit tests had encoded the old, wrong behavior as expected (`test_interpretacion_perfil_unitario.py`'s "sin resultados" case, `test_modo_interpretacion_unitario.py`'s source-substring check) and were updated alongside the fix. Still open: finalizing with zero answers is retained correctly now, but nothing stops the call from succeeding in the first place — adding an explicit "at least one answer" check to `finalizar_examen_seguro` would catch it earlier, with a clearer error, instead of relying on this fallback.

### Interpretation rules: `ReglaInterpretacion` — a second, independent way to force alert

Beyond `Baremo.es_alerta`, a `ReglaInterpretacion` row (`modulos/educativo/models.py`) can force `es_alerta = True` on a specific dimension's diagnosis even when the baremo tramo reached does not call for one — the canonical case is PHQ-9 item 9 (suicidal ideation): a low total score is normally not an alert tramo, but *any* positive answer to that one item must still trigger review. A rule has `ambito` (`item` | `dimension` | `puntaje_total`, CHECK-constrained; `pregunta_id`/`dimension_id` required depending on which), `operador` (one of `>`,`>=`,`<`,`<=`,`==`,`!=`, evaluated via a fixed `operator`-module dict in `crud._OPERADORES_REGLA` — never `eval()`), `valor_comparacion`, and `accion` (only `"es_alerta"` exists; kept as a string column so a second action doesn't need a migration). Rules belong to a `prueba_id` and creating/editing one goes through the same `verificar_propiedad_de_prueba` ownership check as baremos/preguntas — a private test's rules are as tenant-isolated as everything else about it; a public-catalog test's rules (e.g. PHQ-9's) are readable by any institution but writable only by superadmin, same convention as the catalog itself.

`crud.evaluar_reglas_interpretacion()` is generic — it never references a test by name, only by the `ambito`/`pregunta_id`/`dimension_id`/`operador`/`valor_comparacion` columns of the row — and runs inside `finalizar_examen_seguro`, right after `crud.interpretar_segun_modo()` (which dispatches to `interpretar_resultados_alumno()` for `'rango'` or `interpretar_perfil_alumno()` for `'perfil'` — see "Interpretación por perfil" below), before the single `db.commit()`. `crud.aplicar_reglas_a_diagnosticos()` then merges what it found onto the already-built `DiagnosticoAlumno` rows: a rule can only turn `es_alerta` **on**, never off, even where the baremo tramo reached was not an alert one. `DiagnosticoAlumno.alerta_por` (`"baremo"` | `"regla"` | `"baremo,regla"`) plus `regla_activada_id` record which mechanism(s) actually fired, so a professional reviewing a retained case can see why. If a rule references something this specific application never produced (an item the student never answered, or a pregunta/dimension that doesn't actually belong to the rule's own `prueba_id`), that's a configuration gap, never silently read as "no risk" — `Inscripcion.reglas_con_error` records it (parallel to, and independent from, `dimensiones_sin_baremo`) and forces `requiere_revision = True` regardless of what the baremo said.

PHQ-9's own item-9 rule is loaded as data by `seed_phq9.py` (`ambito="item"` on the item-9 `Pregunta`, `operador=">"`, `valor_comparacion=0`) — nothing in `core/algoritmo.py` or the rules engine itself knows PHQ-9 exists. Re-running `seed_phq9.py` against a database that already has PHQ-9 finds it and adds only what's missing (the rule, and separately the informe content described below) — idempotent and additive-only, never overwriting something a psychologist edited by hand.

### Interpretación por perfil: `crud.interpretar_perfil_alumno`

Closes engine limit #3 for real (see "Catálogo de pruebas cargadas" above — the PDF-readability half of that problem was already closed separately by "Diseño A", see "Informe PDF — ordenar dimensiones por puntaje" below; this is the other half, the actual interpretation). `Prueba.modo_interpretacion` had reserved the value `'perfil'` since before any test needed it, deliberately undeclared in the CHECK constraint and in schemas' validator so nothing could use it silently as `'rango'` — IPIP-RIASEC is the first real instrument that needs it, and `crud.interpretar_perfil_alumno()` is the algorithm.

Where `interpretar_resultados_alumno()` (the `'rango'` algorithm, untouched by this feature) reads each dimension against its own absolute `Baremo` range, `interpretar_perfil_alumno()` **never consults `Baremo` at all** — it ranks the dimensions of *this one inscripción* against each other by `ResultadoDimension.puntaje_directo` (descending) and writes that rank straight onto `DiagnosticoAlumno.nivel` (`"1º de 6"`, `"2º de 6"`...) with an automatically-generated `interpretacion` sentence describing the rank and raw score — never invented clinical text, just a description of the computed position. `es_alerta` is **always `False`** in this mode by design (a relative rank never implies risk on its own); `baremo_id` stays `NULL` (there's no tramo to point to). Because it never depends on a configured `Baremo` tramo existing, `'perfil'` mode never produces `dimensiones_sin_baremo` — `interpretacion_completa` is always `True` whenever there's at least one `ResultadoDimension` to rank. `ReglaInterpretacion` still runs afterward exactly as it does for `'rango'` mode (nothing about the rules engine changed) — if a future profile-style test ever needed an item-level safety rule, that's still the mechanism, never a special case inside this function.

`crud.interpretar_segun_modo(db, inscripcion_id, prueba_id)` is the **single** place that reads `Prueba.modo_interpretacion` and decides which of the two algorithms to run — both `finalizar_examen_seguro` and `reprocesar_informe_de_inscripcion` call this instead of `interpretar_resultados_alumno()` directly now, so the two call sites can never disagree about which mode a prueba uses or drift out of sync with each other. A missing/`NULL` modo falls back to `'rango'`, the behavior every test had before this feature existed. `modo_interpretacion` is **deliberately not exposed on `PruebaUpdate`/PATCH** — changing a test's interpretation algorithm is a structural decision, not a configuration tweak, so it can only be set at creation (`PruebaCreate`) or changed by hand on an existing row via a seed script (same `_asegurar_*` idempotent pattern as every other one-time data migration in these scripts) — never by an accidental PATCH call against the wrong test.

`seed_riasec.py` sets `modo_interpretacion=models.MODO_INTERPRETACION_PERFIL` at creation and, via `_asegurar_modo_perfil()`, switches an already-loaded row over on a re-run — which also cleans up the "banda descriptiva" `Baremo` rows an earlier version of this script had loaded as a workaround before this algorithm existed (deleting only tramos with zero `DiagnosticoAlumno` pointing to them, same safety check `crud.eliminar_baremo` already uses elsewhere; any tramo actually in historical use is left intact and only reported, never silently dropped). IPIP-RIASEC is the only one of the seven loaded instruments using `'perfil'` — everything else stays on `'rango'`, unaffected.

Verified against a real generated PDF and the real DB (same `pypdf` technique as the PDF tests): a student scoring Social=40 > Artístico=32 > Investigativo=24 > the rest=8 produced `DiagnosticoAlumno` rows reading exactly "1º de 6"/"2º de 6"/"3º de 6"... in score order, all `es_alerta=False`, all `baremo_id=NULL`, `estado_interpretacion='completa'`, the informe never retained, and the PDF showing both "Código de perfil: SAI" (from "Diseño A", computed independently) and "1º de 6" (the actual interpreted `nivel`, from this feature) — the two are separate computations that happen to agree, by construction, since both sort the same scores the same way. Tests: `test_interpretacion_perfil_unitario.py` (no DB — duck-typed fakes exercise `interpretar_perfil_alumno` and `interpretar_segun_modo`'s dispatch logic directly); `test_modo_interpretacion_unitario.py` was rewritten for the new reality (`'perfil'` now accepted, not rejected) alongside it. No dedicated e2e file — verified manually against the real DB/server, same criterion already used for the `seed_*.py` instrument loads. Migration: `2026_09_30_1100-3a1f4fcd127d_modo_interpretacion_perfil.py` (widens the CHECK constraint only; no existing `Prueba` row changes mode).

### Baremo trazabilidad y soft-delete

Editing or deleting a `Baremo` that had already interpreted a real student's result used to be unsafe: editing its range/nivel/es_alerta retroactively changed the meaning of a historical diagnosis — even though `DiagnosticoAlumno` already snapshots `nivel`/`es_alerta`/etc. at interpretation time, the *tramo it came from* had no pointer of its own — and deleting it outright orphaned that missing pointer. Two additions close this: `DiagnosticoAlumno.baremo_id` (FK to `edu_baremos.id`, `ondelete="SET NULL"`) records exactly which tramo produced each diagnosis, and `Baremo.activo` (Boolean, default `True`) replaces a physical `DELETE` with a soft-delete whenever `_baremo_tiene_diagnosticos()` finds the tramo already in use. `interpretar_resultados_alumno()` and the overlap-validation on baremo create/edit both filter on `activo == True`, so a deactivated tramo stops being reachable for new results — and stops blocking a replacement tramo over the same range — without breaking the historical pointer on old diagnoses. Editing the *definitional* fields (range, nivel, es_alerta) of a baremo already in use is blocked with 409; only the informational fields (`interpretacion`, `conclusion_sugerida`, `recomendacion_sugerida`) can still be edited after use — the intended fix for a wrong tramo is always deactivate-and-recreate, never mutate-in-place. `Baremo.actualizado_en` (nullable, `NULL` = never edited) tracks the last edit. A baremo with zero diagnósticos can still be hard-deleted exactly as before. Tests: `test_baremo_trazabilidad_unitario.py`/`verificar_baremo_trazabilidad_e2e.py`. Migration: `2026_09_23_1349-62ba95119cdf_baremo_trazabilidad_y_soft_delete.py`.

### Criterio normativo de Baremo: `Baremo.criterio_normativo` y `Prueba.criterio_normativo_activo`

Closes limit #2 documented above (GAD-7's classic vs. Peruvian cutoff; APGAR-FAMILIAR's two contradictory Peruvian cutoff tables) — a second, independent axis from `Baremo.activo` (which still means exclusively traceability/correction of a misconfigured tramo, and is never reused for this).

`Baremo.criterio_normativo` (String, nullable, default `NULL`) is a free-text label identifying an alternative interpretive lens for a dimension — `NULL` (every tramo loaded before this feature) means "the only criterion," zero behavior change. `_validar_solapamiento_baremo` now treats `criterio_normativo` as part of the "same scope" tuple (alongside sexo/edad/población), but unlike those — where `NULL` is a wildcard meaning "applies to anyone" — here equality is exact: two tramos only compete for the same puntaje range when their `criterio_normativo` values are equal (both `NULL`, or both the same label). Two tramos with *different* labels can freely overlap in puntaje range without tripping the 409 — they're alternative lenses, not a real duplicate. `actualizar_baremo`'s PATCH-merge fusion includes `criterio_normativo` so a partial edit still re-validates against the right scope; it is **not** in `CAMPOS_BAREMO_BLOQUEADOS_SI_EN_USO` (same precedent as `sexo`/`poblacion` — editable even after use).

`Prueba.criterio_normativo_activo` (String, nullable, default `NULL`) decides which label `interpretar_resultados_alumno()` actually matches against: the function now resolves the inscripción's `Prueba` and filters the `Baremo` query with `Baremo.criterio_normativo == criterio_normativo_activo` — when `NULL` (every prueba today, including PHQ-9/GAD-7/APGAR-FAMILIAR/etc. until someone opts in), this is exactly the implicit "criterio_normativo IS NULL" filter that already existed before this feature, so it's zero behavior change for every test loaded so far. Changing which criterion is active is a plain `PATCH /educativo/pruebas/{id}` with `{"criterio_normativo_activo": "<label>"}` — `schemas.PruebaUpdate` gained the field, no new endpoint. The mechanism that makes this actually useful: flip `criterio_normativo_activo` and then call `POST /educativo/inscripciones/{id}/reprocesar` on the inscripciones that should be reinterpreted under the new criterion — the exact same "correct a Baremo, then reprocess" pattern already documented above, applied to a different axis. `seed_gad7.py`/`seed_apgar_familiar.py`/`seed_rosenberg.py`/`seed_sdq.py` load both criteria for their respective tests (via idempotent, additive `_asegurar_criterio_peru()`/`_asegurar_criterio_sistema_b()`/`_asegurar_criterio_percentil_n1228()`/`_asegurar_criterio_cuatro_bandas()` helpers, same pattern as `seed_phq9.py._asegurar_contenido_informe` — they run even when the prueba already existed, and never touch a tramo already loaded), but leave `criterio_normativo_activo=NULL` — the classic/Sistema-A/sección-8/tres-bandas criterion stays active by default in each; an institution has to opt in explicitly.

Tests: `test_criterio_normativo_unitario.py` (no DB — model/schema checks, and `_validar_solapamiento_baremo` exercised directly with duck-typed fake rows) / `tests/verificar_criterio_normativo_e2e.py` (prefix `ZZCRIT` — a tramo on a second criterion overlapping the active one's range is accepted, a tramo on the same criterion still 409s, an inscripción interprets under the default `NULL` criterion, then a `PATCH` + `reprocesar` flips its diagnosis/alert/informe-release status to what the alternate criterion says, and the prior `InformeVersion` stays byte-identical). Migration: `2026_09_30_0900-87688455d771_criterio_normativo.py`.

### Dimensión compuesta: `Dimension.tipo_calculo` y `DimensionComponente`

Closes limit #1 documented above (SCARED's 0-82 total; RCADS-47's Total Ansiedad/Total Ansiedad+Depresión) — a `Dimension` that, instead of summing its own `Pregunta` rows, sums the already-computed `puntaje_directo` of other `Dimension` rows (its "componentes"), and from that point on behaves exactly like any other dimension: it gets its own `Baremo`, its own `DiagnosticoAlumno`, and can be the target of a `ReglaInterpretacion` — none of `interpretar_resultados_alumno`, `DiagnosticoAlumno`, the PDF, or the dashboards need to know this concept exists. Same discipline `Prueba.modo_calculo` already uses: a discriminator that changes *how* the puntaje is reached, never what's done with it afterward.

`Dimension.tipo_calculo` (String, NOT NULL, `server_default='items'`, CHECK-constrained to `models.TIPOS_CALCULO_DIMENSION_VALIDOS = {'items', 'suma_de_dimensiones'}`) — every dimension loaded before this feature stays `'items'`, zero behavior change. `DimensionComponente` (`edu_dimensiones_componentes`: `dimension_compuesta_id`, `dimension_componente_id`, `orden`) records which dimensions feed a composite one; `dimension_compuesta_id` has `ondelete="CASCADE"` (its composition rows are meaningless without their owner), `dimension_componente_id` deliberately does not (`crud.eliminar_dimension` blocks deleting a dimension that's in use as someone else's componente, rather than silently unraveling that composition). **Nesting is forbidden**: a componente can never itself be `tipo_calculo='suma_de_dimensiones'` — validated in `crud._validar_componentes_dimension_compuesta` (re-checking existence, same-prueba membership, and non-compositeness from the DB, never trusting the client's ids), which keeps the calculation a simple two-pass process with no cycle detection needed.

The engine change is additive and small: `crud.calcular_resultados_dimensiones` runs its normal `'items'` pass exactly as before, then a second pass queries this prueba's `tipo_calculo='suma_de_dimensiones'` dimensions and, for each, sums the `puntajes_brutos` already computed in pass one for its componentes (componentes are always `'items'`, by construction, so they're always already in that dict) into a real `ResultadoDimension` row — not a value used once and discarded. One correctness fix tied directly to this: `evaluar_reglas_interpretacion`'s `puntaje_total` ambito sums every `ResultadoDimension` of the prueba, which would double-count a composite dimension's value together with its own componentes the moment one exists in a prueba — the query now excludes `Dimension.tipo_calculo == 'suma_de_dimensiones'` from that sum.

A composite dimension can never have its own `Pregunta` — guarded in `crear_pregunta`, `actualizar_pregunta` (when `dimension_id` changes), and `cargar_test_masivo` (for a composite declared in the same carga-masiva batch). `crud.actualizar_dimension` blocks changing `tipo_calculo` once the dimension already has `ResultadoDimension` rows (409 — same "already produced a real result, now immutable" precedent as `Baremo`'s blocked fields), and separately blocks converting an `'items'` dimension that still has its own `Pregunta` rows into `'suma_de_dimensiones'` (400).

New endpoints, both `requerir_staff_clinico` + the same `verificar_propiedad_de_prueba` ownership check as every other pregunta/dimensión/baremo endpoint: `PUT /educativo/dimensiones/{dimension_id}/componentes` (full replace, not merge — same convention as `DocumentoInstitucionalSeccionContenido`) and `GET /educativo/dimensiones/{dimension_id}/componentes`. Both are in `tests/matriz_permisos_esperada.json` (`colegio: false`, same tier as the rest of the test-authoring surface).

**First real use, outside its own tests**: `seed_sdq.py` (SDQ-CAS — see "Catálogo de pruebas cargadas" above) builds its composite directly via the ORM (seed scripts never go through the API/`crud.reemplazar_componentes_de_dimension`, same as every other `seed_*.py`) — "Dificultades Totales" sums Síntomas Emocionales + Problemas de Conducta + Hiperactividad + Problemas con Compañeros, deliberately excluding Conducta Prosocial, exactly the mechanism this feature was built for. **Still not done**: SCARED's and RCADS-47's own total scores aren't loaded with this mechanism yet — that's a data-loading follow-up (create the `Dimension(tipo_calculo='suma_de_dimensiones')` row, `PUT .../componentes` with the existing sub-escalas, and a `Baremo` for the total) against each `seed_*.py`, not a motor change; the motor itself is ready and already proven against real data. Tests: `test_dimension_compuesta_unitario.py` (no DB — model/schema/constraint checks, `_validar_componentes_dimension_compuesta` exercised directly with duck-typed fake rows, and source-inspection checks that every guard is wired where it should be) / `tests/verificar_dimension_compuesta_e2e.py` (prefix `ZZDIMC` — a real 2-subescala prueba with a composite "Total," componentes set via the API, a finalized exam producing the composite's own `ResultadoDimension`/`DiagnosticoAlumno`/alert/informe-retention indistinguishably from any other dimension, a `puntaje_total` rule confirmed not to double-count, and the nesting/cross-prueba/convert-while-in-use guards). Migration: `2026_09_30_0930-a3be794d45e0_dimension_compuesta.py`.

### Conteo de síntomas: `Dimension.tipo_calculo='conteo_sintomas'` y `conteo_umbral_item`

Closes a fourth real engine limit, found (not designed ahead of time, same as every other `tipo_calculo`/`criterio_normativo`/`modo_interpretacion` addition) while loading NICHQ Vanderbilt — Escala de Evaluación para Padres (`seed_vanderbilt_padres.py`, see "Catálogo de pruebas cargadas" below): its official clinical criterion is not "sum the item values and compare against a range" (the only thing `Baremo` could express before this feature) but a **symptom count** — "6 of 9 Inatención items with a rating of 2 or 3." A sum cannot express this honestly: nine items all scored 2 gives a count of 9/9 (sum 18), while five items scored 3 and four scored 0 gives a count of only 5/9 (sum 15, *higher* than the first case despite not meeting the criterion) — the two scoring methods can disagree on which result is clinically positive. This extension was proposed to, and confirmed by, the user before being built — it's a real engine change, not a data load, and the decision to build it (rather than loading the instrument's items with no automatic interpretation) was explicitly made by the user, same as the decision to use `test.pdf`'s own 56-item numbering over a secondary scoring document's 55-item numbering (an edition mismatch the loading surfaced, documented in `seed_vanderbilt_padres.py`'s own docstring).

`Dimension.tipo_calculo='conteo_sintomas'` (third value alongside `'items'`/`'suma_de_dimensiones'`) is, like `'suma_de_dimensiones'`, a discriminator that changes *how* `puntaje_directo` is computed — unlike `'suma_de_dimensiones'`, a `'conteo_sintomas'` dimension DOES have its own real `Pregunta` rows (it isn't a derived aggregate), so none of the "no own preguntas" guards built for composite dimensions apply to it. `Dimension.conteo_umbral_item` (Integer, nullable — only meaningful for this `tipo_calculo`, enforced by a CHECK, `ck_dimensiones_conteo_umbral_requerido`) is the value a (possibly already-inverted) item must reach or exceed to count as "positive" — e.g. `2` on a 0-3 frequency scale, or `4` on a 1-5 functioning scale where 4-5 mean "problem." `core/algoritmo.py:calcular_likert_generico` takes an additional `dimensiones_conteo: dict[dimension_id, umbral]` parameter (built in `crud.calcular_resultados_dimensiones` from the prueba's own `Dimension` rows, empty for every prueba loaded before this feature — zero behavior change) and, for a dimension present in that dict, accumulates a count of qualifying items instead of a sum; absent from the dict, a dimension is summed exactly as it always was. Once computed, a `'conteo_sintomas'` dimension's `puntaje_directo` is just a number like any other — `Baremo`, `DiagnosticoAlumno`, and `ReglaInterpretacion` interpret it without knowing it's a count rather than a sum. `crud.evaluar_reglas_interpretacion`'s `puntaje_total` ambito excludes `'conteo_sintomas'` dimensions from its sum, same reasoning (and same code shape) as its existing `'suma_de_dimensiones'` exclusion — summing a count together with a different scale's raw score would produce a meaningless "total." `crud.actualizar_dimension` extends its existing tipo_calculo-change guard to also block changing `conteo_umbral_item` once a dimension has results (same "already produced a real result, now immutable" precedent as `Baremo`'s blocked fields), and validates the *resulting* state of a PATCH so a dimension can never end up `'conteo_sintomas'` with a NULL umbral (a clean 400 instead of a raw `IntegrityError` from the CHECK constraint).

**Deliberately NOT automated — a scoped decision, not an oversight**: Vanderbilt's full official criterion for each symptom area is "N of M symptoms, *plus* at least one Funcionamiento item scored 4 or 5 (functional impairment)" — a condition that crosses two independent dimensions with an AND. `ReglaInterpretacion` (ambito='dimension') only compares a dimension's *own* result against a fixed threshold; it has no mechanism to make one dimension's alert depend on another's result. Building that cross-dimension gate was explicitly scoped out of this session (the counting mechanism itself was already the blocking piece) — so each symptom dimension's `Baremo` marks `es_alerta=True` on its own "criterion met" tramo *without* requiring the Funcionamiento gate (the engine is therefore more sensitive than the full clinical criterion, never less — it never misses a case the real criterion would also flag), and `Baremo.interpretacion` on that tramo explicitly tells the reviewing professional to also check Funcionamiento. "TDAH combinado" (Inatención AND Hiperactividad both positive) is likewise left as direct reading of the already-flagged dimensions, not computed. Tests: `test_conteo_sintomas_unitario.py` (no DB — column/CHECK/schema checks, `calcular_likert_generico` exercised directly to confirm it counts rather than sums even when the sum would be larger, and source-inspection checks that every guard is wired where it should be). No dedicated e2e — verified manually against the real DB (`crud.calcular_resultados_dimensiones` → `interpretar_resultados_alumno` → `evaluar_reglas_interpretacion`/`aplicar_reglas_a_diagnosticos`, inside a rolled-back transaction), same criterion already used for every `seed_*.py` instrument load. Migration: `2026_10_04_1000-e4ab309bbab8_conteo_sintomas.py`.

### Ciclo de vida de campaña y reproceso de informe

Two gaps this file used to list as "known, not yet built" are now implemented, both under `modulos/educativo`.

**Editar/cerrar/cancelar campaña** (`Evaluacion`): a new `estado` column (`'activa'`/`'cerrada'`/`'cancelada'`, CHECK-constrained, default `'activa'`) is the single source of truth for the lifecycle — `Evaluacion.activo` (the pre-existing boolean) is untouched and stays exactly as dead as it always was; nothing reads it. `PATCH /educativo/campanas/{id}` (`requerir_staff_clinico`, tenant re-checked against the DB row) only works while `estado == 'activa'`: `nombre_grupo`/`fecha_fin` are always editable in that state, but `prueba_id` locks (409) the moment a single `Inscripcion` exists for that campaign, roster or anonymous, answered or not — a magic link already issued assumes the original prueba's preguntas/baremos, and `guardar_respuestas_examen`'s authority chain would no longer match a swapped prueba. `POST .../cerrar` (motivo optional) and `POST .../cancelar` (motivo **required**) both move `estado` and, if `fecha_fin` isn't already in the past, force it to "now" — this is the whole mechanism: it reuses, unchanged, the exact `fecha_fin` expiration check that already gates all 7 points of the exam flow (guardar/finalizar/comenzar-test/progreso/preguntas/campos-socio ×2) plus `matricular_roster_en_campana`, so closing a campaign needed zero new gates anywhere in that flow. `cancelar` additionally requires zero `Inscripcion` rows with `estado == 'Finalizado'` (409 otherwise) — cancelling is for a campaign that never produced real results; one that already has finalized results can only be closed, not cancelled. A campaign that is `'cerrada'`/`'cancelada'` rejects every further edit or a second close/cancel with 409 — there is no reopen action. Tests: `test_campanas_ciclo_vida_unitario.py`/`verificar_campanas_ciclo_vida_e2e.py` (prefix `ZZCAMP`).

**Reprocesar informe tras corrección de baremo** (`POST /educativo/inscripciones/{id}/reprocesar`): unlike `.../informe/reemitir` (which only re-renders the PDF from whatever is already in `DiagnosticoAlumno`), this endpoint recalculates from the student's raw `RespuestaAlumno` rows against the **currently active** baremos/reglas — the real fix for "I corrected a misconfigured Baremo, now what?", since a `Baremo` already in use can't have its range/nivel/es_alerta edited in place (see above) and can only be deactivated-and-replaced. It replicates `finalizar_examen_seguro`'s transactional shape exactly: `crud.bloquear_inscripcion_para_reprocesar()` (`with_for_update().populate_existing()`, same reason as `bloquear_inscripcion_para_finalizar`), a single `db.commit()` around `limpiar_resultados_previos` → `calcular_resultados_dimensiones` → `interpretar_resultados_alumno` → `evaluar_reglas_interpretacion`/`aplicar_reglas_a_diagnosticos`, and the identical `requiere_revision` formula — which then recomputes `resultado_visible_alumno`/`informe_liberado` in **either direction**: a correction that newly reveals an alert re-retains an already-released informe (a professional must review it again), and one that removes a false alert releases it again automatically, with no need to call `liberar-informe` by hand. `estado` (stays `"Finalizado"`) and `fecha_resolucion` (the historical fact of when the exam was taken) are never touched; neither are the professional's own `revisado_por_usuario_id`/`interpretacion_clinica` notes. After the commit, `crud.generar_y_almacenar_informe(..., origen="reproceso")` creates `version_actual + 1` exactly like a reissue — never touching any earlier `InformeVersion` — and, if the recomputed result requires review, the same background alert email fires as on `finalizar_examen_seguro`. **Restricted to `requerir_rol("superadmin", "admin")` — deliberately excludes `psicologo`**, unlike every other clinical action in this module (`reemitir`, `liberar-informe`, `revision-informe`): reprocessing after a baremo fix is treated as an administrative action on the engine's configuration, not a case-by-case clinical judgment.

A new `InformeVersion.origen` column (`'automatica'`/`'reemision'`/`'reproceso'`, CHECK-constrained, backfilled from the pre-existing `generado_por_usuario_id IS NULL` convention) makes this explicit instead of leaving a reader to infer it by diffing `resultados_snapshot` between versions — `generar_y_almacenar_informe()` takes `origen` as a parameter (default `"automatica"`, so the background-task call site needed no change) and the automatic call, `reemitir_informe`, and this new endpoint each pass their own value. `GET /inscripciones/{id}/informe`'s version list now includes `origen` alongside `motivo_version`.

**Known operational risk, not fixed by this mechanism**: `reprocesar` re-retaining an already-released informe (`resultado_visible_alumno`/`informe_liberado` flipping back to `False`) only ever affects *future* access — it cannot recall a PDF the student already downloaded while the prior version was released. If a professional liberated an informe, the student downloaded it, and a later baremo correction reveals it should have been an alert, the student is left holding a copy of a report the system now treats as retained; there is no way to invalidate a file already in someone's hands. Separately, nothing in `reprocesar` notifies the psychologist who originally reviewed/released the case that this happened — the only signal is the same background alert email `finalizar_examen_seguro` already sends when a result requires review, which reads exactly like a first-time alert and doesn't say "this was already seen and released once before." A professional relying on `casos-pendientes`/the alert inbox alone can miss that a specific case is a *regression*, not a new one, unless they separately check `InformeVersion.origen="reproceso"` or the version history. Both gaps are accepted as-is for now — no code change tracked here.

Tests: `test_reproceso_informe_unitario.py`/`verificar_reproceso_informe_e2e.py` (prefix `ZZREPR` — includes a Parte A mechanism test for the lock, mirroring `verificar_concurrencia_finalizar_e2e.py`, plus a full Parte B: correct a baremo from no-alert to alert and back, confirming the informe flips retained/released in both directions without a manual `liberar-informe`, and that every older `InformeVersion` stays byte-identical in storage). Migration: `2026_09_28_2141-847f59008bb9_ciclo_vida_campana_y_origen_informe_version.py`. Both new endpoint groups are in `tests/matriz_permisos_esperada.json`.

### Exam finalization is transactional

`POST /educativo/examen/{token}/finalizar` in [modulos/educativo/router.py](backend/modulos/educativo/router.py):

1. Locks the row (`with_for_update()`) and checks idempotency (`estado == "Finalizado"` → 400) before doing anything else.
2. Clears any previous partial results, recalculates, interprets, and sets `estado = "Finalizado"` together with visibility/interpretation fields — all inside the *same* transaction, with a **single `db.commit()`** at the end. Any exception during calculation rolls back everything, including the row lock and the "Finalizado" flip, so the student can simply retry. (Before: the state flip committed first, calculation ran after — a failure there left a permanently "Finalizado" row with no results, and the idempotency check then blocked every retry forever.)
3. If the result requires review, `resultado_visible_alumno` and `informe_liberado` are set false and the endpoint returns an empty list — **an at-risk (or unscoreable) student must never receive their own result before a professional releases it** (`PATCH /inscripciones/{id}/liberar-informe`). The student portal polls `/examen/{token}/estado-resultados`, which returns only status text, never scores. `GET /examen/{token}/progreso` similarly returns only which (pregunta, opción) pairs were already answered, never a score.
4. The alert email — to the campaign's creator, falling back through active admins of the institution and finally the institution's contact email, so a disabled account can't silence a critical case — goes through `BackgroundTasks`, after the commit, so the student is never blocked on SMTP. The student's name and every dimension name interpolated into that HTML email are escaped (`html.escape`) — both are free-text data an institution controls, not a fixed string.

**`PATCH /inscripciones/{id}/liberar-informe` only ever sets `informe_liberado = True`** — read directly from `liberar_informe()` in `modulos/educativo/router.py`, it never touches `resultado_visible_alumno`. This is deliberate, not an oversight: the sibling endpoint `PATCH /inscripciones/{id}/revision-informe` is the one documented (in its own docstring) as deciding "por separado la visibilidad del resultado y PDF," and an existing regression (`verificar_informe_phq9_e2e.py`, check "[13] Tras liberar, el alumno SÍ puede descargar su PDF") explicitly asserts that calling `liberar-informe` alone is sufficient for the student to download the PDF — because `GET /examen/{token}/informe-pdf` only checks `informe_liberado`, never `resultado_visible_alumno`. In practice this makes `resultado_visible_alumno` narrower than its name suggests: as of this writing it gates exactly two things, both purely cosmetic/one-shot for the student's own flow — the diagnósticos list returned synchronously in `POST /examen/{token}/finalizar`'s own response body (which a student can never re-fetch, since a second `/finalizar` call 400s on the idempotency check), and the status *message text* of `GET /examen/{token}/estado-resultados` (never real data either way). It is **not**, and was never, "one flag for the student-facing flow and one for institutional documents" — until the fix described under "Motor de documentos institucionales" → "`resultados_prueba` never renders a retained result", no code outside `modulos/educativo` read `resultado_visible_alumno` at all. That fix is the *first* other consumer, and it deliberately ORs both flags rather than trusting `informe_liberado` alone precisely *because* `liberar-informe` alone (a state the exam flow already treats as fully valid, tested, and sufficient for a PDF download) must not silently double as authorization for a `documentos` section to show the same raw score. If a future change gives `resultado_visible_alumno` a real, ongoing gate on the student's side (not just the one-shot response), revisit whether `liberar-informe` should flip it too, or whether `revision-informe` should stay the only path — don't assume today's narrow scope of `resultado_visible_alumno` is fixed forever, it was that narrow mostly by accident of what happened to get built, not by an explicit "this flag is retired" decision.

### Exam resumption

`POST /educativo/comenzar-test/{token}` handles four states for an existing enrolment, in this order: an unknown token is 404; a campaign past `fecha_fin`, or an enrolment that's been soft-deleted/anonymized, is 410 (Gone) everywhere in the exam flow — not just here, the same lock applies to loading questions, saving answers, checking progress, and finalizing; a `Finalizado` enrolment is 409; revoked consent is 403; unchecked terms is 400. An enrolment in `Pendiente` or `En Progreso` resumes normally — demographic fields (`nombre`, `edad`, `sexo`, `poblacion`) are only filled if still empty, never overwritten mid-exam.

### JWT credential versioning

`Usuario.token_version` (int, defaults to 0) is embedded in every login JWT as the `"tv"` claim. `obtener_usuario_actual` rejects a token whose `tv` doesn't match the user's current `token_version` — a token issued before this feature existed has no `tv` claim and is treated as `0`, so no one gets logged out by the upgrade itself. Changing a password (via `/auth/resetear-password` or `seed_superadmin.py`) increments `token_version`, which invalidates every JWT issued before that moment (previously a stolen token stayed valid for its full 7-day life even after the account holder changed their password) and marks every other pending password-recovery token for that user as used.

### SSRF protection on `Institucion.logo_url`

[core/url_segura.py](backend/core/url_segura.py) validates any URL before it's stored (`PATCH /instituciones/{id}`) and again before it's fetched (PDF generation): only `https`, only port 443, no userinfo in the URL, and — the part a plain scheme/port check misses — the hostname is resolved and **every** IP it returns must be public (`ipaddress.is_global`, with IPv4-mapped IPv6 addresses unwrapped first); the actual HTTP connection is then pinned to that already-validated IP (TLS SNI still targets the hostname), so a DNS record that changes between validation and fetch can't be used to reach an internal address. No redirects are followed, the response must be `image/*`, and it's capped at 2 MiB with a 5s timeout. `descargar_logo_seguro()` never raises — a bad or unreachable logo just means no logo on the PDF, not a broken report.

### Rate limiting on the public exam endpoints

[core/limiter.py](backend/core/limiter.py) — the shared `limiter` instance, imported from here, never a second `Limiter()`. Every public exam endpoint (comenzar, preguntas, progreso, guardar, finalizar, estado-resultados, informe-pdf, campos-socio) carries **two** stacked limits: a strict one keyed by the magic-link token (`clave_por_token`, via `@limiter.limit(..., key_func=clave_por_token)`), and a loose one keyed by client IP (`@limiter.shared_limit(..., scope=ambito_ip(nombre))`) — loose on purpose, because a whole classroom typically shares one NAT'd public IP. The per-IP limit **must** use `shared_limit` with a fixed scope string from `ambito_ip()`; slowapi's default scope is the URL path, which for these routes includes the token, so a plain `@limiter.limit` per-IP rule silently counts per (IP, token) instead of per IP and never fires against token enumeration. Auth endpoints keep their own limits (`5/minute` login/registration, `3/minute` password-recovery requests). Deploying behind a reverse proxy needs `uvicorn --proxy-headers --forwarded-allow-ips=...` or every student appears to share the proxy's IP; the counters live in each worker process's memory, so multiple workers each count independently.

### Migrations: a reproducible chain from an empty database

The chain now starts from `0a1b2c3d4e5f` (`down_revision=None`), which builds the schema as it stood before Alembic was introduced — including tables the very next migration drops. A completely empty PostgreSQL database reaches `head` with a plain `alembic upgrade head`, and `alembic check` reports no drift against the models; `tests/comparar_esquemas.py` goes further and confirms a from-scratch install is column-for-column, FK-name-for-FK-name, index-for-index identical to a real migrated database. An existing, already-migrated database is unaffected — it's already past `0a1b2c3d4e5f`'s revision point and never runs it. The one thing that does **not** go through this chain is a database created by `crear_tablas.py`/`create_all()`: stamp it (`alembic stamp head`), don't upgrade it.

### Student core: `Persona` + academic structure

`Persona` is still the one identity table (`modulos/superadmin/models.py`) — there is no separate `Estudiante` entity, and `tipo_perfil` is what distinguishes a student from any other population (patient, candidate...) the same row shape can represent later. What's new is a genuine academic structure hanging off it, instead of the old free-text `Persona.grado_seccion` (kept, but no longer authoritative for students):

- `NivelEducativo` → `Grado` → `Seccion`, all scoped to an institution (`institucion_id` denormalized on all three, same defense-in-depth already used by `CitaProgramada`/`RegistroAuditoriaArco`). `NivelEducativo` and `Grado` are stable catalogs reused every year; `Seccion` is **anchored to `anio_escolar`** — "3° B" of 2025 and "3° B" of 2026 are deliberately two different rows, because the actual group of students changes every year even when the label doesn't. This is what makes "Institución → Grado → Sección → Estudiantes" an unambiguous query for a given year, and what gives the per-year history for free.
- `MatriculaAcademica` links a `Persona` to a `Seccion` for a span of time (`fecha_inicio`/`fecha_fin`, `fecha_fin IS NULL` = current). Moving a student never updates a row — it closes the open one and inserts a new one — so the full academic history is `ORDER BY fecha_inicio`, and a partial unique index (`uq_matricula_activa_por_persona`, `WHERE fecha_fin IS NULL`) makes "at most one active enrolment per student" a database guarantee, not an application-level hope. `crud.matricular_persona_en_seccion` is the only path that's supposed to write this table — it re-validates that the target `Seccion`'s institution matches the student's, from the DB, never from what the request claims, and rejects a `Persona` whose `tipo_perfil` isn't `"estudiante"` (400) — the academic structure is conceptually for students only.
- `Persona.codigo_institucional` (unique per institution, like `documento_identidad`) is the functional identifier meant for Excel import, search, and bulk association later — **never use `documento_identidad` for that**; a school may not track it for every student, and it isn't guaranteed unique in the way a school's own roster code is.
- `Inscripcion.seccion_id` + `Inscripcion.grado_seccion_historico` are a snapshot, following the exact same pattern as `nombre_completo`/`edad`/`sexo`/`poblacion` on that same table: `matricular_roster_en_campana` copies the student's *currently active* section onto the enrolment at the moment it's created, and it is never touched again — moving the student to a new section afterward does not retroactively change a past evaluation's recorded section. If a student has no active `MatriculaAcademica` yet, both stay NULL; nothing breaks, the enrolment just carries no section data.
- Enrolling a roster-linked student (`matricular_roster_en_campana`) also derives `Inscripcion.poblacion` from the student's current `NivelEducativo.nombre` when it case-insensitively matches one of the values the scoring engine understands (`Primaria`/`Secundaria`/`Universitario`) — one less thing the exam form has to ask a student who's already in the system for. `nombre_completo`/`edad`/`sexo` were already being derived this way before this change; `POST /educativo/comenzar-test/{token}` still accepts (and, for an unnamed/anonymous link, still needs) those fields in its body, but for an already-known student they're silently ignored in favor of what's on file — see "only fills what's still empty" in exam resumption, above. The exam's request contract and the frontend's exam UI are deliberately untouched by this — that's future, visual work. **Fixed**: `Persona.genero` is unconstrained free text (a school might enter "M", "Hombre", "masculino"...), but `Baremo.sexo` and `RegistroAlumnoDemograficos.sexo` (the other intake path, for an anonymous exam) only ever use the exact literals `"Masculino"`/`"Femenino"`, and `interpretar_resultados_alumno` matches by exact string equality — so a roster-matriculated student's sex-specific baremo tramo could silently never match, forcing "sin baremo aplicable" even when a matching tramo existed. `matricular_roster_en_campana` now runs `persona.genero` through `_normalizar_sexo_para_baremo()` before copying it onto `Inscripcion.sexo` — a small alias table (`"m"`/`"h"`/`"hombre"`/`"masculino"` → `"Masculino"`, and the `"Femenino"` equivalents) that only *recognizes more input*, never discards a value it doesn't recognize (an unmapped value passes through unchanged, same behavior as before).

`PersonaDatosFamiliares` (composición del hogar: `numero_hermanos`, `vive_con`, `lugar_nacimiento`, `lugar_procedencia` — two separate columns, not one combined field, because a real informe distinguishes "born in X" from "comes from Y") and `PersonaAntecedentesClinicos` (external treatment/diagnosis: `recibe_terapia_psicologica_externa`/`recibe_atencion_psiquiatrica_externa` booleans + free-text detail each, `diagnostico_reportado`) are two more 1:1-with-`Persona` blocks on the student ficha, both mutable with no version history of their own (same treatment as `Persona.nombres`/`genero`), both nullable-by-default (`None` means "not asked yet", never coerced to `False`/empty). `GET/PATCH /personas/{id}/datos-familiares` and `GET/PATCH /personas/{id}/antecedentes-clinicos` upsert them (a GET before any write returns the empty shape, never 404); read is open to any authenticated role of the same institución including `colegio`, write is `superadmin`/`admin`/`psicologo` only — same convention as `ContactoFamiliar`. Filled once, reused by any individual `DocumentoInstitucional` (see below) instead of being re-captured per document — and explicitly **not** touched by Excel import.

`GET /admin/personas/{id}/ficha-completa` now also returns `informacion_academica_actual` (resolved labels for the active `Seccion`/`Grado`/`NivelEducativo`, or `null`) and `historial_academico` (every `MatriculaAcademica`, oldest first) alongside the existing consent/evaluation/session data. New endpoints: `POST/GET /admin/personas/academico/{niveles,grados,secciones}` (creation is `requerir_rol("superadmin","admin")`; `Grado`'s and `Seccion`'s `institucion_id` is derived from their parent row, never accepted as a field, so there's no `institucion_id` to spoof there — `NivelEducativo`, having no parent to derive from, does take `institucion_id` directly as a request field, but it's re-validated against the caller's own institución for every non-superadmin role, same defense-in-depth as everywhere else), `POST /admin/personas/{id}/matricula` (assign/move), `GET /admin/personas/{id}/historial-academico`, and `GET /admin/personas/por-codigo/{codigo}?institucion_id=` (the búsqueda from point 5 — superadmin must pass `institucion_id`, everyone else is forced to their own, same convention as `GET /auth/usuarios/`). All of these live on the existing `/personas` router with paths of two or more segments on purpose: `GET /personas/{institucion_id}` and `PATCH /personas/{persona_id}` are single dynamic segments already registered on that router, and a new single-segment literal route declared after them would silently never be reached (Starlette matches by segment shape + method, first registration wins) — `tests/test_nucleo_estudiante_unitario.py` asserts every new route has 2+ segments so this can't regress unnoticed.

### Promoción anual de estudiantes: `ProcesoPromocion`

Closing a school year and moving students up a grade is now a first-class, auditable operation instead of a manual re-matriculation per student. `Institucion.anio_escolar_activo` is a separate, explicit switch (never flipped automatically by confirming a promotion) that says which year's `Seccion`s are "current" for that institution. A `ProcesoPromocion` (`borrador`/`confirmado`/`cancelado`, unique per institución+año_origen+año_destino once confirmed) is the header of one promotion run; `ProcesoPromocionDetalle` is one row per student with the algorithm's proposed destination `Seccion` — resolved via `resolver_grado_siguiente()`/`resolver_seccion_destino()` from each `Grado.orden` — or an `advertencia_mapeo` (added in a follow-up migration) when the algorithm can't resolve it with confidence (an `orden` tie between grados in the same nivel, or no matching destination `Seccion` for the target year) and needs a manual override before confirming. `Persona.condicion_matricula` records `retirado`/`trasladado`/`egresado` once a promotion closes a student's path instead of moving them forward. Nothing is ever auto-created — an unresolvable mapping is always a row that needs a human decision, never a guess. Tests: `test_promocion_unitario.py`/`verificar_promocion_e2e.py` — the unit test also documents and guards a real bug found during development: the original ambiguity check compared `orden` against *every* grado in the nivel instead of only the ones actually competing to be "next" for the row being resolved, which wrongly blocked unrelated, unambiguous automatic mappings. Migrations: `2026_09_26_1000-716c022d49bb_promocion_anual_estudiantes.py`, `2026_09_26_1400-a3f8c1e07d92_advertencia_mapeo_promocion.py`.

### Two independent consents: apoderado and estudiante

`ConsentimientoInformado` (`modulos/superadmin/models.py`) holds **both** consent tracks in one table, discriminated by `tipo_consentimiento` (`"apoderado"` | `"estudiante"`, `models.TIPOS_CONSENTIMIENTO_VALIDOS`) — not two tables, because everything except a handful of "who granted it" columns (vigencia, revocation, audit trail, history) is identical between them, and duplicating the table would have duplicated that logic too. Registering one **never** creates or touches the other; they're tracked, queried, revoked and renewed completely independently, and every function that touches this table (`tiene_consentimiento_vigente`, `obtener_consentimiento_vigente`, `registrar_consentimiento`, `revocar_consentimiento_de_persona`, `historial_consentimientos`) takes an explicit `tipo_consentimiento`. `tiene_consentimiento_vigente`/`obtener_consentimiento_vigente`/`registrar_consentimiento`/`revocar_consentimiento_de_persona` default to `"apoderado"`, on purpose: every call site that predates the student-consent track (the roster-matriculation gate, the live-exam gate) calls these functions without passing it, and must keep behaving exactly as it did before — the student consent is additive, it never silently starts gating anything that didn't require it before. `historial_consentimientos` is the one exception, and deliberately not the same default: it defaults to `tipo_consentimiento=None`, which means "both tracks combined" — the natural default for a function whose whole job is showing history, not gating access. No call site currently relies on that default (every caller passes the argument explicitly), so this isn't a behavior risk, just a different — and correct — default for a different kind of function.

- **Vigencia** is `estado` (`"vigente"` | `"revocado"`, `models.ESTADOS_CONSENTIMIENTO_VALIDOS`, both columns backed by a Postgres `CHECK` — new columns, so unlike the legacy free-text status columns elsewhere in this codebase there was no existing bad data to work around, and the constraint could go on from day one). The boolean `revocado` column from before this feature still exists and is kept in sync on every write (Fase 2/B-8's crud and regression tests read it directly) — `estado` is the field new code should read.
- **At most one *vigente* consent per (persona, institución, tipo)** is a database guarantee, not just application logic: `uq_consentimiento_vigente_por_persona_y_tipo` is a partial unique index (`WHERE estado = 'vigente'`), the same technique `MatriculaAcademica` already uses. A vigente apoderado consent and a vigente estudiante consent for the same student coexist without conflict — the index is scoped by `tipo_consentimiento`, so the two tracks never compete for the same "only one" slot.
- **Revocation never deletes or edits history** — it flips `estado`/`revocado` (+ `fecha_revocacion`, `revocado_por_usuario_id`, `ip_revocacion`) on the *same* row. **Renewal** is registering a brand-new row once the old one is revoked (the partial index is what makes this required: you cannot create a second vigente row while one already exists) — the old row stays exactly as it was, permanently queryable via `historial_consentimientos`/`GET /personas/{id}/consentimientos`.
- **Columns that only make sense for `"apoderado"`** (`otorgado_por_nombre`, `otorgante_apellidos`, `otorgante_documento`, `otorgante_relacion`, `tipo_otorgante`) are nullable and simply left `NULL` on `"estudiante"` rows — the student is their own otorgante, there's nothing to fill. `evidencia_ruta` is an unused placeholder column (point 13 of that phase) for a future file's path/URL/key, kept deliberately separate from `referencia_documento` (a free-text human note, e.g. "folio 45") — there is no file storage built yet.
- **What consent gates an exam is now an institutional policy, apoderado-only by default**: `Institucion.exigir_consentimiento_estudiante` (Boolean, `server_default`/`default` `False` — no existing institución changes behavior) is read by both `matricular_roster_en_campana` (loaded once per call, before the per-student loop, never per-student — avoids an N+1) and `consentimiento_vigente_para_inscripcion`. A vigente **apoderado** consent is still required unconditionally, exactly as before; when the flag is on, a vigente **estudiante** consent is *additionally* required — its absence rejects the roster row with `"Sin consentimiento del propio estudiante vigente."`, and its live revocation blocks `comenzar-test` (403) on resume exactly like an apoderado revocation always has, independent of `Inscripcion.consentimiento_estudiante_id`'s enrolment-time snapshot. `PATCH /instituciones/{id}/politica-consentimientos` (body `{"exigir_consentimiento_estudiante": bool}`) is the dedicated endpoint to flip it — `requerir_rol("superadmin", "admin")`, admin restricted to their own institución, same convention as `PATCH /instituciones/{id}/anio-escolar-activo` (deliberately not folded into the general `PATCH /instituciones/{id}`, which stays superadmin-only for licence/plan). Anonymous links (`persona_id IS NULL`) stay exempt regardless of the flag — `consentimiento_vigente_para_inscripcion` still returns `True` immediately for them before the flag is ever read. Tests: `test_politica_consentimiento_estudiante_unitario.py`/`verificar_politica_consentimiento_estudiante_e2e.py`. Migration: `2026_09_28_2013-34d35dc8d70e_politica_consentimiento_estudiante.py`.
- **Every enrolment snapshots which consent(s) backed it**: `matricular_roster_en_campana` looks up the persona's currently-vigente consent row(s) (`obtener_consentimiento_vigente`, not just the boolean) and stores their ids on `Inscripcion.consentimiento_apoderado_id`/`.consentimiento_estudiante_id` (both nullable — NULL if that type had no vigente consent, or for an anonymous/no-`persona_id` enrolment). Because a consent row is only ever mutated by revocation (never edited or deleted), that FK alone is a permanent, immutable pointer to "exactly what was vigente when this application happened" — no separate text snapshot needed, unlike `grado_seccion_historico` (which exists because `Seccion` labels are freer to reinterpret). A later revocation changes what that same row *currently* says (`estado='revocado'`), but never detaches it from the enrolment, and never touches the enrolment's own state, results, diagnoses, or informe — finalización is a one-time event with no consent re-check afterward.
- `GET /personas/{id}/consentimientos` (new, plural) returns both tracks combined (`{"apoderado": {...}, "estudiante": {...}}`, each with `tiene_consentimiento_vigente` + full `historial`); `obtener_ficha_completa` embeds the same structure under `"consentimientos"`. The older `GET /personas/{id}/consentimiento` (singular) is untouched and still apoderado-only, for backward compatibility with Fase 2's regression suite and any existing frontend integration — don't extend its response shape to include the student track; use the plural endpoint for that.
- **A snapshot is fixed at enrolment time, not re-synced on resume**: `validar_y_comenzar_evaluacion` (`comenzar-test`) re-checks *live* apoderado vigencia every time a student opens/resumes an exam (`consentimiento_vigente_para_inscripcion`), independent of what `Inscripcion.consentimiento_apoderado_id` recorded at enrolment. A consent revoked after enrolment but before the student starts blocks `comenzar-test` (403) without touching the enrolment's snapshot or state; a later renewal un-blocks the *same still-`Pendiente`* enrolment, but the snapshot keeps pointing at the original (now-revoked) row — it is never rewritten to the renewed one. The live check is what gates access; the snapshot is what a future informe reads to say which consent applied.

### Excel import: bulk-onboarding students

`modulos/superadmin/importacion_estudiantes.py` (router endpoints on the same `/personas` router: `GET importar/plantilla`, `POST importar/validar`, `POST importar/confirmar`) produces exactly what a correct manual alta would: it calls the same `crud.buscar_persona_por_codigo` / `crud.matricular_persona_en_seccion` the rest of the codebase uses, and writes nothing but `Persona` + `MatriculaAcademica` rows — **no migration was needed for this phase**, every table it touches already existed. `codigo_institucional` (never the DNI, never the internal id) is the match key, scoped by `institucion_id + codigo_institucional`: a row whose code already exists in that institution updates that `Persona` (name/document/birthdate/gender +, if the row resolves a different section, a new `MatriculaAcademica` via the normal close-old-open-new mechanism); a new code creates one. A code that resolves to an existing `Persona` with `tipo_perfil != "estudiante"` is rejected as a row error, not silently repurposed.

**Who may pass `institucion_id`, and to whom the three endpoints are open at all**: all three (`GET importar/plantilla`, `POST importar/validar`, `POST importar/confirmar`) are gated by `requerir_rol("superadmin", "admin", "psicologo")` — `colegio` cannot reach any of them, full stop (403 before the request body is even read). `_institucion_para_importacion()` then resolves the actual `institucion_id` used: `superadmin` must pass `?institucion_id=` explicitly (400 if omitted); `admin`/`psicologo` are **always** forced to their own token's institución — any `institucion_id` sent in the request is silently ignored, never a 403, exactly the same convention as `GET /auth/usuarios/`. This means a non-superadmin can send any value (or none) and the import still only ever reads/writes their own institución — proven in `verificar_importacion_estudiantes_e2e.py` (a cross-institution attempt gets 200 and creates the row under the caller's *own* institución, never the one requested) and in `verificar_flujo_completo_e2e.py` (a `codigo_institucional` that already exists as a `Persona` in institución A resolves as `"nuevo"`, not `"actualizado"`, when B requests A's id — proof A's data was never actually consulted). Tests: `test_aislamiento_importacion_unitario.py`.

- **Only three endpoints, and validation never writes.** `/validar` parses+resolves the file against the current DB and returns the full per-row plan (action, resolved names/ids, errors) without touching anything — call it as many times as needed while fixing the file. `/confirmar` takes the *same* file again and **re-derives everything from scratch** (parses, re-resolves nivel/grado/sección, re-checks every constraint) rather than trusting anything echoed back from a prior `/validar` response, then applies every `nuevo`/`actualizado` row inside one transaction — an unexpected failure (e.g. two new rows sharing a `documento_identidad`, which passes single-row checks against the DB but collides with each other at flush time) rolls back the *entire* batch, not just the offending row. `duplicado` (same `codigo_institucional` twice in one file) and `error` rows are simply never part of the write set — they're not a "failed" part of the atomic operation, they were never attempted.
  **Fixed**: that all-or-nothing promise used to be false for any row carrying a `seccion_id`. `aplicar_importacion` calls the same `crud.matricular_persona_en_seccion()` the manual single-row endpoint uses, and that function used to end with its own `db.commit()` — which flushed to disk not just that row's matrícula but also any earlier row in the same batch that had only been `db.flush()`-ed, so a failure later in the batch could no longer be rolled back for rows already committed this way. `matricular_persona_en_seccion` now takes a `commit: bool = True` parameter (default preserves the manual endpoint's exact prior behavior); `aplicar_importacion` calls it with `commit=False` so its own outer `db.commit()`/`db.rollback()` is the only thing that ever decides the batch's fate.
- **`Seccion`'s year-anchoring (see student-core section above) means the template needs an `anio_escolar` column** the phase's own minimum column list didn't mention — without it there's no way to know which year's "3° B" a row means. Nothing is ever auto-created: an unresolvable nivel/grado/sección/año is always a row error, including the specific case of a real section that exists for a *different* year than requested (distinct message from "doesn't exist at all") — no implicit promotion logic exists or is inferred.
- **Consent is completely untouched by import** (`grep -L consentimiento` on this file would find nothing that writes one) — a newly-imported student has zero consent rows and is exactly as unauthorized for an evaluation as one created by hand with none; re-importing/updating an existing student never creates a duplicate or touches their existing consent history either.
- File handling: `.xlsx` only (via the already-a-dependency `openpyxl`, no new dependency), capped at 5 MiB / 2000 data rows, loaded with `data_only=True` so a formula cell yields its last cached value and is never evaluated as an expression, every cell coerced to plain text and control-character-stripped before it's compared against anything — the file is processed entirely in memory and never written to disk, so there's no path-traversal surface either. Header matching is by name (case/whitespace-insensitive), not column position.

### Auditoría de cambios a Persona: `RegistroCambiosPersona`

`actualizar_persona` writes an append-only audit row to `registro_cambios_persona` for every one of four identity fields that actually changes value (`nombres`, `apellidos`, `fecha_nacimiento`, `documento_identidad` — `crud.CAMPOS_AUDITADOS_PERSONA`) — one row per changed field, never one per request, each carrying the old value, the new value, and who made the change plus their role at that moment (a snapshot, same convention as everywhere else in this codebase). `campo` is a free-text column on purpose, so auditing a fifth field later doesn't need a migration. What counts as "actually changed" (`_valor_comparable`/`_texto_para_auditoria`) is deliberately picky — see the test for the exact rules a naive string comparison would get wrong. **Fixed**: `_valor_comparable` didn't strip whitespace, so re-saving `documento_identidad="12345678 "` against a stored `"12345678"` logged a real audit row (and, with `referencia_solicitud_arco` present, a real `auditoria_arco` row) for a purely cosmetic edit; it now `.strip()`s string values before comparing — deliberately *not* case-folding, since correcting "juan" to "Juan" is a real change that should stay audited. `GET /admin/personas/{persona_id}/historial-cambios` returns the trail. Editing these fields never touches any already-finalized `Inscripcion`/`DiagnosticoAlumno`/`InformeVersion` — those keep reading their own independent snapshots exactly as before, unaffected by a later correction to the person's name or DNI. Tests: `test_auditoria_persona_unitario.py`/`verificar_edicion_persona_e2e.py`. Migration: `2026_09_25_2229-9424f38351ae_registro_cambios_persona.py`.

### Privacy / legal constraints (Ley 29733)

Consent is checked on every write to an exam (`acepto_consentimiento` on the enrolment plus `tiene_consentimiento_vigente` for the person, apoderado track) and is always evaluated scoped to a specific institution — a consent recorded at School A is never valid grounds to enrol the same person at School B, even though `Persona`/consent rows are keyed by person, not by campaign. ARCO rights are implemented as soft delete (`is_deleted`) and anonymization (`is_anonymized`) rather than hard deletes, and anonymization is itself logged in `auditoria_arco` (who, when, from what IP, on whom). `documento_identidad` and `codigo_institucional` are each unique per institution, not globally — the same person (or two unrelated people who share a typo'd DNI) at two different schools doesn't collide, and a 409 from one school never confirms that a document/code exists at another. An enrolment is unique per (campaign, person) — `uq_edu_inscripciones_evaluacion_persona` — so a student can't hold two seats in the same campaign; anonymous/unnamed links (`persona_id IS NULL`) are exempt, since PostgreSQL treats NULLs as distinct and several nameless seats in one campaign is legitimate. Reapplication limits (`puede_aplicar_prueba`) combine the institution's `limite_pruebas_mensual_por_alumno` with the test's `dias_minimos_entre_aplicaciones` — note this rule and "already enrolled in this exact campaign" (C-15) are both independent of consent state and are evaluated separately; a test that enrols the same student twice for a renewal check needs either a different campaign or a different test, or it'll trip one of these instead of what it meant to test.

### Informes: `Informe`/`InformeVersion`, storage, and the professional psychometric report

An `Informe` (`modulos/educativo/models.py`) is 1:1 with an `Inscripcion` (`ON DELETE CASCADE`, unique on `inscripcion_id`) — it belongs to *that application*, not to the student, so a student with three resolved campaigns has three independent `Informe` rows, each with its own version history. `InformeVersion` is the immutable record of one actually-rendered PDF: `numero_version`, `resultados_snapshot` (JSON — the *entire* structured content used to build that PDF, see below), `storage_key`/`nombre_archivo`/`mime_type`/`tamano_bytes`/`checksum_sha256`, and `generado_por_usuario_id`/`motivo_version` (`NULL`/`"Emisión inicial"` for the automatic one, a required reason for every reissue). `Informe.version_actual` only ever moves forward; a version is never edited or overwritten.

The PDF itself is never stored in Postgres. [core/storage/](backend/core/storage/) defines `StorageService` (abstract: `guardar`/`leer`/`existe`), `LocalStorageService` (writes under `STORAGE_LOCAL_PATH`, default `./storage_local`, with an anti-path-traversal check even though every caller already builds the key from validated data) for the pilot, and `ObjectStorageService` (any S3-compatible provider — AWS S3, Cloudflare R2, MinIO — via `boto3`, imported lazily so a dev box running the default `STORAGE_BACKEND=local` never needs `boto3` installed) for production. `obtener_storage_service()` picks the backend from `STORAGE_BACKEND`/`STORAGE_S3_*` env vars and caches the instance. `construir_storage_key(institucion_id, informe_id, numero_version)` is the *only* place a key is built (`instituciones/{institucion_id}/informes/{informe_id}/v{n}.pdf`) — no endpoint accepts a client-supplied key; every download resolves the file server-side starting from an already-authorized `inscripcion_id`/token.

Generation is triggered automatically, once, right after `finalizar_examen_seguro` commits — via `BackgroundTasks` (`crud.tarea_generar_informe_en_segundo_plano`, which opens its *own* `SessionLocal()` since the request's session is already closed by the time a background task runs), regardless of whether the result is an alert. That's deliberate: the file existing in storage is never itself the authorization check — `resultado_visible_alumno`/`informe_liberado` still gate every download exactly as before this phase, so a retained informe's PDF sits in storage same as a released one, just inaccessible to the student until a professional liberates it. Regeneration only happens through an explicit reissue (`POST /inscripciones/{id}/informe/reemitir`, requiring a `motivo`), which creates `version_actual + 1` and never touches an earlier version — nothing regenerates a PDF just because someone opened a student's file again. Mass/batch generation (hundreds of PDFs from one action) is explicitly not built — `BackgroundTasks` is fine for the one-application-at-a-time pilot; a queue/worker design is future work.

The PDF ([core/pdf_generator.py](backend/core/pdf_generator.py)) is a fixed, numbered, reusable **structure** whose **content** is entirely data-driven — nothing in this file, or in `crud.construir_contenido_pdf()`/`obtener_datos_para_pdf()` which feed it, mentions PHQ-9 or any other instrument by name:

```
INFORME PSICOMÉTRICO
1. DATOS DE FILIACIÓN            5. RESULTADOS
2. MOTIVO DE CONSULTA               5.1 Resultados cuantitativos
3. TÉCNICAS E INSTRUMENTO           5.2 Resultados cualitativos
4. OBSERVACIÓN CONDUCTUAL           5.3 Análisis de riesgo
                                  6. CONCLUSIONES
                                  7. RECOMENDACIONES
                                  8. FIRMA
```

Format: Arial at 11pt body text (registered from the OS's font files when present — `arial.ttf`/`arialbd.ttf`/`ariali.ttf` on the usual Windows/Linux/macOS paths — falling back silently to Helvetica, its metric equivalent, when not; this is verified in the tests by inspecting the PDF's actual `Tf` content-stream operators, not just that a font resource is declared), justified paragraphs, a running header (institution name + "DOCUMENTO CONFIDENCIAL") and footer (prueba name + page number) drawn per-page via a reportlab canvas callback (not flowables, which would scroll away from a fixed position), and `KeepTogether` around each heading plus its first paragraph to avoid orphaned titles.

Every piece of content is traceable to one of three sources, and the PDF itself marks which one it came from so a configured suggestion is never mistaken for something a psychologist wrote:

- **Automatic** — filiación (all from the `Inscripcion` snapshot, never live `Persona`), fecha, prueba, puntajes, dimensiones, niveles, `es_alerta`/`alerta_por`/`estado_interpretacion`/`reglas_con_error`.
- **Configured by the prueba/baremo** — `Prueba.motivo_consulta_default`, `Prueba.tecnicas_adicionales` (comma-separated, same convention as `dimensiones_sin_baremo`), and per baremo tramo: `Baremo.interpretacion` (pre-existing) plus the newer `Baremo.conclusion_sugerida`/`recomendacion_sugerida`. All three, plus the tramo's own `puntaje_minimo`/`puntaje_maximo`, are snapshotted onto `DiagnosticoAlumno` (as `conclusion_sugerida`/`recomendacion_sugerida`/`rango_minimo`/`rango_maximo`) at interpretation time — same instant-not-reference pattern as `nivel`/`es_alerta`.
- **Professional** — four nullable `Inscripcion` columns (`motivo_consulta`, `observacion_conductual`, `conclusion_override`, `recomendaciones_override`), writable only through `PATCH /inscripciones/{id}/revision-informe`. A professional value always wins over a configured one; `observacion_conductual` has no configured fallback at all — it's either what the professional wrote or an explicit "pendiente de registro", *never* inferred from a score. Writing these fields does **not** retroactively change any already-generated PDF — same "no silent regeneration" rule as everything else here — a professional has to call the reissue endpoint for their edits to actually appear in a new version.

`InformeVersion.resultados_snapshot` freezes the *entire* assembled content (filiación, motivo, técnicas, observación, per-dimension results, análisis de riesgo, conclusiones, recomendaciones) as it was for that specific render, so a later change to `Prueba`/`Baremo`/`Inscripcion` — or the student moving to a different `Seccion` — never alters a historical informe; `filiacion.grado_instruccion` reads `Inscripcion.grado_seccion_historico`, never the student's current enrolment.

**PHQ-9 is the first, and so far only, test with a complete professional informe**: catalog, item-9 rule, and the motivo/técnicas/conclusion/recommendation content are all loaded by `seed_phq9.py`. Adding a second instrument is meant to be a repeat of the same data-loading exercise (carga-masiva + baremos with `conclusion_sugerida`/`recomendacion_sugerida` + optional `ReglaInterpretacion` rows) — not a code change to `pdf_generator.py`, `crud.construir_contenido_pdf`, or the rules engine.

**Known non-blocking gaps**: `"Vive con"` in filiación always renders as "No registrado" — no form anywhere collects it, for any test; firma/sello are blank lines for the professional to fill by hand, deliberately (no digital signature yet — `core/pdf_generator.py` has a comment marking exactly where an image from `StorageService` would go once that exists); the matplotlib bar chart still renders with its default font, not Arial, since it's a rasterized image rather than document text; and the Fase-1 concurrent-double-submit test can be flaky under a saturated local dev server, see the test-suite note above — the underlying locking in `finalizar_examen_seguro` was re-verified correct.

### Informe PDF — ordenar dimensiones por puntaje ("Diseño A" para pruebas de perfil)

Loading IPIP-RIASEC (see "Catálogo de pruebas cargadas" above) surfaced a second, practical problem beyond engine limit #3 (no comparative/"perfil" interpretation mode — closed separately, see "Interpretación por perfil" below): even with the correct scores already computed, the PDF itself made them unreadable as a profile. `crud.obtener_datos_para_pdf` built `dimensiones_datos` straight from an unordered query, so the 5.1 results table and the bar chart always printed dimensions in creation order (R-I-A-S-E-C), never by score — a professional had to scan all 6 rows by hand to find the top 3 (the "Holland code"). Separately, section "5.3. ANÁLISIS DE RIESGO" is clinically framed and, for an instrument that can never flag `es_alerta` (RIASEC, and already CHASIDE before it), printed that clinical heading just to say "nothing here" on every single report.

Both are pure **presentation** fixes — neither touches `Baremo`, `DiagnosticoAlumno`, or how a result is interpreted:

- `Prueba.ordenar_dimensiones_por_puntaje` (Boolean, NOT NULL, `server_default='false'`) — every test loaded before this feature stays `False`, zero behavior change. When `True`, `obtener_datos_para_pdf` sorts `dimensiones_datos` by `puntaje` descending before anything downstream reads it, and `crud._calcular_codigo_perfil()` takes the first letter of each of the top-3 dimensions' `nombre` (generic — it doesn't know RIASEC exists, it just assumes dimension names are chosen so their initials are meaningful, true for R-I-A-S-E-C) and exposes it as `contenido["codigo_perfil"]`. `pdf_generator.generar_pdf` prints a "Código de perfil (3 dimensiones con mayor puntaje): XXX" line right under the 5.1 bar chart only when that key is present — for every other test it's `None` and the line never appears.
- `crud._prueba_puede_generar_alerta(db, prueba_id)` — **derived, not stored**, so it can never drift from the actual baremo/regla configuration: `True` if the prueba has any `Baremo` (`activo=True`) with `es_alerta=True`, or any `ReglaInterpretacion` (`activa=True`) that could force one, regardless of whether *this particular* result triggered it. Exposed as `analisis_riesgo.puede_alertar` (default `True` if the key is ever missing, so a historical `resultados_snapshot` from before this feature still renders with the original clinical title). `pdf_generator.generar_pdf` titles section 5.3 "5.3. INDICADORES REGISTRADOS" instead of "5.3. ANÁLISIS DE RIESGO", and prints "Esta prueba no clasifica resultados como indicadores de alerta clínica." instead of "No se identificaron indicadores de alerta en esta aplicación." — only when `puede_alertar` is `False`. PHQ-9/GAD-7/APGAR-FAMILIAR (all genuinely alertable) keep the exact title/wording they always had; CHASIDE's *new* informes pick up the neutral wording automatically (its already-stored PDFs are untouched — informes are never regenerated just because the renderer changed).

`seed_riasec.py` sets `ordenar_dimensiones_por_puntaje=True` on creation, and `_asegurar_orden_por_puntaje()` (idempotent, additive, same pattern as every other `_asegurar_*` helper in these scripts) flips it on an already-loaded row on a re-run.

This is **not** the same thing as engine limit #3 (`modo_interpretacion='perfil'`, comparing dimensions to decide `es_alerta`/`nivel` — since closed for real, see "Interpretación por perfil" below): that one is about *interpretation*, this is only about *display order and section wording* for results already computed. The two were built independently (this one first) and compose cleanly: IPIP-RIASEC uses both today, `ordenar_dimensiones_por_puntaje` for how the PDF displays what `interpretar_perfil_alumno` already interpreted.

Verified against a real generated PDF (via `pypdf`, same technique as `verificar_informe_pdf_e2e.py`): the código de perfil line and section renaming appear correctly for IPIP-RIASEC, and a PHQ-9 PDF generated the same session is byte-for-byte identical in wording to before (title, "No se identificaron indicadores..." line, no "Código de perfil" line) — no dedicated e2e test file was added for this (manual verification only, same criterion already used for the six `seed_*.py` instrument loads), but `tests/test_perfil_ordenado_unitario.py` covers the pure logic (`_calcular_codigo_perfil`, `_prueba_puede_generar_alerta`, and source-level checks that both call sites and `pdf_generator.py`'s conditionals are wired correctly) with no DB. Migration: `2026_09_30_1030-92461c40d56e_ordenar_dimensiones_por_puntaje.py`.

### Expediente clínico individual: `EntradaExpediente`/`EntradaExpedienteVersion`

A per-`Persona` clinical timeline already exists in [modulos/superadmin/models.py](backend/modulos/superadmin/models.py) — it predates this file's last full pass and is easy to miss without grepping for it. `EntradaExpediente` is the identity of one timeline row (same split as `Informe`/`InformeVersion`): `tipo_entrada` is CHECK-constrained to six values, three of them narrative (`observacion_conducta`, `contacto_apoderado`, `derivacion`, content in `EntradaExpedienteVersion`, versioned exactly like `InformeVersion` — `numero_version`, immutable, a required `motivo_version` for any correction past v1) and three of them **bridges** (`sesion` → `SesionSeguimiento`, `aplicacion_prueba` → `Informe`, `documento_institucional` → `DocumentoInstitucional`) that only link to content owned by another module and never carry their own version (`version_actual` stays NULL for these — there is nothing of their own to version). A second CHECK (`ck_expediente_campos_segun_tipo`) enforces that each `tipo_entrada` populates exactly the FK column that belongs to it. **Fixed**: the `sesion`/`aplicacion_prueba` bridges always exposed their target id (`sesion_seguimiento_id`/`informe_id`) in both the list and detail responses, but `documento_institucional_id` was missing from both — a caller who saw a `tipo_entrada='documento_institucional'` row had no way, through either endpoint, to learn which `DocumentoInstitucional` it pointed to. Both `schemas.EntradaExpedienteResponse` and the hand-built dict in `crud.obtener_detalle_entrada_expediente` now include it.

**Confidentiality is strict and has no intermediate tier**: only `autor_usuario_id` or `superadmin` can read a row's content — not even `admin`. The one exception is `AutorizacionAccesoColegio`, a per-`Persona` grant (never per-entry) that only roles `psicologo`/`superadmin` can create or revoke (`requerir_rol("psicologo", "superadmin")` — `admin` and `colegio` cannot, and `colegio` can't even list its own grants), following the exact same "grant is a new row / revoke mutates that same row" mechanism as `ConsentimientoInformado`, with a partial unique index guaranteeing at most one vigente grant per persona. There is deliberately no "visible metadata, locked content" middle state: `crud.listar_entradas_expediente_visibles` filters out the entire row for anyone who fails the access check, so an unauthorized role doesn't even learn that an entry exists, let alone its type or date. `RegistroLecturasExpediente` is an append-only audit trail of every *full-content* read (never of metadata-only list views), recording which version was read and, when the read only happened because of a vigente `AutorizacionAccesoColegio`, a permanent pointer to that specific grant row.

The `documento_institucional` bridge (added alongside the documentos engine, see below) is created internally by `superadmin_crud.crear_entrada_expediente_documento_institucional()` — **never** through the public `POST .../expediente` endpoint, whose schema doesn't accept this `tipo_entrada` at all. It's idempotent by design: it's invoked on every version generation (v1 and every reissue) but only inserts a row the first time for a given (persona, documento) pair, because the bridge points at the `DocumentoInstitucional` *identity*, not at a specific version — same principle as `aplicacion_prueba` pointing at `Informe`, never at an `InformeVersion`, so reissuing never duplicates the timeline entry. `DocumentoInstitucional.nivel_visibilidad` (its own, separate visibility rule — see "Motor de documentos institucionales") has **zero** effect on this bridge's confidentiality: a `colegio` user who can open a `compartible_colegio` document still needs a vigente `AutorizacionAccesoColegio` to read its bridge entry in the student's expediente, exactly like any other entry. This was a deliberate design choice to avoid a second authorization channel into the same clinical record.

Tests: `tests/test_expediente_unitario.py` / `tests/verificar_expediente_e2e.py`. Migrations: `2026_09_26_1600-4e554b5d23e8_expediente_estudiante.py` (original five-type expediente), extended by `2026_09_27_1000-9f13619766a9_motor_documentos_institucionales.py` (adds the sixth type + `documento_institucional_id`).

Frontend: there is no dedicated `/expediente` route — the timeline (list, detail, create entry, new version) and `AutorizacionAccesoColegio` management (grant/revoke) are embedded inside `aurora_ui/app/(educativo)/estudiantes/[personaId]/page.tsx`, the student's ficha page. The client does no confidentiality filtering of its own: it renders exactly what `GET /admin/personas/{id}/expediente` and the detail endpoint return (already filtered server-side), and only gates *write* buttons on `rol === "psicologo" || "superadmin"` client-side — cosmetic, same as `<RequireAuth>` elsewhere, and intentional, not a gap. `types/api.ts` already has full contracts for `EntradaExpediente`/`EntradaExpedienteVersion`/`EntradaExpedienteDetalle`/`AutorizacionAccesoColegio` and their create/response shapes.

### Motor de documentos institucionales: `TipoDocumento`/`PlantillaDocumento`/`DocumentoInstitucional`

A configurable-template engine for clinical/institutional documents — informe individual, informe grupal/institucional (a whole section, several sections, or a hand-picked list of students), plan de trabajo/matriz (no students at all) — living entirely in `modulos/documentos/` (`models.py`/`schemas.py`/`crud.py`/`router.py`/`pdf_generador.py`). It is **not** the psychometric `Informe`/`InformeVersion` (still 1:1 with an `Inscripcion`, untouched) — the two systems are independent; a "PHQ-9 result" document and an "informe individual" document about the same student are unrelated rows in unrelated tables.

**Catalog layer, superadmin-only writes**: `TipoDocumento` (global catalog — `alcances_permitidos`/`visibilidades_permitidas` are comma-lists, same convention as `Prueba.tecnicas_adicionales`, naming which of the fixed CHECK-enum values a given tipo may use; `requiere_consentimiento_individual` is the *only* signal the consent gate reads — **never** `clave`/slug, same "no logic by name" discipline already used for pruebas) and `AnioOficial` (tiny global catalog: the government-declared name of the year, e.g. "Año De La Esperanza Y El Fortalecimiento De La Democracia", shown in a header section when its plantilla opts in). `PlantillaDocumento` is per (institución, tipo), **edited only by superadmin** — the platform owner builds each school's template from real documents the school provides, never a self-serve designer — with a partial unique index (`activa=true`) guaranteeing at most one active plantilla per institución+tipo, same mechanism as `ConsentimientoInformado`/`MatriculaAcademica`; typography (`fuente`/`tamano_pt`/`interlineado`/`justificado`) is fixed per plantilla, never adjusted per document. `PlantillaSeccion` composes a plantilla from a **closed** set of eight `tipo_seccion` values (`encabezado`, `datos_filiacion`, `datos_familiares`, `texto_libre`, `tabla_dinamica`, `resultados_prueba`, `firma`, `grupo_campos`) — unlike `TipoDocumento` (pure data), this one needs an actual renderer per value (`modulos/documentos/pdf_generador.py:_RENDERIZADORES`), same role `Prueba.modo_calculo` plays in the scoring engine. The eighth, `grupo_campos`, used to be deferred here as a "no real school has asked for it yet" placeholder — it's now built (see "Known non-blocking gaps" below for what closed it and why) and can also double as a generic labeled-field block for cases like third-party contacts, not just the structured-interview need that justified building it.

**Creating a `DocumentoInstitucional`** (`crud.crear_documento_institucional`) never accepts `institucion_id` as a request field at all — it's derived from `plantilla_documento_id` (itself re-fetched and validated from the DB) and cross-checked against the caller's own institución. The frozen student list (`DocumentoInstitucionalEstudiante`) is populated by either or both of two paths in the same request: a "shortcut" (`estructura`: one or more `NivelEducativo`/`Grado`/`Seccion` nodes, each re-validated against the DB before resolving its currently-matriculated students — `DocumentoInstitucionalEstructura` records the criterion used, purely for audit) and manual `persona_ids` (each re-validated too). `alcance='estructura_academica'` allows combining both in one document (a full section plus a few extra names, deduplicated, the shortcut-sourced ones keeping `incluido_via='seccion'`); `alcance='personas_especificas'` is manual-only; `alcance` in (`institucion`, `ninguno`) must produce zero rows. This list is **immutable across versions** — a reissue can never add or remove a student; that's a new `DocumentoInstitucional` — enforced by the reissue endpoint's schema simply not accepting any such field, not by a cross-table DB constraint (there isn't a cheap way to express that).

**Draft content** (`DocumentoInstitucionalSeccionContenido`, one row per `plantilla_seccion_id`, upserted via `PUT /documentos/{id}/secciones/{plantilla_seccion_id}`, full replace not merge) stays intentionally schema-less JSON — not every `tipo_seccion` uses it the same way (`texto_libre`/`tabla_dinamica` are professional-authored; `datos_filiacion`/`datos_familiares`/`resultados_prueba` are mostly automatic and only read a sliver of it, e.g. `datos_filiacion`'s one professional field, "diagnóstico presuntivo") — fixing a strict per-type shape here would have meant guessing ahead of the actual renderer. Editing content after a document already has a `version_actual` is normal and expected: it's exactly how the *next* reissue's content gets authored: the already-emitted version's own `contenido_snapshot` is frozen and never reads this table again.

**Generating a version** (`crud.generar_version_documento`, `POST /documentos/{id}/generar-version` for v1, `POST /documentos/{id}/reemitir` requiring a `motivo` for v2+) is the highest-risk path, and reuses the exact concurrency-safety shape `CLAUDE.md` already documents for `finalizar_examen_seguro`: `bloquear_documento_institucional_para_version`/`bloquear_correlativo_para_emision` both use `.with_for_update()` (the latter with `.populate_existing()`), and the correlativo counter (`CorrelativoDocumento`, `anio=0` — not `NULL` — is the sentinel for "never resets annually", because Postgres treats `NULL`s in a `UNIQUE` as distinct from each other) is incremented and the PDF rendered *inside* that lock, so two simultaneous emissions of the same institución+tipo(+año) can never receive the same correlativo number — there's no unique constraint on the number itself to catch it after the fact if the lock were ever removed. The **consent gate** (`tiene_consentimiento_vigente`, apoderado track only — the student's own asentimiento is tracked and visible via `GET /personas/{id}/consentimientos` but deliberately does not block this, a psychologist's explicit decision) fires only when `TipoDocumento.requiere_consentimiento_individual` is true, and is re-evaluated on **every** call, v1 and every reissue alike — unlike exam finalización (a one-time historical event that never re-checks), each document version is treated as a fresh act of producing personal-data output, so a consent revoked between v1 and a reissue blocks the reissue too. Every write with a unique constraint behind it (`CorrelativoDocumento`, the plantilla-activation race, the ficha upsert races, the version race) is wrapped in `try/except IntegrityError → rollback → 409`, matching the pattern already used everywhere else in this codebase (`auth.crear_usuario`, `NivelEducativo`/`Grado`/`Seccion` creation, `AutorizacionAccesoColegio`...) — a concurrent double-submit here fails clean, never with an opaque 500.

The renderer (`modulos/documentos/pdf_generador.py`) is independent of `core/pdf_generator.py` on purpose (different structure, per-institución configurable typography vs. the psychometric informe's fixed Arial 11pt) but shares font *registration* logic via `core/pdf_fuentes.py` (extracted, behavior-preserving — the existing informe PDF e2e tests are its regression check). `datos_filiacion`/`datos_familiares`/`resultados_prueba` sections only render real content when the document has **exactly one** student in its frozen list — with 0 or more than 1, they explicitly render "no aplica" rather than guessing whose data to show; `resultados_prueba` additionally needs a `DocumentoInstitucionalResultadoPrueba` row (documento × plantilla_seccion × persona → `Inscripcion`) pointing it at a real psychometric application, supporting a single individual document referencing more than one instrument (e.g. FES + CARAS-R), each with its own row.

**Reading/downloading** (`GET /documentos/{id}`, `.../secciones`, `.../versiones`, `.../versiones/{n}/descargar`) all funnel through `crud.usuario_puede_ver_documento`: `superadmin` always; `admin`/`psicologo` of the same institución always, regardless of who created the document (tenant+rol, no per-document ACL); `colegio` only when `DocumentoInstitucional.nivel_visibilidad='compartible_colegio'` (default `confidencial_clinico`) — the listing endpoint doesn't block `colegio` outright, it just filters rows. This rule governs *only* direct access to the document itself and has no bearing whatsoever on the expediente bridge's own confidentiality (see above) — the two are deliberately independent so a document can be teacher-facing without ever loosening the clinical record.

**Read-audit trail**: `RegistroLecturaDocumento` (`documentos_registro_lecturas`, append-only, same role as `RegistroLecturasExpediente`) records every time someone reads the actual content of a document — `GET .../secciones` (`tipo_acceso='contenido'`, `numero_version_leida` NULL since the draft isn't versioned) and `GET .../versiones/{n}/descargar` (`tipo_acceso='descarga_pdf'`, `numero_version_leida` set) — with who, their role at that moment, their IP (`core.deps.ip_del_cliente`), and `acceso_via_visibilidad_colegio` (true whenever the reader's role is `colegio`, since that's the only way `usuario_puede_ver_documento` lets `colegio` reach either endpoint). `GET /documentos/{id}` (detail), the plural listing, and `GET .../versiones` (version list) are metadata only and never write a row here, same "listing never audits, only content does" rule `RegistroLecturasExpediente` already follows. This trail is completely independent from the expediente bridge's own confidentiality rule: a `colegio` reader who can open a `compartible_colegio` document's content (and gets audited for it here) still needs a vigente `AutorizacionAccesoColegio` to read that same student's bridge entry in the expediente — reading the document, however it happened, never unlocks the bridge.

Tests: six pairs under `test_documentos_*_unitario.py`/`verificar_documentos_*_e2e.py` (catalogo, creacion, contenido, version, acceso, lecturas — see the Commands section above; `PersonaDatosFamiliares`/`PersonaAntecedentesClinicos` have their own seventh pair, but live in `modulos/superadmin`, not here). Migrations: `2026_09_27_1000-9f13619766a9_motor_documentos_institucionales.py` (the whole schema), `2026_09_28_1000-5430930882da_antecedentes_clinicos_persona.py` (`PersonaAntecedentesClinicos`, added one round later), and `2026_09_28_2130-c47a2e91f0b6_auditoria_lecturas_documentos.py` (`documentos_registro_lecturas`, the read-audit trail).

Three gaps documented here previously are **now closed**, all part of the same scalability pass (loading batteries like BARSIT, SDQ, NICHQ Vanderbilt, GAD-7, ICAR, RCADS, SCARED, CHASIDE, etc. across many institutions, each wanting its own document design):

- **`DocumentoInstitucionalResultadoPrueba` now has a public write path** — `PUT/DELETE /documentos/{documento_id}/secciones/{plantilla_seccion_id}/resultados-prueba` (`crud.vincular_resultado_prueba`/`desvincular_resultado_prueba`), `requerir_rol("superadmin","admin","psicologo")`. Re-validates, from the DB, that the section really is `tipo_seccion='resultados_prueba'` on this document's own plantilla, that the persona is in the document's frozen student list, and that the `Inscripcion` belongs to that persona and to an `Evaluacion` of the same institución as the document — same "never trust an id the client sent without re-checking it" discipline as everywhere else. Upsert on the (documento, sección, persona) unique index, so re-linking before a version is generated corrects a mistake instead of erroring.
- **The engine now renders each institución's own logo.** `crud.construir_contenido_documento` snapshots `Institucion.logo_url` into `contenido["institucion"]` at generation time (frozen per version, same as everything else in that snapshot); `pdf_generador.generar_pdf_documento` draws it via the same SSRF-safe `core.url_segura.descargar_logo_seguro()` the psychometric informe already used — a bad/unreachable logo just means no logo, never a broken document.
- **An eighth `tipo_seccion`: `grupo_campos`** — a generic, plantilla-defined set of etiqueta/valor fields (`PlantillaSeccion.config = {"campos": [{"etiqueta": "..."}]}`, filled per document in `DocumentoInstitucionalSeccionContenido.contenido = {"valores": {...}}`), needing no new tables since both were already free-form JSON. This is exactly the "labeled field group" this file used to list as deliberately deferred — the concrete need that justified building it is a structured interview/anamnesis whose questions are fixed per institución (e.g. a colegio's own intake interview format). Migration: `2026_09_29_1000-b9fb300190a4_seccion_grupo_campos.py` (widens `ck_documentos_plantilla_seccion_tipo_valido`).

**New, not gap-closing**: `POST /documentos/plantillas/{plantilla_id}/clonar` (`crud.clonar_plantilla_documento`, superadmin-only) copies a `PlantillaDocumento`'s structure (its `PlantillaSeccion` rows, in order, with their `config`) to another institución — never any already-emitted document's content, and never `activa=True` unless explicitly requested (so it can't silently deactivate a destination institución's existing plantilla for that tipo). This exists because onboarding scales to many institutions by cloning a plantilla that already fits what a new colegio is asking for and adjusting typography/logo/wording, not by re-authoring every section from scratch each time.

The three new endpoints above (`PUT`/`DELETE .../resultados-prueba`, `POST .../clonar`) are in `tests/matriz_permisos_esperada.json`, confirmed against `test_matriz_permisos_unitario.py` — no endpoint lets `colegio` in. `test_documentos_version_unitario.py`'s renderer-count check was updated from "7 tipos" to "8 tipos" to account for `grupo_campos`. None of these four features have their own dedicated e2e yet (no `verificar_documentos_resultado_prueba_e2e.py`/logo/clonado-specific test) — only verified manually against the real local DB and via the existing unit suites; that's open follow-up work, same as the informante feature above.

**`resultados_prueba` never renders a retained result — fixed.** The same validation pass found that `crud._resolver_resultados_prueba` read `DiagnosticoAlumno.nivel`/`.interpretacion` with no check of `Inscripcion.informe_liberado`/`.resultado_visible_alumno`, so a `DocumentoInstitucionalVersion` could surface a psychometric result the professional review/release gate (see "Exam finalization is transactional" above) was still withholding. The fix is a **section-level degradation, never a whole-document failure** — deliberately consistent with `_resolver_datos_filiacion`/`_resolver_datos_familiares`'s existing "no aplica" pattern, and deliberately conservative (it does not condition on `DocumentoInstitucional.nivel_visibilidad`, even though only `colegio` reading a `compartible_colegio` document is actually blocked from an unreleased informe today via `crud.verificar_puede_ver_informe` — staff can already see a retained informe through the direct endpoints). If either flag is `False`, `_resolver_resultados_prueba` now returns `{"aplica": True, "retenido": True}` instead of the score/dimensions, and `pdf_generador._renderizar_resultados_prueba` prints "Pendiente de revisión profesional" in that section instead — the rest of the document (filiación, texto libre, firma, other sections) generates normally, `generar-version`/`reemitir` never fails because of this. Since a version's content is frozen at generation time and never re-evaluated per reader, this is a one-time decision made when the PDF is built, not a per-request check. A later reissue (after the professional actually liberates the informe via the existing `informe_liberado`/`resultado_visible_alumno` endpoints) picks up the real data, exactly like any other content correction — earlier versions stay byte-identical, same as always. Tests: `test_documentos_version_unitario.py` (pure-logic branch coverage of the OR condition and of the renderer's placeholder, no DB) and `tests/verificar_documentos_resultado_retenido_e2e.py` (prefix `ZZDOCRET` — mounts a real high-score PHQ-9 application that finalizes retained, confirms v1 never exposes the real nivel/interpretación, confirms `informe_liberado` and `resultado_visible_alumno` are independent — releasing only one still leaves it retained — and confirms a reissue after both are set shows the real result while the earlier retained version stays byte-identical).

## Frontend architecture

Read [aurora_ui/AGENTS.md](aurora_ui/AGENTS.md) first: this is Next.js 16, whose APIs and conventions differ from older versions — consult `node_modules/next/dist/docs/` before writing App Router code rather than relying on memory. (`aurora_ui/CLAUDE.md` just imports that file.)

Route groups map to audiences, and the group name never appears in the URL:

- `app/(educativo)/` → `/estudiantes`, `/campanas`, `/agenda`, `/academico`, `/casos-riesgo`, `/pruebas` — the psychologist's app. `/agenda` is a plain list of the logged-in psychologist's `CitaProgramada` rows (`GET /personas/citas/mi-agenda`) with a cancel button, not a calendar/grid view. `/academico` is a real CRUD for `NivelEducativo`/`Grado`/`Seccion` (create/list against `GET/POST /admin/personas/academico/{niveles,grados,secciones}`), not a dashboard.
- `app/(superadmin)/master/` → AuroraSoft's own back office, guarded by `<RequireAuth rolesPermitidos={["superadmin"]}>`.
- `app/(examen)/examen/[token]/` → the student's public exam, intentionally with no sidebar and no auth guard. Keep it that way; a guard here would lock students out.

Auth is client-side only: [contexts/AuthContext.tsx](aurora_ui/contexts/AuthContext.tsx) stores the JWT in `localStorage` under `aurora_token` and decodes `sub`/`rol`/`institucion_id` from it ([lib/jwt.ts](aurora_ui/lib/jwt.ts)) without a `/auth/me` round-trip — there is still no `/auth/me` endpoint on the backend. `<RequireAuth>` is cosmetic — the backend dependencies are the real enforcement, including the credential-versioning check above, so a token revoked by a password change fails server-side even though the frontend has no way to notice proactively.

Data fetching goes through [lib/api-client.ts](aurora_ui/lib/api-client.ts), which attaches the bearer token and normalizes errors into `ApiError`. Login is the exception: the backend uses `OAuth2PasswordRequestForm`, so it posts `application/x-www-form-urlencoded` with the email in the `username` field.

Tailwind v4 is configured entirely through the `@theme` block in [app/globals.css](aurora_ui/app/globals.css) — there is no `tailwind.config`. Brand tokens: teal is the primary palette, `mist` the app background, `ink` the text, and `amber` is reserved exclusively for risk alerts. Don't spend amber on ordinary accents.

### Known rough edges

- `AuthContext.login` still hardcodes `http://127.0.0.1:8000/api/auth/login` (`contexts/AuthContext.tsx`) instead of using the `login()` helper in `lib/api-client.ts` that respects `NEXT_PUBLIC_API_URL` — a deployment with a different API origin breaks login silently.
- `app/(educativo)/pruebas/page.tsx`, `campanas/nueva/`, `campanas/[id]/dashboard/`, and both `master/` pages (`master/page.tsx`, `master/clientes/page.tsx`) are still empty files; the exam page is still a placeholder. The backend endpoints they need already exist (including `GET /educativo/campanas/{id}/dashboard` and `GET /educativo/procesos/dashboard?institucion_id=`, both batch-loaded — no N+1 per student) — check `/docs` for exact shapes before inventing types.
- Campaign edit/close/cancel and admin/superadmin reprocessing after a baremo correction are **now implemented on the backend** (see "Ciclo de vida de campaña y reproceso de informe" below) — but there is still **no frontend** for any of it: `campanas/nueva/`/`campanas/[id]/dashboard/` are still empty files, and nothing in `aurora_ui` calls `PATCH /educativo/campanas/{id}`, `.../cerrar`, `.../cancelar`, or `POST /educativo/inscripciones/{id}/reprocesar` yet.
- There's no calendar-style view or in-app reminder anywhere: `/agenda` (see above) is a text list, and the only real "recordatorio" is the `notificar_agenda_diaria.py` cron email — it never surfaces in the UI. The post-login landing page for staff is the student roster (`/estudiantes`), not a dashboard, so there's no home screen for an agenda/reminder widget to live on even if one existed.
- The motor de documentos institucionales (backend, fully built — see above) has **zero** frontend: no route under `app/`, no type in `types/api.ts`, no mention in `AGENTS.md`, no consumption of any `/api/documentos/*` endpoint anywhere in `aurora_ui`.

## Known backend gaps (not blocking, not yet built)

Kept here so they aren't rediscovered from scratch: no `/auth/me`; **ARCO acceso and rectificación are now built** (closing what used to be documented here as a gap) — `GET /admin/personas/{id}/exportar-datos-arco` (`requerir_staff_clinico`: superadmin/admin/psicologo, never `colegio`; tenant-checked like the rest of this ficha) exports ficha, historial académico, datos familiares/antecedentes clínicos, contactos, ambos consentimientos, every inscripción with its full diagnóstico content (not just `nivel`), informe version metadata (never the PDF binary), sesiones de seguimiento, citas, and the caller's own visible slice of the expediente clínico — entries the caller isn't personally authorized to read (same rule as the expediente endpoints: author or superadmin only) are omitted and only counted (`expediente_entradas_omitidas`), and reading one still logs a `RegistroLecturasExpediente` row exactly as if opened one by one; the motor de documentos institucionales and the informe PDF binary are deliberately out of this export's scope. Separately from all that, **every successful export writes its own unconditional `RegistroAuditoriaArco` row** (`accion="acceso_datos_persona"`, via the shared `registrar_auditoria_arco` helper — never a second hand-built insert) recording who exported, their role at that moment, the IP, the persona exported, and — when passed — the caller's `referencia_solicitud` in `detalle`; unlike rectificación below, this one has no "did something change" gate, because the act being audited is the access itself, which always happened the moment the endpoint returned 200. Rectificación reuses the existing `PATCH /personas/{id}` rather than a new endpoint: an optional `referencia_solicitud_arco` query param makes `crud.actualizar_persona` additionally write one `RegistroAuditoriaArco` row (`accion="rectificacion_persona"`) in the same commit as its existing `RegistroCambiosPersona` diff, but only when that reference is present *and* at least one audited field actually changed — a routine edit (no reference) or a no-op PATCH (reference present, nothing changed) leaves `auditoria_arco` untouched. Both actions reuse `RegistroCambiosPersona`/`auditoria_arco` exactly as instructed, adding no new tables or migrations. Tests: `test_arco_datos_persona_unitario.py`/`verificar_arco_datos_persona_e2e.py` (prefix `ZZARCO`). Anonymization (`/anonimizar-arco`) remains the only ARCO right that's *irreversible* (the newer `AutorizacionAccesoColegio` grant, see "Expediente clínico individual" above, is a school-access permission a psicólogo issues to a `colegio`, not an ARCO right, and doesn't fill this gap); no cross-campaign historical comparison view for a student; states that are free-text `String` columns with a fixed set of real values in practice (`Inscripcion.estado`, `estado_interpretacion`, `SesionSeguimiento.estado`, `CitaProgramada.estado`, `Usuario.rol`) rather than an enum or CHECK constraint — a `CHECK` constraint is the lower-risk option if this gets tightened later, since adding a value to a native Postgres `ENUM` needs care inside a transaction (newer columns added after this remediation, like `ReglaInterpretacion`'s `ambito`/`operador`/`accion` or `Prueba.modo_interpretacion`, already do use CHECK from day one — this gap is only about the older, pre-existing status columns); a sweep from `datetime.utcnow()` to timezone-aware `datetime.now(timezone.utc)` has started but is incomplete — `modulos/auth/crud.py` and `modulos/documentos/crud.py` are fully on the new pattern, `modulos/superadmin/crud.py` is a mix of both, but `core/` and `modulos/educativo` (the largest module) still use the deprecated-but-still-correct naive-UTC pattern throughout — finish this as one dedicated, whole-codebase pass, not piecemeal. A permission matrix now exists as a *test*, not a document: `tests/test_matriz_permisos_unitario.py` + the checked-in snapshot `tests/matriz_permisos_esperada.json` (see the Commands section above) — it walks `app.routes`, reads the real `Depends(...)` on every `/api` endpoint, and fails on any undeclared/removed/changed endpoint. It does **not** see authorization written inline inside a function body instead of as a `Depends` — see below for what that blind spot turned up and how it was closed.

### Permission surface: `colegio` and clinical content — closed by a five-step remediation

Building the matrix test above (auditing only, no permissions were changed *by the audit itself*) surfaced that most of `modulos/educativo`'s CRUD, plus several genuinely clinical read paths, let `colegio` in by omission — any endpoint using only `Depends(obtener_usuario_actual)` with no role or content gate — rather than by decision. That gap was then closed in a separate five-step remediation, each step covered by its own addition to `tests/test_permisos_colegio_unitario.py` (no DB) and `tests/verificar_permisos_colegio_e2e.py` (prefix `ZZCOLE`, real DB — mounts one actual PHQ-9 application with a real alert-level diagnosis and a real seguimiento note, so the checks prove something is hidden, not just that a list happens to be empty), and reflected in `tests/matriz_permisos_esperada.json`:

1. **`core/deps.py`**: `requerir_staff_clinico = requerir_rol("superadmin", "admin", "psicologo")` — a named alias for the "never `colegio`" tier, so new code expresses this trust boundary with one recognizable name instead of retyping the role tuple (which 19+ call sites already did correctly — the endpoints below simply hadn't).
2. **Mechanical role closure** (`modulos/educativo/router.py`, ~24 endpoints): the full CRUD of `Baremo`/`Dimension`/`Pregunta`/`Opcion`/`ReglaInterpretacion`/`Prueba` (including `carga-masiva`), creating a `Campana`/`matricular-roster`, `GET .../links` (magic-link tokens are access credentials, not read-only data), `GET /casos-pendientes` (the psychologist's alert worklist — this one was actually mis-classified as safe-by-design partway through building the audit tooling itself, and caught before it shipped), and all four `seguimiento` endpoints (create/list/edit/delete follow-up session notes) now require `requerir_staff_clinico`. `PATCH`/`DELETE /seguimiento/{sesion_id}` keep their pre-existing author-ownership check (`sesion.psicologo_id == usuario_actual.id`) as defense in depth on top of the role gate, not instead of it.
3. **Informes gated by `informe_liberado`** (`crud.verificar_puede_ver_informe`): `GET /inscripciones/{id}/informe-pdf` and `.../informe` now apply, for `colegio` only, the exact same condition that already protected the student's own token-based download (`GET /examen/{token}/informe-pdf`) — a retained, unreviewed informe is invisible to `colegio` until a professional releases it, same as before this fix it wasn't. `GET /personas/{id}/informes` (a list, one row per application, each with its own `informe_liberado`) filters row-by-row on the same field instead of a single check.
4. **`ficha-completa` redaction** (`crud.obtener_ficha_completa`, now takes `usuario_actual`): for `colegio`, `historial_evaluaciones` (per-dimension `nivel`) and `sesiones_seguimiento` (narrative `observaciones`/`accion_tomada`) are never queried in the first place — cut before the DB round-trip, not filtered after. No `response_model` was added for this endpoint; the redaction alone removes the sensitive content regardless of how the rest gets serialized, and typing the unrelated parts of this dict (consentimientos, historial académico, citas) was out of scope for this fix.
5. **Dashboard redaction** (`crud.redactar_resultados_dashboard_campana`/`_institucional`): `GET /campanas/{id}/dashboard`, its Excel twin `.../exportar-excel` (same dict, same redaction, applied before `generar_excel_dashboard` builds the spreadsheet), and `GET /procesos/dashboard` all keep participation info (name, estado, fecha, the aggregate `total_*`/`distribucion_por_dimension` counts) visible to `colegio` but blank the per-student `resultados`/`nivel`.

The catalog reads that stay open to `colegio` — `GET /pruebas/`, `/pruebas/{id}/completa`, `/pruebas/{id}/reglas`, `/baremos/{dimension_id}`, `/campanas/` (listing) — are a product decision, not a leftover omission, and are recorded as such in the matrix test's `_COLEGIO_POR_DISENO_CONOCIDO`. As of this remediation, the matrix test's report step (`reportar_endpoints_sensibles_sin_exclusion_de_colegio`) finds **zero** unreviewed endpoints where `colegio` passes the `Depends` layer — any future one it finds is a new gap, not a rediscovery of these.

Deliberately not built yet, on top of the student-core structure above (it's meant to be built *on* this, not alongside it): any dashboard reading the academic structure (per-section, per-grade breakdowns, counts, charts — `app/(educativo)/academico/page.tsx` exists but is a plain CRUD, not a dashboard), follow-up sessions beyond the existing basic `SesionSeguimiento`, documents/images on a student's record, and every bit of frontend for any of this (including for Excel import and for the entire motor de documentos institucionales, both built backend-only) — `crear_tablas.py`'s `BORRAR`-gated reset already covers the new tables, but no UI does yet. `POST /educativo/comenzar-test/{token}` still requires `RegistroAlumnoDemograficos` in its body even for a roster-linked student whose data is already known and gets silently preferred over what's submitted — loosening that requirement is exam-flow/frontend work, intentionally deferred. The institutional policy for which of the two consents (apoderado/estudiante) an application requires is **now implemented** (`Institucion.exigir_consentimiento_estudiante`, see "Two independent consents" above) — apoderado still gates unconditionally, estudiante only when a school opts in. ARCO acceso/rectificación at the `Persona` level are **now implemented** too (see above); what's still missing is an ARCO right scoped to a consent record *itself* (e.g. rectifying an otorgante's own misspelled name on a past `ConsentimientoInformado` row, as opposed to rectifying the `Persona`) — consent rows stay immutable-except-for-revocation, by design, so this would need its own decision, not an extension of what exists. `evidencia_ruta` on `ConsentimientoInformado` is still an unused placeholder until document storage exists. Annual grade promotion **is now implemented** (`ProcesoPromocion`, see "Promoción anual de estudiantes" above) — Excel import itself still has no promotion logic of its own and still requires the target `Seccion` to already exist for the requested `anio_escolar`, same as manual `POST /personas/{id}/matricula`. The motor de documentos institucionales's read-audit trail gap is **now closed** (`RegistroLecturaDocumento`, see "Motor de documentos institucionales" above).
