## What this is

AuroraSoft — a multi-tenant psychometric evaluation SaaS for schools (Peru). A psychologist creates an evaluation campaign, each student gets a unique magic link (`/examen/[token]`), answers a test without logging in, and the backend scores it, interprets it against baremos (norm tables), and withholds at-risk reports until a professional reviews them.

Two independent projects, no shared tooling or root package:

- [backend/](backend/) — FastAPI + SQLAlchemy 2 + PostgreSQL 16, Alembic migrations.
- [aurora_ui/](aurora_ui/) — Next.js 16 (App Router) + React 19 + Tailwind v4.

Code, comments, identifiers, and API paths are in Spanish. Keep writing Spanish — `crear_prueba`, `usuario_actual`, `institucion_id`. Do not rename existing symbols to English.

The backend went through a phased remediation (Fases 0–4, tracked in commit-message-free sessions, not in separate docs) that closed the audit findings referenced throughout this file (`B-1`…`B-12`, `C-1`…`C-17`). Where this file says "antes" ("before"), it means before that remediation — the old behavior no longer exists in the code, but the comments explaining *why* the current code is shaped the way it is were kept on purpose. Don't undo a fix because the surrounding comment reads like a historical note; the note is there so the fix doesn't get silently reverted.

`crear_tablas.py` **drops the entire `public` schema** and rebuilds from models. It is guarded (refuses unless `ENTORNO=development`, plus an interactive `BORRAR` confirmation) and exists only for local resets — never suggest it as a migration path. A database built this way has no `alembic_version` row; stamp it with `alembic stamp head` (never `upgrade`) before touching it with Alembic again, or Alembic will try to recreate tables that already exist.

**File organization**: the 22 `seed_*.py` instrument/bootstrap scripts live under [backend/seeds/](backend/seeds/), not at the backend root — they used to sit directly in `backend/` alongside `main.py`, which is also why every one of them is invoked with `python -m seeds.seed_x` (module form) rather than `python seed_x.py` (direct path): a direct-path invocation only puts the script's *own* directory on `sys.path`, which would break every `from modulos...`/`from core...` import the moment the script isn't sitting next to those packages — the exact same reason `tests/` has used `python -m tests.<archivo>` all along. `seeds/__init__.py` makes it an importable package for that purpose only; nothing on the import side changed (`from modulos.educativo import models` etc. still resolve from `backend/` being on `sys.path`, same as before the move). `backend/bd/` was an empty, unreferenced leftover directory and has been deleted — it held nothing and nothing pointed to it. `modulos/superadmin/_init__.py` (note the typo — one leading underscore, not `__init__.py`) was a second, later find: a 0-byte file with zero references anywhere, confirmed harmless to remove by the fact that `modulos/educativo/` and `modulos/documentos/` have never had an `__init__.py` at all and work identically (implicit Python 3 namespace packages) — `main.app` still imports with the same 153 routes after deleting it. **🆕 A third dead-file sweep (session 2026-10-13, a dedicated audit agent, cross-checked independently before deleting anything)** found three more empty, unreferenced directories under `modulos/` — `modulos/clinico/`, `modulos/seleccion/`, `modulos/organizacional/` (no files inside, not even an `__init__.py`, zero imports anywhere) — same pattern as `backend/bd/`, now deleted (`main.app` still imports with 165 routes after). **Test-hardening pass** (no production code changed, only the tests themselves): a review found that several unit tests for multi-step orchestration functions (`reprocesar_informe_de_inscripcion`, `calcular_resultados_dimensiones`, `actualizar_dimension`) were checking `"texto" in inspect.getsource(funcion)` instead of actually calling the function — a pattern that can't catch calls happening in the wrong order, a value being computed and then silently discarded, or a step quietly disappearing in a future refactor. Where the function's own DB calls are simple enough to duck-type faithfully (a short, known sequence of `.query(Modelo).filter(...).first()/.all()` calls, each resolved once in plain Python with no SQL-level semantics to get wrong), the weak test was replaced with one that calls the real function against a small `_FakeDB`/`_FakeQuerySecuencia` and asserts the actual order of calls and the actual values that flowed between them — `test_reproceso_informe_unitario.py` (two new tests, 40/40 total), `test_conteo_sintomas_unitario.py` (`calcular_resultados_dimensiones` and `actualizar_dimension`'s five real scenarios, 29/29 total), `test_dimension_compuesta_unitario.py` (the `'suma_de_dimensiones'` second pass, 36/36 total). Where it genuinely isn't — a `db.query(func.sum(...)).join(...).filter(...)` SQL aggregate, or picking the one correct `Baremo` row among several sharing a range by `criterio_normativo`, both of which only mean anything once a real database evaluates the condition over real rows, and a one-answer-queued fake would just already know the "correct" answer it's supposed to be testing for — the check stayed as source inspection, but now says so explicitly in the test's own docstring and points at the real `verificar_*_e2e.py` that already proves the same behavior against real Postgres (`test_puntaje_total_excluye_conteo_sintomas`, `test_puntaje_total_no_cuenta_doble`, `test_interpretar_resultados_alumno_filtra_por_criterio_activo` — this last one pointing at `verificar_criterio_normativo_e2e.py`/`ZZCRIT`). The role-gate check in `test_reproceso_informe_unitario.py` (`requerir_rol("superadmin","admin")`, no `requerir_staff_clinico`) was left as source inspection too, for the ordinary reason every other `Depends(...)` check in this suite is — there's no real alternative short of running the full FastAPI dependency-injection stack, which is exactly what `verificar_reproceso_informe_e2e.py` already does for real.

The Fase-1 concurrent-double-submit test (CASO 5 inside `verificar_fase1_e2e.py`) used to fail intermittently — both requests returning 200 instead of one 200/one 400 — and was once believed to be TIME_WAIT connection buildup on the dev machine. It wasn't: the row lock (`with_for_update()`) was always serializing correctly at the Postgres level (verified in isolation), but `finalizar_examen_seguro` queried the same `Inscripcion` twice in the same `Session` — once unlocked (Fase 1), once locked (Fase 2) — and without an explicit refresh, SQLAlchemy's identity map handed the Fase 2 query back the *same Python object* Fase 1 had already loaded, with its stale (pre-lock) `estado`, instead of the row Postgres had just unblocked. The idempotency check (`if inscripcion.estado == "Finalizado"`) read that stale value and never fired for the losing request, which then recomputed everything and duplicated real side effects (the risk alert email sent twice, a second informe-generation attempt colliding on `uq_edu_informes_inscripcion`). Fixed by extracting the Fase 2 query into `crud.bloquear_inscripcion_para_finalizar()`, which adds `.populate_existing()` to force the fresh, post-lock row onto that same identity-mapped object. `tests/verificar_concurrencia_finalizar_e2e.py` reproduces the exact mechanism deterministically (two real ORM sessions, no dependence on a real network race) and separately confirms, via a real concurrent HTTP double-submit, that the informe and its version are generated exactly once.

The repository has no git (`git init` has never been run here); there's no commit history and no branch to check changes against.
