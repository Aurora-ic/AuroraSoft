> Parte de `CLAUDE.md`, separada en la fase 8 del plan de remodelación. Multi-tenancy, JWT, SSRF, rate limiting y la remediación de permisos para el rol `colegio`.

### Multi-tenancy is the central invariant

Every tenant-scoped row carries `institucion_id`. Enforcement lives in [core/deps.py](../backend/core/deps.py) and must go through it:

- `obtener_usuario_actual` — decodes the JWT, loads the user, checks the token's credential version against `Usuario.token_version` (see JWT below), and additionally rejects the request if the institution's `plan_activo` is false or its licence expired. `superadmin` bypasses the licence check.
- `verificar_acceso_institucion` — use on any endpoint that takes an `institucion_id` from path/query/body. `superadmin` passes always; everyone else only for their own institution.
- `requerir_rol("superadmin", "admin", ...)` — role gate. Roles are `superadmin` (AuroraSoft staff, `institucion_id` may be NULL), `admin` (school owner), `psicologo`, `colegio`.

CRUD functions that list or mutate tenant data take `institucion_id` and filter on it (see `listar_campanas_de_institucion`, `soft_delete_alumno`, `verificar_propiedad_de_prueba`). When adding an endpoint, thread the tenant filter all the way into the query — **never trust an id sent by the frontend** (`institucion_id`, `persona_id`, `prueba_id`...) when it can instead be derived from the authenticated user or re-validated against the record it claims to belong to. `matricular_roster_en_campana` is the canonical example: it re-checks every `persona.institucion_id` against the campaign's institution from the DB row, not from the request.

Answering a public exam endpoint (no login, just a magic-link token) goes through its own authority chain, not the JWT one: `guardar_respuestas_examen` walks *inscripción → evaluación/campaña → prueba → pregunta → opción* in the database and rejects the whole batch if any (pregunta, opción) pair falls outside it, so a crafted request can't borrow another test's — or another school's — scoring values.


### JWT credential versioning

`Usuario.token_version` (int, defaults to 0) is embedded in every login JWT as the `"tv"` claim. `obtener_usuario_actual` rejects a token whose `tv` doesn't match the user's current `token_version` — a token issued before this feature existed has no `tv` claim and is treated as `0`, so no one gets logged out by the upgrade itself. Changing a password (via `/auth/resetear-password` or `seed_superadmin.py`) increments `token_version`, which invalidates every JWT issued before that moment (previously a stolen token stayed valid for its full 7-day life even after the account holder changed their password) and marks every other pending password-recovery token for that user as used.


### Sesiones de servidor: token corto, renovación, cookies httpOnly (`core/sesiones.py`)

🆕 (sesión 2026-11-02) Antes, el JWT duraba 7 días y vivía en `localStorage`, donde cualquier script inyectado podía leerlo. "Cerrar sesión" solo lo borraba del navegador, así que seguía valiendo, y el bloqueo por inactividad existía solo en la pantalla. Ahora cada login crea una fila en `auth_sesiones` (`models.SesionUsuario`, migración `4ffd2710409b`) y emite dos cookies httpOnly:

- **Acceso** (`aurora_sesion`, path `/api`): JWT de `ACCESS_TOKEN_MINUTOS` (15) con el claim `sid`. `obtener_usuario_actual` valida la sesión **en la misma consulta** que ya traía al usuario (un outer join, sin consulta extra) y responde 401 si está revocada, bloqueada, vencida o es de otra versión de credenciales.
- **Renovación** (`aurora_renovacion`, path `/api/auth`, así que solo viaja a login, renovar, bloquear y cerrar): valor aleatorio del que la BD guarda solo el SHA-256. Vida máxima `SESION_HORAS` (12, no se extiende) y caduca si pasa `SESION_INACTIVIDAD_MINUTOS` (60) sin renovarse. **Sin rotación** a propósito: con varias pestañas, dos renovaciones simultáneas se invalidarían entre sí. La cookie solo viaja a `/api/auth`, y revocar la fila corta la sesión en el acto.
- **Endpoints nuevos**, públicos por `Depends` porque los autentica la cookie de renovación (el acceso pudo haber vencido):
  - `POST /auth/renovar` devuelve un acceso nuevo, sin token en el cuerpo: si un script inyectado pudiera leerlo, la cookie httpOnly no serviría de nada;
  - `POST /auth/bloquear` bloquea la sesión en el servidor (lo llama la pantalla de inactividad);
  - `POST /auth/cerrar-sesion` la revoca y borra las cookies.
  - Un login que trae la cookie de una sesión anterior la revoca como `reemplazada`: es el caso de desbloquear la pantalla.
- **CSRF:** con cookies, el navegador las adjunta solo. Toda petición que cambia algo y se autentica por cookie exige la cabecera `X-Aurora-Cliente`, que un formulario de otro sitio no puede poner; un `fetch` de otro origen con ella dispara un preflight que el CORS rechaza. Además, `SameSite=Lax`.
- **Compatibilidad:** `Authorization: Bearer` se sigue aceptando (Swagger, los `verificar_*_e2e.py`, scripts) y no exige la cabecera anti-CSRF, porque ningún navegador la adjunta solo. El login sigue devolviendo `access_token` en el cuerpo, aunque el frontend lo ignora. Los tokens sin `sid`, emitidos antes de esto, valen hasta que vencen.
- **Configuración:**
  - `SESION_COOKIE_SECURE`: por defecto `true` fuera de `ENTORNO=development`;
  - `SESION_COOKIE_SAMESITE`: `lax` sirve mientras frontend y API compartan sitio (`app.x.pe`/`api.x.pe`, o `localhost:3000`/`localhost:8000`, porque el puerto no cuenta). ⚠️ `127.0.0.1:3000` contra `localhost:8000` **no** son el mismo sitio y las cookies no viajan. Con la API en otro sitio (un túnel ngrok) hace falta `none`, y entonces Secure.
- **Tests:**
  - `tests/verificar_sesiones_e2e.py` (prefijo `ZZSES`, :8010, 42/42): cookies y sus atributos; CSRF por cookie frente a Bearer; renovar; bloquear (cookie y Bearer de esa sesión dan 401, renovar da 401 y borra las cookies); desbloquear reemplaza; cerrar revoca un acceso copiado antes; cambio de contraseña; inactividad y vida máxima; tokens sin `sid`;
  - `aurora_ui/e2e/sesion.spec.ts` lo cubre en el navegador real.
- **Pendiente:** las filas vencidas de `auth_sesiones` no se purgan todavía. Es una tarea periódica simple para cuando el volumen lo pida.

### SSRF protection on `Institucion.logo_url`

[core/url_segura.py](../backend/core/url_segura.py) validates any URL before it's stored (`PATCH /instituciones/{id}`) and again before it's fetched (PDF generation): only `https`, only port 443, no userinfo in the URL, and — the part a plain scheme/port check misses — the hostname is resolved and **every** IP it returns must be public (`ipaddress.is_global`, with IPv4-mapped IPv6 addresses unwrapped first); the actual HTTP connection is then pinned to that already-validated IP (TLS SNI still targets the hostname), so a DNS record that changes between validation and fetch can't be used to reach an internal address. No redirects are followed, the response must be `image/*`, and it's capped at 2 MiB with a 5s timeout. `descargar_logo_seguro()` never raises — a bad or unreachable logo just means no logo on the PDF, not a broken report.


### Rate limiting on the public exam endpoints

[core/limiter.py](../backend/core/limiter.py) — the shared `limiter` instance, imported from here, never a second `Limiter()`. Every public exam endpoint (comenzar, preguntas, progreso, guardar, finalizar, estado-resultados, informe-pdf, campos-socio) carries **two** stacked limits: a strict one keyed by the magic-link token (`clave_por_token`, via `@limiter.limit(..., key_func=clave_por_token)`), and a loose one keyed by client IP (`@limiter.shared_limit(..., scope=ambito_ip(nombre))`) — loose on purpose, because a whole classroom typically shares one NAT'd public IP. The per-IP limit **must** use `shared_limit` with a fixed scope string from `ambito_ip()`; slowapi's default scope is the URL path, which for these routes includes the token, so a plain `@limiter.limit` per-IP rule silently counts per (IP, token) instead of per IP and never fires against token enumeration. Auth endpoints keep their own limits (`5/minute` login/registration, `3/minute` password-recovery requests). Deploying behind a reverse proxy needs `uvicorn --proxy-headers --forwarded-allow-ips=...` or every student appears to share the proxy's IP; the counters live in each worker process's memory, so multiple workers each count independently.


### Captcha de imagen en el login (`core/captcha.py`)

🆕 `GET /api/auth/captcha` (público, 30/min por IP) devuelve `{habilitado, captcha_id, imagen}` — la imagen es un PNG en data URL con 5 caracteres distorsionados (fuente, tamaño, color y rotación distintos por carácter, ondulación y trazos cruzados). El texto **nunca** sale del backend: el almacén guarda solo un HMAC-SHA256 del código con `SECRET_KEY`. `POST /api/auth/login` recibe además `captcha_id`/`captcha_respuesta` como campos de formulario y valida el captcha **antes** de mirar la contraseña — si fuera después, un script podría seguir probando claves y solo "fallar el captcha" sin coste. Cada captcha es de **uso único** (se saca del almacén al verificarlo, acierte o no), vence a los 5 minutos y el almacén tiene tope de 10 000 pendientes. Igual que el contador de `core/limiter.py`, el almacén sigue la regla de `ALMACEN_SEGURIDAD_URL` (ver la sección siguiente).

`LOGIN_CAPTCHA_OBLIGATORIO=false` lo apaga (entonces `/captcha` responde `habilitado=false` y el login de `aurora_ui/app/page.tsx` oculta el bloque). Por defecto está **encendido** — por eso el uvicorn de `:8010` que usan los `verificar_*_e2e.py` y la suite de Playwright debe arrancarse con `LOGIN_CAPTCHA_OBLIGATORIO=false`: todos inician sesión por script y no pueden leer la imagen.

### Contadores de seguridad compartidos en Redis (`core/almacen_seguridad.py`)

🆕 (sesión 2026-11-02) El rate limit de slowapi, el almacén de captchas y los contadores del captcha adaptativo vivían en la memoria de cada proceso. Con más de un worker de uvicorn no se compartían: un captcha emitido por un worker no lo conocía otro, y cada worker tenía su propio cupo de intentos. Con `ALMACEN_SEGURIDAD_URL=redis://host:6379/2` los tres van a Redis (el mismo servidor de Celery, en otra base; db 0/1 son de Celery), con claves bajo el prefijo `aurora:seg:`:

- captchas → `SET ... EX 300`, y la verificación hace `GET`+`DEL` en una transacción, así que siguen siendo de uso único aunque dos workers reciban el mismo `captcha_id`;
- fallos de contraseña → un sorted set por IP o por correo, puntuado con `time.time()`, recortado a la ventana de 15 min y con TTL;
- rate limit → `storage_uri` de slowapi con `in_memory_fallback_enabled`.

Sin la variable todo queda en memoria como antes (desarrollo y tests unitarios); fuera de `ENTORNO=development`, `main.py` deja un aviso en el log al arrancar. **En producción con varios workers es obligatoria.** Si Redis se cae en pleno uso, cada operación vuelve a la memoria del proceso y lo registra en el log, en vez de impedir el login. ⚠️ Si `:8000` y `:8010` comparten la misma URL, también comparten el cupo de `/login` (5/min por IP), así que conviene no definirla en el `.env` de desarrollo o usar una base distinta por servidor. Test: `tests/test_almacen_seguridad_redis.py` (necesita Redis, usa la db 15 y la vacía; simula cada worker con un subproceso de Python real).

### Recuperación de contraseña: solo superadmin

🆕 `POST /api/auth/solicitar-recuperacion` solo emite token y envía el correo cuando la cuenta es `rol="superadmin"` y está activa (decisión del equipo: el superadmin es la cuenta de AuroraSoft con correo real, `auroraintegratedconsulting@gmail.com`; a admin/psicólogo/colegio les restablece la clave un administrador). Para cualquier otro correo — exista o no, tenga el rol que tenga — la respuesta es la misma, así que el endpoint no delata qué cuentas existen. `/resetear-password` no repite el filtro: la solicitud es la única vía que emite tokens. Frontend: enlace "¿Olvidaste tu contraseña?" en el login → `aurora_ui/app/recuperar-password/` (pide el enlace) → el correo lleva a `aurora_ui/app/resetear-password/?token=…` (que quita el token de la barra de direcciones al leerlo). `verificar_fase3_e2e.py` comprueba que un psicólogo **no** recibe token y luego emite uno directo en la BD para seguir probando la invalidación de JWT (C-4), que vale para cualquier rol.

### Permission surface: `colegio` and clinical content — closed by a five-step remediation

Building the matrix test above (auditing only, no permissions were changed *by the audit itself*) surfaced that most of `modulos/educativo`'s CRUD, plus several genuinely clinical read paths, let `colegio` in by omission — any endpoint using only `Depends(obtener_usuario_actual)` with no role or content gate — rather than by decision. That gap was then closed in a separate five-step remediation, each step covered by its own addition to `tests/test_permisos_colegio_unitario.py` (no DB) and `tests/verificar_permisos_colegio_e2e.py` (prefix `ZZCOLE`, real DB — mounts one actual PHQ-9 application with a real alert-level diagnosis and a real seguimiento note, so the checks prove something is hidden, not just that a list happens to be empty), and reflected in `tests/matriz_permisos_esperada.json`:

1. **`core/deps.py`**: `requerir_staff_clinico = requerir_rol("superadmin", "admin", "psicologo")` — a named alias for the "never `colegio`" tier, so new code expresses this trust boundary with one recognizable name instead of retyping the role tuple (which 19+ call sites already did correctly — the endpoints below simply hadn't).
2. **Mechanical role closure** (`modulos/educativo/router.py`, ~24 endpoints): the full CRUD of `Baremo`/`Dimension`/`Pregunta`/`Opcion`/`ReglaInterpretacion`/`Prueba` (including `carga-masiva`), creating a `Campana`/`matricular-roster`, `GET .../links` (magic-link tokens are access credentials, not read-only data), `GET /casos-pendientes` (the psychologist's alert worklist — this one was actually mis-classified as safe-by-design partway through building the audit tooling itself, and caught before it shipped), and all four `seguimiento` endpoints (create/list/edit/delete follow-up session notes) now require `requerir_staff_clinico`. `PATCH`/`DELETE /seguimiento/{sesion_id}` keep their pre-existing author-ownership check (`sesion.psicologo_id == usuario_actual.id`) as defense in depth on top of the role gate, not instead of it.
3. **Informes gated by `informe_liberado`** (`crud.verificar_puede_ver_informe`): `GET /inscripciones/{id}/informe-pdf` and `.../informe` now apply, for `colegio` only, the exact same condition that already protected the student's own token-based download (`GET /examen/{token}/informe-pdf`) — a retained, unreviewed informe is invisible to `colegio` until a professional releases it, same as before this fix it wasn't. `GET /personas/{id}/informes` (a list, one row per application, each with its own `informe_liberado`) filters row-by-row on the same field instead of a single check.
4. **`ficha-completa` redaction** (`crud.obtener_ficha_completa`, now takes `usuario_actual`): for `colegio`, `historial_evaluaciones` (per-dimension `nivel`) and `sesiones_seguimiento` (narrative `observaciones`/`accion_tomada`) are never queried in the first place — cut before the DB round-trip, not filtered after. No `response_model` was added for this endpoint; the redaction alone removes the sensitive content regardless of how the rest gets serialized, and typing the unrelated parts of this dict (consentimientos, historial académico, citas) was out of scope for this fix.
5. **Dashboard redaction** (`crud.redactar_resultados_dashboard_campana`/`_institucional`): `GET /campanas/{id}/dashboard`, its Excel twin `.../exportar-excel` (same dict, same redaction, applied before `generar_excel_dashboard` builds the spreadsheet), and `GET /procesos/dashboard` all keep participation info (name, estado, fecha, the aggregate `total_*`/`distribucion_por_dimension` counts) visible to `colegio` but blank the per-student `resultados`/`nivel`.

The catalog reads that stay open to `colegio` — `GET /pruebas/`, `/pruebas/{id}/completa`, `/pruebas/{id}/reglas`, `/baremos/{dimension_id}`, `/campanas/` (listing) — are a product decision, not a leftover omission, and are recorded as such in the matrix test's `_COLEGIO_POR_DISENO_CONOCIDO`. As of this remediation, the matrix test's report step (`reportar_endpoints_sensibles_sin_exclusion_de_colegio`) finds **zero** unreviewed endpoints where `colegio` passes the `Depends` layer — any future one it finds is a new gap, not a rediscovery of these.

Deliberately not built yet, on top of the student-core structure above (it's meant to be built *on* this, not alongside it): any dashboard reading the academic structure (per-section, per-grade breakdowns, counts, charts — `app/(educativo)/academico/page.tsx` exists but is a plain CRUD, not a dashboard), follow-up sessions beyond the existing basic `SesionSeguimiento`, documents/images on a student's record, and every bit of frontend for any of this (including for Excel import and for the entire motor de documentos institucionales, both built backend-only) — `crear_tablas.py`'s `BORRAR`-gated reset already covers the new tables, but no UI does yet. `POST /educativo/comenzar-test/{token}` still requires `RegistroAlumnoDemograficos` in its body even for a roster-linked student whose data is already known and gets silently preferred over what's submitted — loosening that requirement is exam-flow/frontend work, intentionally deferred. The institutional policy for which of the two tracks (apoderado consentimiento / student asentimiento) an application requires is **now implemented** (`Institucion.exigir_asentimiento_estudiante`, see "Two independent tracks" above) — apoderado still gates unconditionally, the student's own asentimiento only when a school opts in. ARCO acceso/rectificación at the `Persona` level are **now implemented** too (see above), and so is an ARCO export scoped to one specific `ConsentimientoInformado` record (`?consentimiento_id=` on `exportar-datos-arco`, docs/gaps-pendientes.md) — it recorts `inscripciones`/`informes` to what that one consent covers, deliberately leaving out expediente/sesiones/citas/datos_familiares/antecedentes/contactos (none of those link to a single consent or inscripción). `evidencia_ruta` on `ConsentimientoInformado` is **no longer a placeholder** either — `POST .../consentimiento/{id}/evidencia` uploads the real signed/scanned document through `core/storage/` (docs/gaps-pendientes.md). Annual grade promotion **is now implemented** (`ProcesoPromocion`, see "Promoción anual de estudiantes" above) — Excel import itself still has no promotion logic of its own and still requires the target `Seccion` to already exist for the requested `anio_escolar`, same as manual `POST /personas/{id}/matricula`. The motor de documentos institucionales's read-audit trail gap is **now closed** (`RegistroLecturaDocumento`, see "Motor de documentos institucionales" above).
