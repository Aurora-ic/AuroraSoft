## Frontend architecture

Read [aurora_ui/AGENTS.md](../aurora_ui/AGENTS.md) first: this is Next.js 16, whose APIs and conventions differ from older versions — consult `node_modules/next/dist/docs/` before writing App Router code rather than relying on memory. (`aurora_ui/CLAUDE.md` just imports that file.)

Route groups map to audiences, and the group name never appears in the URL:

- `app/(educativo)/` → `/estudiantes`, `/campanas`, `/agenda`, `/academico`, `/casos-riesgo`, `/pruebas` — the psychologist's app. `/agenda` is a plain list of the logged-in psychologist's `CitaProgramada` rows (`GET /personas/citas/mi-agenda`) with a cancel button, not a calendar/grid view. `/academico` is a real CRUD for `NivelEducativo`/`Grado`/`Seccion` (create/list against `GET/POST /admin/personas/academico/{niveles,grados,secciones}`), not a dashboard.
- `app/(superadmin)/master/` → AuroraSoft's own back office, guarded by `<RequireAuth rolesPermitidos={["superadmin"]}>`.
- `app/(examen)/examen/[token]/` → the student's public exam, intentionally with no sidebar and no auth guard. Keep it that way; a guard here would lock students out.

Auth is client-side only: [contexts/AuthContext.tsx](../aurora_ui/contexts/AuthContext.tsx) stores the JWT in `localStorage` under `aurora_token` and decodes `sub`/`rol`/`institucion_id` from it ([lib/jwt.ts](../aurora_ui/lib/jwt.ts)) without a `/auth/me` round-trip — there is still no `/auth/me` endpoint on the backend. `<RequireAuth>` is cosmetic — the backend dependencies are the real enforcement, including the credential-versioning check above, so a token revoked by a password change fails server-side even though the frontend has no way to notice proactively.

Data fetching goes through [lib/api-client.ts](../aurora_ui/lib/api-client.ts), which attaches the bearer token and normalizes errors into `ApiError`. Login is the exception: the backend uses `OAuth2PasswordRequestForm`, so it posts `application/x-www-form-urlencoded` with the email in the `username` field.

Tailwind v4 is configured entirely through the `@theme` block in [app/globals.css](../aurora_ui/app/globals.css) — there is no `tailwind.config`. Brand tokens: teal is the primary palette, `mist` the app background, `ink` the text, and `amber` is reserved exclusively for risk alerts. Don't spend amber on ordinary accents.

### Known rough edges

- `AuthContext.login` still hardcodes `http://127.0.0.1:8000/api/auth/login` (`contexts/AuthContext.tsx`) instead of using the `login()` helper in `lib/api-client.ts` that respects `NEXT_PUBLIC_API_URL` — a deployment with a different API origin breaks login silently.
- **`app/(educativo)/pruebas/page.tsx`, `campanas/nueva/`, `campanas/[id]/dashboard/`, and the public exam page (`app/(examen)/examen/[token]/`) are no longer empty/placeholder** — all four now have real, functional (deliberately undesigned — no visual polish invested, plain Tailwind utility classes matching the rest of the app) implementations:
  - `/pruebas` — read-only catalog browser (`GET /educativo/pruebas/`), expandable per test to show its dimensions (`GET .../{id}/completa`). Loading a new instrument's items/baremos is still a data exercise (seed script), never a form on this page, on purpose.
  - `/campanas/nueva` — create a campaign (`POST /educativo/campanas/`), then matricular a chosen subset of the padrón (`POST .../matricular-roster`, raw `persona_ids: number[]` body — not wrapped in an object), then copy each generated magic link.
  - `/campanas/[id]/dashboard` — stats, distribución por dimensión, tabla de alumnos, ver/copiar links, exportar Excel, and cerrar/cancelar (`POST .../cerrar`, `.../cancelar`). **Still missing from this screen**: editing `nombre_grupo`/`fecha_fin`/`prueba_id` (`PATCH /educativo/campanas/{id}`) and triggering `POST /educativo/inscripciones/{id}/reprocesar` — both exist on the backend, neither has a UI control yet.
  - `app/(examen)/examen/[token]/page.tsx` — the full public student flow: datos demográficos + consentimiento (`comenzar-test`, handles resume), campos sociodemográficos propios de la institución when any exist, preguntas with **autosave per answer** (`POST .../guardar` fires on every selection, not on a manual "save progress" button — resumible via `GET .../progreso`, which pre-fills already-answered items), `finalizar`, and the post-finalizar screen (`estado-resultados` message + PDF download when `informe_liberado`). Verified end-to-end against the real backend (no browser available in that session — simulated via direct HTTP calls matching the frontend's exact payloads) including a real generated PDF download.
  - New types added to `types/api.ts` for all of this: `Prueba`/`PruebaDetalle`/`Dimension`, `Evaluacion`/`EvaluacionCreate`/`EvaluacionUpdate`, `InscripcionCampana`/`MatriculaRosterResponse`, `DashboardCampana`/`AlumnoDashboard`/`ResultadoAlumnoDashboard`, and the public-exam-flow types (`RegistroAlumnoDemograficos`, `CampoSociodemografico`, `PreguntaExamen`/`OpcionExamen`, `ProgresoExamen`, `DiagnosticoAlumno`, `EstadoResultadosAlumno`).
- Both `master/` pages (`master/page.tsx`, `master/clientes/page.tsx`) are still empty files — AuroraSoft's own back office has no frontend yet.
- There's no calendar-style view or in-app reminder anywhere: `/agenda` (see above) is a text list, and the only real "recordatorio" is the `notificar_agenda_diaria.py` cron email — it never surfaces in the UI. The post-login landing page for staff is the student roster (`/estudiantes`), not a dashboard, so there's no home screen for an agenda/reminder widget to live on even if one existed.
- The motor de documentos institucionales (backend, fully built — see above) **now has its first screen**, embedded in the student ficha (`app/(educativo)/estudiantes/[personaId]/page.tsx`, new "Documentos institucionales" section) — not a separate route. It covers: picking a `PlantillaDocumento` of the institución and creating a `DocumentoInstitucional` for that one student (`alcance='personas_especificas'`), editing `texto_libre`/`grupo_campos` content and `datos_filiacion`'s one professional field (`diagnóstico_presuntivo`), generating v1/reemitiendo with motivo, and downloading the real PDF. **Deliberately left out of this first screen**: manually linking/unlinking a `resultados_prueba` section to an `Inscripcion` (`PUT/DELETE .../resultados-prueba` — the automatic engine already covers the common case; unlinked sections just render read-only as "se completa automáticamente"), and the catalog-authoring side (`TipoDocumento`/`PlantillaDocumento`/`PlantillaSeccion` CRUD) — those stay API/Swagger-only, consistent with "the platform owner builds each school's template, never a self-serve designer." `types/api.ts` gained `TipoDocumento`, `PlantillaDocumento`, `PlantillaSeccion`, `DocumentoInstitucional`, `DocumentoInstitucionalEstudiante`, `DocumentoInstitucionalDetalle`, `DocumentoInstitucionalSeccionContenido`, `DocumentoInstitucionalVersion`. `lib/api-client.ts` gained a `put` method (only had `get/post/patch/delete` before — needed for `PUT .../secciones/{id}`). Backend gained one small additive change to support this: `GET /documentos/` takes an optional `persona_id` filter (join on `DocumentoInstitucionalEstudiante`) so the ficha can list "documents of this student" without loading the whole institución and filtering client-side.
