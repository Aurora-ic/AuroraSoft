> Parte de `CLAUDE.md`, separada en la fase 8 del plan de remodelación. Arquitectura del frontend (`aurora_ui/`) y sus pendientes conocidos.

## Frontend architecture

Read [aurora_ui/AGENTS.md](../aurora_ui/AGENTS.md) first: this is Next.js 16, whose APIs and conventions differ from older versions — consult `node_modules/next/dist/docs/` before writing App Router code rather than relying on memory. (`aurora_ui/CLAUDE.md` just imports that file.)

Route groups map to audiences, and the group name never appears in the URL:

- `app/(educativo)/` → `/estudiantes`, `/campanas`, `/documentos`, `/agenda`, `/academico`, `/casos-riesgo`, `/pruebas` — the psychologist's app. `/agenda` is a plain list of the logged-in psychologist's `CitaProgramada` rows (`GET /personas/citas/mi-agenda`) with a cancel button, not a calendar/grid view. `/academico` is a real CRUD for `NivelEducativo`/`Grado`/`Seccion` (create/list against `GET/POST /admin/personas/academico/{niveles,grados,secciones}`), not a dashboard.
- `app/(superadmin)/master/` → AuroraSoft's own back office, guarded by `<RequireAuth rolesPermitidos={["superadmin"]}>`.
- `app/(examen)/examen/[token]/` → the student's public exam, intentionally with no sidebar and no auth guard. Keep it that way; a guard here would lock students out.

Auth is client-side only: [contexts/AuthContext.tsx](../aurora_ui/contexts/AuthContext.tsx) stores the JWT in `localStorage` under `aurora_token` and decodes `sub`/`rol`/`institucion_id` from it ([lib/jwt.ts](../aurora_ui/lib/jwt.ts)) without a `/auth/me` round-trip. **`GET /auth/me` now exists on the backend** (docs/gaps-pendientes.md) — nothing in `aurora_ui` calls it yet, so this stays the real behavior today; wiring it in would only let the UI confirm the decoded JWT against the server, not change what data is available. `<RequireAuth>` is cosmetic — the backend dependencies are the real enforcement, including the credential-versioning check above, so a token revoked by a password change fails server-side even though the frontend has no way to notice proactively.

Data fetching goes through [lib/api-client.ts](../aurora_ui/lib/api-client.ts), which attaches the bearer token and normalizes errors into `ApiError`. Login is the exception: the backend uses `OAuth2PasswordRequestForm`, so it posts `application/x-www-form-urlencoded` with the email in the `username` field.

Tailwind v4 is configured entirely through the `@theme` block in [app/globals.css](../aurora_ui/app/globals.css) — there is no `tailwind.config`. Brand tokens: teal is the primary palette, `mist` the app background, `ink` the text, and `amber` is reserved exclusively for risk alerts. Don't spend amber on ordinary accents.

### Known rough edges

- **Fixed**: `AuthContext.login` no longer hardcodes `http://127.0.0.1:8000/api/auth/login` — it now calls the `login()` helper in `lib/api-client.ts`, which respects `NEXT_PUBLIC_API_URL` and already handled token storage (`guardarToken`) correctly; that helper existed since Fase 7 but had zero callers until now (nothing else in the app imports the named `login` export, only the default `apiClient` object). A deployment with a different API origin no longer breaks login silently.
- **`app/(educativo)/pruebas/page.tsx`, `campanas/nueva/`, `campanas/[id]/dashboard/`, and the public exam page (`app/(examen)/examen/[token]/`) are no longer empty/placeholder** — all four now have real, functional (deliberately undesigned — no visual polish invested, plain Tailwind utility classes matching the rest of the app) implementations:
  - `/pruebas` — read-only catalog browser (`GET /educativo/pruebas/`), expandable per test to show its dimensions (`GET .../{id}/completa`). Loading a new instrument's items/baremos is still a data exercise (seed script), never a form on this page, on purpose. **🆕 Also hosts "Dashboard por salón o grado"** (not documented here before this pass, though the feature predates this session): a cascading Nivel→Grado→Sección picker plus a prueba select, submitting to `GET /educativo/dashboard/academico?prueba_id=&seccion_id=|grado_id=` — aggregates results across *every* campaign in which that prueba was applied to that salón/grado (not a single campaign, unlike `/campanas/[id]/dashboard` below), using `Inscripcion.seccion_id`'s historical snapshot. No dedicated export for this view (the campaign dashboard's Excel export doesn't cover it).
  - `/campanas/nueva` — create a campaign (`POST /educativo/campanas/`), then matricular a chosen subset of the padrón (`POST .../matricular-roster`, raw `persona_ids: number[]` body — not wrapped in an object), then copy each generated magic link.
  - `/campanas/[id]/dashboard` — stats, distribución por dimensión, tabla de alumnos, ver/copiar links, exportar Excel, and cerrar/cancelar (`POST .../cerrar`, `.../cancelar`). **Still missing from this screen**: editing `nombre_grupo`/`fecha_fin`/`prueba_id` (`PATCH /educativo/campanas/{id}`) and triggering `POST /educativo/inscripciones/{id}/reprocesar` — both exist on the backend, neither has a UI control yet.
  - `app/(examen)/examen/[token]/page.tsx` — the full public student flow: datos demográficos + asentimiento (`comenzar-test`, handles resume), campos sociodemográficos propios de la institución when any exist, preguntas with **autosave per answer** (`POST .../guardar` fires on every selection, not on a manual "save progress" button — resumible via `GET .../progreso`, which pre-fills already-answered items), `finalizar`, and the post-finalizar screen (`estado-resultados` message + PDF download when `informe_liberado`). Verified end-to-end against the real backend (no browser available in that session — simulated via direct HTTP calls matching the frontend's exact payloads) including a real generated PDF download.
  - **Fixed, real bug**: this page used to destructure its route param as a plain prop (`function ExamenPage({ params }: { params: { token: string } })`, `const token = params.token`) — the old Pages-Router-era pattern. Next.js 16's `params` is a `Promise`; accessing `.token` directly off it synchronously returns `undefined`, not a type error, so every call in this file silently sent the literal string `"undefined"` as the token (`POST /educativo/comenzar-test/undefined`, a 404 the user sees as "El link de evaluación es inválido o no existe.") — found only by a user actually clicking a real generated link. Fixed to `useParams<{ token: string }>()` from `next/navigation`, the same pattern every other dynamic page in this app already used correctly (`campanas/[id]/dashboard/page.tsx`, `estudiantes/[personaId]/page.tsx`) — this was the one page that hadn't been written that way. A residual `[browser] A param property was accessed directly with params.token... sync-dynamic-apis` console warning persists even after the fix and does not reproduce on the other pages using the identical `useParams()` call — real requests do carry the correct token (verified against the backend), so this looks like framework-instrumentation noise specific to this route rather than an actual bug; not chased further.
  - **`GET /educativo/examen/{token}/intake`** (new backend endpoint, see docs/informes-psicometricos.md "Exam resumption") is called on mount: a demographic field already known (roster-matriculated student) renders read-only instead of as an input, and the "¿en nombre de otra persona?" block only appears — open, not collapsed — when the prueba's `informante_tipo` actually isn't `"estudiante"`. An asentimiento-informado disclosure (hardcoded frontend text, marked "sugerido, pendiente de validación institucional/profesional" — not yet backend-configurable, see docs/estudiante-nucleo-y-privacidad.md) now sits above the acceptance checkbox, whose label and the three `Inscripcion` columns it writes to were also renamed from "consentimiento" to "asentimiento" this same session (see that doc).
  - New types added to `types/api.ts` for all of this: `Prueba`/`PruebaDetalle`/`Dimension`, `Evaluacion`/`EvaluacionCreate`/`EvaluacionUpdate`, `InscripcionCampana`/`MatriculaRosterResponse`, `DashboardCampana`/`AlumnoDashboard`/`ResultadoAlumnoDashboard`, and the public-exam-flow types (`RegistroAlumnoDemograficos`, `CampoSociodemografico`, `PreguntaExamen`/`OpcionExamen`, `ProgresoExamen`, `DiagnosticoAlumno`, `EstadoResultadosAlumno`).
- **The student ficha gained a "Pruebas aplicadas" section** (`app/(educativo)/estudiantes/[personaId]/page.tsx`, right before "Expediente clínico") — see docs/informes-psicometricos.md ("Revisar/editar el informe desde la ficha del alumno") for the full writeup: a history of every informe the student has (any instrument, not just PHQ-9, via the pre-existing `GET /educativo/personas/{id}/informes`), each with a review panel that reuses `PATCH /inscripciones/{id}/revision-informe` and `POST .../informe/reemitir` — both of which existed on the backend with no UI anywhere until now. New types in `types/api.ts`: `DetalleInforme`, `RevisionInformeRequest`, `VersionInforme` (`HistorialInformePersona` already existed, reused as-is).
- **🆕 `DimensionBar` reconectado en los 2 dashboards, con un bug de diseño corregido** (sesión 2026-10-13): el componente (`components/ui/DimensionBar.tsx`) llevaba borrado por no tener ningún uso — su propio comentario decía que debía usarse en 3 pantallas (ficha del alumno, dashboard de campaña, casos-riesgo) que nunca llegaron a conectarlo. Un análisis dedicado encontró que ninguna de esas 3 aplica tal cual hoy (ninguna tiene mínimo/máximo del baremo disponible, y "casos-riesgo" opera por prueba completa, no por dimensión), pero sí encontró un 4º lugar real y barato: la columna "Resultados" de `campanas/[id]/dashboard/page.tsx` y la lista de alumnos de la sección "Dashboard por salón" en `pruebas/page.tsx` eran, hasta este cambio, texto plano concatenado ("Ansiedad: alto, Depresión: 14") **sin ningún indicador visual de riesgo en ninguna de las dos pantallas** — un psicólogo revisando una campaña de varias decenas de alumnos tenía que leer cada celda para detectar quién necesita atención. `DiagnosticoAlumno.rango_minimo`/`rango_maximo`/`es_alerta` ya estaban snapshotados y ya estaban en memoria en el mismo join que arma la tabla (`crud._armar_alumnos_y_distribucion`) — exponerlos en `ResultadoAlumnoDashboard` no necesitó consulta nueva ni migración (ver docs/motor-scoring.md). Aprovechando la reconexión, se corrigió también un bug real del diseño original: el color de la barra se elegía buscando el TEXTO de `nivel` en un diccionario fijo — justo el antipatrón que docs/motor-scoring.md ya advierte ("never infer risk from the text of `nivel`... un tramo de alerta real puede llamarse 'Sin indicadores aparentes'") — ahora recibe `esAlerta: boolean`, el campo autoritativo. Ambas tablas caen a texto plano cuando el backend no manda mínimo/máximo (dimensión sin baremo aplicable, o `modo_interpretacion='perfil'`). La redacción ya existente para el rol `colegio` (vacía `resultados` por completo) cubre los 3 campos nuevos sin cambios de permisos.
- **🆕 La sección "Pruebas aplicadas" gana vista previa de PDF embebida y 3 campos de revisión nuevos** (sesión 2026-10-13, ver docs/informes-psicometricos.md): al abrir "Revisar informe", el panel ahora es un layout de dos columnas — a la izquierda un `<iframe>` con el PDF actual (blob URL del mismo `GET .../informe-pdf` que ya usaba "Descargar"; sin librería nueva, lo renderiza el visor nativo del navegador), con botón "Actualizar vista previa" y refresco automático tras reemitir; a la derecha, el formulario de edición de siempre más 3 campos nuevos — "Técnicas adicionales" (`tecnicas_override`, completa el último hueco de editabilidad por aplicación individual de las 4 secciones iniciales del PDF), "Nombre en la firma" y "DNI del profesional en la firma" (`firma_nombre_override`/`firma_dni_override`, completan el bloque de firma — antes el nombre era 100% automático y el DNI siempre un placeholder en blanco). `types/api.ts` (`DetalleInforme`/`RevisionInformeRequest`) y `pruebas/page.tsx`/`campanas/nueva/page.tsx`/`campanas/[id]/dashboard/page.tsx` (`Prueba.nombre_corto`, `DashboardCampana.nombre_corto_prueba`, `DashboardAcademico.nombre_corto_prueba`) se actualizaron en el mismo pase — el catálogo de pruebas ahora muestra el título corto arriba y el nombre completo como descripción (antes al revés), y los selects de prueba usan el nombre corto con el nombre completo como `title` (tooltip) en vez de saturar la lista. `tsc --noEmit` limpio.
- **The student ficha's identity-adjacent data is now unified into one "Datos de filiación del estudiante" section** (`app/(educativo)/estudiantes/[personaId]/page.tsx`) — previously four separate concerns rendered as separate `<section>`s (and two of them, `PersonaDatosFamiliares`/`PersonaAntecedentesClinicos`, had full backend CRUD — `GET/PATCH /personas/{id}/datos-familiares` and `.../antecedentes-clinicos` — but **zero UI at all**, despite being asked about explicitly). Now one `<section>` holds four sub-blocks, each still hitting its own independent endpoint exactly as before (this was a visual/layout change, never a data-model or API change): **Identidad** (`Persona`, unchanged), **Datos familiares** (`numero_hermanos`/`vive_con`/`lugar_nacimiento`/`lugar_procedencia`, new UI), **Antecedentes clínicos externos** (the two `recibe_*_externa` booleans + their `detalle_*` + `diagnostico_reportado`, new UI — the two booleans render as a 3-state `<Select>` "Sin especificar"/"Sí"/"No", never coerced to a default, since `NULL` on the backend means "not asked yet" and must stay distinguishable from "no"), and **Contactos familiares** (`ContactoFamiliar`, moved here, unchanged otherwise). Read is open to any authenticated role (including `colegio`) on the two new sub-blocks, matching the backend's own `permisos.STAFF_CLINICO`-gated `PATCH`; the UI hides the "Editar" button for `colegio` on those two instead of letting it hit a 403 on save. Verified against a real running backend (contract matches exactly) and `tsc --noEmit` clean; no interactive browser was available in that session to click through it, so a manual check is still worth doing after pulling this.
- **First real adoption of the `components/ui/` primitives built in a prior "Fase 6"** (`Input`/`Select`/`Tabla`'s `TheadFila`/`Th`/`Campo` existed with zero call sites anywhere in the app until now): the new "Datos de filiación" section above uses `Input`/`Select` throughout, and the existing "Contactos familiares" table was migrated from a hand-written `<table>` to `Tabla`'s `TheadFila`/`Th` (this does change its header's look — `bg-mist/70` background, uppercase bold text — to match the header style already used in `estudiantes/page.tsx`, `estudiantes/importar/page.tsx`, and the campaign dashboard table, which is the point: one shared header style instead of four slightly different hand-written ones). Two new primitives were added in the same pass: `CampoEditable` (extracts the repeated `<label><span>etiqueta</span>{control}</label>` pattern into a component) and `Textarea` (no shared textarea existed before — needed for the long-text antecedentes-clínicos fields). `Campo` gained an optional `className` prop (backward compatible, default `""`) to let a field span multiple grid columns. The other ~9 files still on raw `<input>`/`<select>`/`<th>` (≈78 raw tag instances total) are unmigrated — adopt file-by-file, verifying visually each time, same convention as the rest of this remodeling.
- Both `master/` pages (`master/page.tsx`, `master/clientes/page.tsx`) are still empty files — AuroraSoft's own back office has no frontend yet.
- There's no calendar-style view or in-app reminder anywhere: `/agenda` (see above) is a text list, and the only real "recordatorio" is the `notificar_agenda_diaria.py` cron email — it never surfaces in the UI. The post-login landing page for staff is the student roster (`/estudiantes`), not a dashboard, so there's no home screen for an agenda/reminder widget to live on even if one existed.
- **The motor de documentos institucionales now has a real dedicated screen, `/documentos` (sidebar), replacing the earlier embedded-in-ficha version entirely** — the student ficha (`app/(educativo)/estudiantes/[personaId]/page.tsx`) now only shows a read-only list of "documentos de este alumno", each linking out to `/documentos/[id]`; every bit of create/edit/generate logic that used to live there was removed, not duplicated. Four routes:
  - `/documentos` — lists the institución's `TipoDocumento`-backed `PlantillaDocumento`s and every `DocumentoInstitucional` already generated; "nueva plantilla" picks an existing `TipoDocumento` (still superadmin-only — see below) and creates a `PlantillaDocumento` under the caller's own institución.
  - `/documentos/plantillas/[id]` — **the constructor**: tipografía del cuerpo (fuente/tamaño/interlineado/justificado) *and*, new, independent tipografía del título del documento (negrita/cursiva/tamaño — see the backend section above, `PlantillaDocumento.titulo_negrita`/`titulo_cursiva`/`titulo_tamano_pt`); membrete/pie upload (`admin`/`superadmin` only, reuses the existing `POST /instituciones/{id}/branding/{tipo}`, will 503 on a local/no-public-domain backend by design); and the full section list — add (any of the 12 `tipo_seccion`), reorder (↑↓, implemented as a two-row `orden` swap via `PATCH`), inline título edit, delete (`DELETE /documentos/secciones/{id}`, new endpoint from the same session), and a config editor with **all six configurable types now a real structured form, no JSON textarea left**: `encabezado`'s two booleans, `firma`'s `lineas_fijas`, `grupo_campos`'s field list (all three from the first pass), plus `tabla_dinamica` (columnas with origen automático/libre + `filas_desde_lista_estudiantes`), `firma_doble` (dos columnas, izquierda/derecha, cada una con sus propias `lineas_fijas` y la derecha con `cargo_fijo`), and `ficha_imprimible` (los siete campos de su config: encabezado, leyenda, columnas/filas de la tabla, listas de checkbox anidadas, preguntas abiertas, firmas en blanco) — added in a follow-up pass the same session, closing what had been deliberately left as a raw-JSON fallback. The "Configurar" button itself only renders for the six `tipo_seccion` that actually have config (`lib/documentos-constantes.ts:TIPOS_CON_CONFIG_SIMPLE`) — the other six (`texto_libre`/`datos_filiacion`/`datos_familiares`/`resultados_prueba`/`grafico_barras`/`imagen_anexo`) never show it, since their config is either nonexistent or resolved entirely server-side. A generic JSON-textarea branch still exists in `EditorConfigSeccion` as a defensive fallback (if the two lists — the `if` chain and the constant — were ever to drift out of sync) but is unreachable in practice today.
  - `/documentos/nuevo` — create a `DocumentoInstitucional`: pick a plantilla, then either a roster multi-select (same padrón-search pattern as `campanas/nueva`) for `alcance='personas_especificas'`, or a cascading Nivel→Grado→Sección picker for `alcance='estructura_academica'` (whole grade/section at once — the backend already supported this, nothing in the frontend used it before this pass).
  - `/documentos/[id]` — content editor per section (texto_libre with viñetas, grupo_campos, tabla_dinamica libre — all three ported verbatim from the old embedded version) plus the two new types from this session: `grafico_barras` (manual etiqueta/valor list, or linking to a real `Inscripcion` via the student's `GET /educativo/personas/{id}/informes` history — same `PUT/DELETE .../resultados-prueba` mechanism `resultados_prueba` already used) and `imagen_anexo` (file upload via `apiClient.postForm`, plus an `onPaste` handler so a copied image can be pasted directly into the file input — no separate "paste" endpoint, it's the same upload call). Generar/reemitir and version history/download are also ported verbatim.
