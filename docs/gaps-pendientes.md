## Known backend gaps (not blocking, not yet built)

Kept here so they aren't rediscovered from scratch: **`GET /auth/me` is now built** — depends on `obtener_usuario_actual` (same token-version/licencia validation that already protects every other endpoint) and returns `schemas.UsuarioResponse` as-is, no logic of its own; any authenticated role can call it (it exposes nothing a decoded JWT didn't already give the caller). Closes the gap this file used to document as "the frontend decodes the JWT locally, with no round-trip to confirm who the user actually is." Tests: `test_gaps_backend_unitario.py`. **ARCO acceso and rectificación are now built** (closing what used to be documented here as a gap) — `GET /admin/personas/{id}/exportar-datos-arco` (`requerir_staff_clinico`: superadmin/admin/psicologo, never `colegio`; tenant-checked like the rest of this ficha) exports ficha, historial académico, datos familiares/antecedentes clínicos, contactos, ambos consentimientos, every inscripción with its full diagnóstico content (not just `nivel`), informe version metadata (never the PDF binary), sesiones de seguimiento, citas, and the caller's own visible slice of the expediente clínico — entries the caller isn't personally authorized to read (same rule as the expediente endpoints: author or superadmin only) are omitted and only counted (`expediente_entradas_omitidas`), and reading one still logs a `RegistroLecturasExpediente` row exactly as if opened one by one; the motor de documentos institucionales and the informe PDF binary are deliberately out of this export's scope. Separately from all that, **every successful export writes its own unconditional `RegistroAuditoriaArco` row** (`accion="acceso_datos_persona"`, via the shared `registrar_auditoria_arco` helper — never a second hand-built insert) recording who exported, their role at that moment, the IP, the persona exported, and — when passed — the caller's `referencia_solicitud` in `detalle`; unlike rectificación below, this one has no "did something change" gate, because the act being audited is the access itself, which always happened the moment the endpoint returned 200. Rectificación reuses the existing `PATCH /personas/{id}` rather than a new endpoint: an optional `referencia_solicitud_arco` query param makes `crud.actualizar_persona` additionally write one `RegistroAuditoriaArco` row (`accion="rectificacion_persona"`) in the same commit as its existing `RegistroCambiosPersona` diff, but only when that reference is present *and* at least one audited field actually changed — a routine edit (no reference) or a no-op PATCH (reference present, nothing changed) leaves `auditoria_arco` untouched. Both actions reuse `RegistroCambiosPersona`/`auditoria_arco` exactly as instructed, adding no new tables or migrations. Tests: `test_arco_datos_persona_unitario.py`/`verificar_arco_datos_persona_e2e.py` (prefix `ZZARCO`). Anonymization (`/anonimizar-arco`) remains the only ARCO right that's *irreversible* (the newer `AutorizacionAccesoColegio` grant, see "Expediente clínico individual" above, is a school-access permission a psicólogo issues to a `colegio`, not an ARCO right, and doesn't fill this gap). **The cross-campaign historical comparison view and ARCO-scoped-to-one-consentimiento are now built too.** `GET /admin/personas/{id}/historico-campanas` (`requerir_staff_clinico`, never `colegio`) is the working-team view of a student's evolution across every campaign they took: same "don't resurrect it" filter as `obtener_ficha_completa` (`is_deleted`/`is_anonymized` excluded, unlike the ARCO export below, which deliberately includes them), ordered ascending so it reads like a timeline, returned in two shapes from the same query — a chronological `evaluaciones` list and a `comparacion_por_dimension` map keyed by dimension name, each a time-ordered series of `{campaña, fecha, nivel, valor_convertido, es_alerta}` — the second shape being the one that actually answers "how did this student's PHQ-9 score change between March and August" without the caller having to grep the first one by hand. `GET /admin/personas/{id}/exportar-datos-arco` now takes an optional `?consentimiento_id=N`: with it, the export recorts to only the `inscripciones`/`informes` that cite that consentimiento (via `Inscripcion.consentimiento_apoderado_id`/`consentimiento_asentimiento_id` — the same link `matricular_roster_en_campana` already wrote, no new heuristic), returns that one consentimiento instead of the combined apoderado+asentimiento history, 404s if the id doesn't belong to the persona being exported, and — on purpose — leaves out `expediente_clinico`/`sesiones_seguimiento`/`citas_programadas`/`datos_familiares`/`antecedentes_clinicos`/`contactos_familiares`/`historial_cambios_persona`/`registro_auditoria_arco_previo`, none of which link to a `ConsentimientoInformado` or a single `Inscripcion`, so scoping them would mean inventing an unrequested date-based heuristic rather than reusing a real link; identity fields (`datos_personales`, academic history) stay unscoped, since they're not "covered" by any one consentimiento. Tests: `test_gaps_arco_evidencia_unitario.py` / `verificar_gaps_arco_evidencia_e2e.py` (prefix `ZZGAPS`). **`evidencia_ruta` is no longer a dead placeholder either** — `POST /admin/personas/consentimiento/{id}/evidencia` (any authenticated role of the same institución, same as the rest of the consentimiento endpoints — this is administrative, not clinical, content) uploads the real signed/scanned consent document (PDF/JPG/PNG, 10 MB cap, extension allow-listed — the client's filename is never trusted beyond its extension) through the storage service the informes engine already set up (`core/storage/`, new `construir_storage_key_evidencia_consentimiento`), writes the real key into `evidencia_ruta` (finally matching what that column's comment always said it was for) plus upload metadata (`evidencia_nombre_archivo`/`evidencia_content_type`/`evidencia_tamano_bytes`/`evidencia_subido_en`/`evidencia_subido_por_usuario_id`, migration `e0c0768c55fd`), and `GET` of the same path streams it back. A re-upload replaces the previous file at the same key — no versioning, unlike `InformeVersion`. `evidencia_ruta` still accepts a free-text value at consentimiento-creation time for backward compatibility; a real upload overwrites it. **`tipo_consentimiento="estudiante"` is now `"asentimiento"`** — a terminology fix, not a new feature: the student's own track was always legally an *asentimiento* (a minor's assent), distinct from the *consentimiento informado* their apoderado gives, and the old value conflated the two. Renamed end-to-end in one pass (no deprecated alias — there's no real institución deployed yet and no frontend consuming the old names, so additive-then-deprecate wasn't worth the complexity here): the constant `TIPO_CONSENTIMIENTO_ASENTIMIENTO`, the schemas `ConsentimientoAsentimientoCreate`/`ConsentimientoAsentimientoResponse`, the endpoints `POST/.../consentimiento/asentimiento` and `.../asentimiento/revocar`, `Inscripcion.consentimiento_asentimiento_id` (the FK snapshot written at matrícula), and `Institucion.exigir_asentimiento_estudiante` (the institutional policy flag) all moved together, backend models/crud/router/schemas, the DB (migration `d4c774e7c9cf`: drops+recreates the `tipo_consentimiento` CHECK with a backfill `UPDATE` for any pre-existing `'estudiante'` rows, plus two plain column renames with their FK/constraint names kept in sync), every test file that referenced the old names, the permission-matrix snapshot, and `aurora_ui/types/api.generated.ts` (regenerated from the live OpenAPI schema — the hand-maintained `types/api.ts` never referenced this and no page in `aurora_ui` called the old endpoints yet, so the frontend blast radius was zero). **The five free-text status columns now have a CHECK constraint** (`Inscripcion.estado IN ('Pendiente', 'En Progreso', 'Finalizado')`, `estado_interpretacion IN ('completa', 'incompleta')`, `SesionSeguimiento.estado IN ('Pendiente', 'En proceso', 'Atendido')`, `CitaProgramada.estado IN ('Programada', 'Realizada', 'Cancelada')`, `Usuario.rol IN ('superadmin', 'admin', 'psicologo', 'colegio')`) — confirmed against the real database first that no row held a value outside that set, migration `ea0e1784dade` written by hand (`alembic revision --autogenerate` doesn't detect CHECK constraints). Still a plain `String` column, never a native Postgres `ENUM` — adding a value to those needs care inside a transaction, a CHECK doesn't. Tests: `test_gaps_backend_unitario.py`; verified directly against Postgres that an invalid value is rejected with `CheckViolation`. **The `datetime.utcnow()` sweep in `core/` and `modulos/educativo` is now done** — not a blind find-replace: every call site was audited against the real column type it writes to or compares against. Pure writes to a naive `DateTime` column (and the JWT `"exp"` claim, which `python-jose` computes identically either way) moved to `datetime.now(timezone.utc)`; the handful of sites that compare, in the same scope, against a value already read back from a naive column (`core/deps.py`'s licence check, `crud.campana_esta_expirada()`/`_cerrar_o_cancelar_campana()` against `Evaluacion.fecha_fin`, `puede_aplicar_prueba()`'s two reapplication-window filters) deliberately kept `datetime.utcnow()`, each with a comment explaining why switching would raise `TypeError` or silently miscompare — the columns themselves were not migrated to `timestamptz`, that's a separate, bigger change out of scope here. A permission matrix now exists as a *test*, not a document: `tests/test_matriz_permisos_unitario.py` + the checked-in snapshot `tests/matriz_permisos_esperada.json` (see the Commands section above) — it walks `app.routes`, reads the real `Depends(...)` on every `/api` endpoint, and fails on any undeclared/removed/changed endpoint. It does **not** see authorization written inline inside a function body instead of as a `Depends` — see below for what that blind spot turned up and how it was closed.

## Principios rectores de la remodelación de arquitectura

Migrado de `PLAN_REMODELACION_ARQUITECTURA.md` (sección 0) antes de borrarlo — las ocho fases de esa remodelación ya se ejecutaron (ver los commits de `backend/`, `aurora_ui/` y este repo), pero estos principios siguen aplicando a cualquier trabajo futuro de la misma naturaleza (refactors transversales, cierre de huecos de composición del motor, etc.):

1. **Aditivo primero, deprecar después.** Ninguna función/símbolo público se renombra ni se borra en la misma fase en que se introduce su reemplazo. Se agrega el reemplazo, se migran los call sites uno por uno (verificando tests en cada uno), y solo al final — en una fase separada — se elimina lo viejo si ya no lo usa nadie.
2. **Una fase, un commit, una verificación completa.** Cada fase de las que siguen termina con: la suite completa de tests unitarios (`tests/test_*_unitario.py`) en verde, al menos un e2e real relevante corrido contra Postgres, y `tsc --noEmit` limpio del lado frontend si la fase tocó `aurora_ui`. Nunca se empieza la fase siguiente con la anterior a medias.
3. **Nunca tocar dos subsistemas no relacionados en la misma fase.** Las fases de abajo están ordenadas por independencia — se puede ejecutar la 1 sin la 2, etc. Si algo bloquea, se puede parar entre fases sin dejar nada roto.
4. **Los tres repos (`/`, `backend/`, `aurora_ui/`) son independientes** (ver `CLAUDE.md` raíz) — cada fase que toque más de uno debe commitear por separado en cada repo, nunca un commit mezclado.
5. **Todo lo nuevo sigue las convenciones ya establecidas del propio código** (español en identificadores/comentarios, el estilo de test ya usado — scripts con `comprobar()`, no pytest —, el estilo de commit ya usado). No se introduce un segundo estilo en paralelo.
